# ADR-0022: 과목 정렬 순서·색과 세션 완료 할 일 기록

- 상태: 승인
- 날짜: 2026-09-22
- 티켓: BY-724 (스토리 BY-696, 후행 [FE] BY-725)
- 선행: ADR-0021 (과목 > 할 일과 세션 과목 시간)

## 맥락

과목 시트(frontend#179)를 실기기에서 써 보니 ADR-0021 계약에 세 가지가 빠져 있었다.

1. **순서가 서버에 없다.** 끌어서 바꾼 과목 순서를 앱이 localStorage에만 남겨 재설치·기기 변경 뒤 `id` 순으로 돌아간다.
2. **어느 세션에서 무엇을 끝냈는지 남지 않는다.** ADR-0021 갱신(V17)으로 세션↔할 일 연결이 전부 사라져, 기록 탭에서
   "하루 중 어느 세션에서 어떤 할 일을 완료했는지"를 보여줄 저장 기반이 없다.
3. **과목 색이 없다.** 프로필(`users.color_index`)처럼 과목마다 색 정수가 있어야 시트·기록에서 과목을 구별한다.

## 결정

1. **순서는 `study_subject.sort_order`에 보관하고 응답에 번호를 노출하지 않는다.** 목록은 `sort_order asc, id asc`로
   내려가고 배열 순서가 곧 계약이다 — 앱이 정렬 필드를 해석할 일이 없다.
2. **저장은 `PUT /api/subjects/order`로 전체 순서를 한 번에 받는다.** 앱은 드래그 중 자리 바꿈을 화면에만 반영하고 놓을 때
   1회 보낸다. 과목별 `PATCH sortOrder`는 기각: 드래그 결과는 항상 전체 순서라 부분 갱신이 오히려 여러 요청과 중간 상태를
   만든다. 남의·지운·없는·중복 id가 섞이면 400으로 통째 거절해 원자성을 지키고, 빠진 살아있는 과목은 기존 상대 순서대로 뒤에
   붙여 일부만 보내도 된다. 응답은 정렬된 전체 목록(GET과 같은 모양) — `rename`처럼 바뀐 자원을 돌려주고, 빠진 과목이 뒤에
   붙은 서버 결과를 앱이 한 번에 받는다.
3. **새 과목은 살아있는 과목의 `max(sort_order) + 1`이다.** 개수를 쓰면 중간 삭제로 생긴 빈자리(`[0,2,3]`에 count 3) 뒤의
   값과 겹친다. 빈자리는 허용한다 — 순서 저장이 어차피 0..n-1로 다시 매긴다. 동시 저장은 행마다 나중 쓰기가 이기지만
   `(sort_order, id)` 정렬이라 어떤 조합이든 전순서다.
   - 엔티티는 `@DynamicUpdate`다. 순서 저장이 읽어 둔 과목을 flush할 때 Hibernate 기본 UPDATE는 안 바뀐 컬럼도
     함께 쓰므로, 그 사이 다른 요청이 지운 과목의 `deleted_at`을 null로 되돌려 되살릴 수 있었다(Codex 리뷰 P2).
   - 같은 사용자의 과목 생성·순서 저장은 사용자 단위 advisory 락(`pg_advisory_xact_lock`, 룸 도메인과 같은 관용구)으로
     트랜잭션 동안 직렬화한다. 락 없이는 동시 생성 두 건이 같은 살아있는 목록을 읽어 같은 색·같은 순서를 받는다.
4. **색은 생성 시 서버가 "그 사용자의 살아있는 과목이 가장 적게 쓴 인덱스"(동률이면 작은 번호)를 배정하고 이후 바꾸지 않는다.**
   범위는 `0..19`(`SUBJECT_COLOR_COUNT` = 과목 상한)라 20개가 전부 다른 색이고, 지운 과목의 색은 풀려 다시 쓰인다.
   프로필처럼 랜덤으로 뽑는 방식은 기각 — 한 사용자의 목록에 나란히 보이는 값이라 과목 5개만 돼도 겹칠 확률이 40%를 넘는다.
   앱이 고르는 방식도 기각 — 시트에 색 선택 UI가 없어 결정 로직만 앱으로 옮겨질 뿐이다. 앱은 인덱스를 팔레트에 매핑만 한다.
   상한·다음 순서·색은 살아있는 과목 목록(≤ 20건) 한 번으로 계산하고 별도 집계 쿼리를 두지 않는다. 기존 행 백필은
   **살아있는 행만** 세어 색을 매긴다 — 삭제된 행까지 세면 1번째·21번째만 남은 사용자의 두 과목이 같은 색을 받는다.
5. **세션에서 완료한 할 일은 세션의 자식 테이블 `study_session_task_done(session_id, task_id)`에 남긴다.** 세션과 함께
   저장·멱등 대체·삭제되고(`ON DELETE CASCADE`), 자동 확정본 대체 흐름(ADR-0014의 delete-and-replace)도 그대로 탄다.
   - `study_task.done_session_id` 컬럼은 기각: 자동 확정본 교체 때 FK가 끊어져 따로 다듬어야 하고, 해제 뒤 다른 세션에서
     다시 완료하면 이전 세션 기록이 덮여 사라진다.
   - 매핑은 `@ElementCollection<Long>`이다. PK가 `(session_id, task_id)`라 엔티티로 만들려면 surrogate id를 추가하거나
     이 코드베이스에 없는 양방향 매핑을 들여야 한다. 그 대가로 행 전용 리포지토리가 없다 — 읽기 후속은 JPQL join으로 한다.
   - 할 일 FK는 CASCADE하지 않는다. 할 일은 soft delete라 지운 할 일의 기록도 남긴다(ADR-0021 §1과 같은 정책).
6. **앱이 `POST /api/study-sessions`에 `completedTaskIds[]`를 명시적으로 보낸다.** 서버가 `done_at`이 세션 구간 안인
   할 일을 스스로 찾는 방식은 기각 — 다른 기기에서 체크한 것이 섞이고, 앱이 시트에서 체크한 사실이 계약에 드러나지 않는다.
   앱은 로컬 과목 목록에서 `doneAt ≥ 세션 시작`인 할 일을 제출 시점에 파생하므로 스냅샷·복구 계약을 건드리지 않는다.
   스냅샷·복구·자동 확정·구 앱(v1) 경로에는 싣지 않는다 — 자동 확정본은 완료 할 일이 없다.
7. **소유 검증은 ADR-0021 §6 그대로 컨트롤러가 `StudySubjectService.assertTasksOwned`를 먼저 부른다.** 검증 결과를
   `CompletedTask(taskId, doneAt)` 레코드(세션 dto 패키지)로 넘겨 세션 도메인이 과목 엔티티를 모른다 — 의존 방향은
   기존처럼 subject → studysession.dto뿐이다. 할 일은 과목을 거쳐 유저에 닿고, 삭제 여부는 보지 않는다. V17로 사라진
   "taskId가 subjectId 소속" 검증은 되살리지 않는다 — 제출에 subjectId가 함께 오지 않는다.
8. **자정 분할 귀속: 각 할 일은 `done_at`이 속한 `[시작, 끝)` 조각 하나에 붙고, 없거나 범위 밖이면 마지막 조각이다.**
   시간처럼 비례 배분하지 않는다 — 체크는 양이 아니라 사건이다. `done_at`이 null이어도 받는다(앱이 완료 해제한 뒤 제출해도
   기록 전체를 거절하지 않는다). 반개구간이라 정확히 자정에 완료하면 다음 날 조각이다.
9. **읽기는 후속이다.** 이번엔 제출 응답·세션 상세(`StudySessionResponse.completedTaskIds`, id 오름차순)까지만이고
   일간 목록(`StudySessionSummaryResponse`)에 완료 할 일·과목명을 붙이는 조회는 기록 탭 스토리에서 한다. 과목은 soft
   delete라 그때 이름 조회는 `deleted_at`을 무시해야 한다.

## 결과

- 계약: `PUT /api/subjects/order`(기본버전 1, 토큰 필요), `SubjectResponse.colorIndex`, `POST /api/study-sessions`의
  선택 필드 `completedTaskIds`, `StudySessionResponse.completedTaskIds`. 구 앱은 영향 없다.
- 스키마 V19: `study_subject.sort_order`·`color_index`(기존 행은 사용자별 id 순으로 백필), `study_session_task_done`.
  두 컬럼의 `DEFAULT 0`은 원시 INSERT(테스트·수동)용이고 실제 값은 서비스가 넣는다.
- 세션 저장·멱등 재제출·자동 확정본 대체·동시 제출 경로에서 완료 할 일이 세션과 같이 움직인다 — 별도 코드 없이 매핑이 보장한다.
- `StudyTaskRepository.findByIdIn`(V17 이후 미사용)은 소유 조인 쿼리 `findByIdInAndOwner`로 대체했다.
- 후속: 일간 기록 조회, 과목 색 변경(PATCH)·팔레트 디자인, 스냅샷·복구·자동 확정의 완료 할 일.
