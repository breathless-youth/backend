# ADR-0015: API 버전닝 전략 — 엔드포인트 단위 expand/contract + API-Version 헤더

- 상태: 승인
- 날짜: 2026-09-02

## 맥락
운영이 시작되면 API 스펙이 깨지는 변경이 생길 때 프론트와 백엔드를 동시에 배포할 수 없다.
웹은 배포 전환 사이의 짧은 갭이 문제고, 모바일은 앱스토어 심사와 미업데이트 유저 때문에
구버전 클라이언트가 몇 주~몇 달 살아남는다. 따라서 서버가 신·구 스펙을 동시에 지원하는
기간이 필수인데, 그 방식을 정해야 했다.

전체 API 표면을 v1/v2 두 벌로 복제하는 방식(공개 API식 URI 버전닝)은 안 바뀐 엔드포인트까지
복제되어 내부 API에는 과하다. Spring Framework 7(Boot 4)에 API 버전닝이 1급 기능으로
들어와(매핑의 `version` 속성 + `ApiVersionConfigurer`) 추가 의존성 없이 엔드포인트 단위
버전 병행이 가능해졌다.

## 결정
1. **기본은 additive-only.** 필드 추가·옵셔널 파라미터 추가·새 엔드포인트는 깨지는 변경이
   아니므로 버전을 올리지 않는다. 클라이언트는 모르는 필드를 무시한다(tolerant reader).
2. **깨지는 변경만 해당 엔드포인트에 버전을 추가한다** (expand → migrate → contract).
   같은 URL에 `@GetMapping(..., version = "2")` 핸들러를 병행하고, 클라이언트 전환이 끝나면
   구버전 핸들러를 삭제한다.
3. **버전은 `API-Version` 요청 헤더로 전달한다.** RFC 6648 권고에 따라 `X-` 접두사를 쓰지
   않는다. URL 경로 방식(`/api/v1/…`)은 기존 클라이언트의 호출 경로 전체를 옮겨야 해서
   제외했다.
4. **헤더가 없는 요청은 기본버전 1로 해석한다.** 버전 개념 없이 배포된 기존 앱·웹
   클라이언트가 수정 없이 그대로 동작하기 위한 핵심 장치다.
5. **contract(구버전 삭제)는 릴리즈 주기가 아니라 구버전 호출량으로 판단한다.** 모바일
   구버전 앱의 수명을 고려해, 로그·메트릭으로 구버전 호출이 0에 수렴한 것을 확인한 뒤
   삭제한다. 삭제 예고는 Spring의 deprecation 핸들러(RFC 9745 `Deprecation` / RFC 8594
   `Sunset` 응답 헤더)로 통지할 수 있다.
6. **배포 순서는 항상 백엔드(신·구 지원) 먼저, 프론트 나중.** 동시 배포를 전제하는 변경은
   만들지 않는다.

## 구현 요약
- `ApiVersionConfig`: `useRequestHeader("API-Version")` + `setDefaultVersion("1")`.
  기본버전은 지원 버전 목록에 자동 포함되며, 이후 버전은 매핑의 `version` 속성에서
  자동 감지되므로 `addSupportedVersions` 명시가 필요 없다
- 미지원 버전(`API-Version: 99`)·파싱 불가 버전은 매핑 단계에서 거부되어 400
- 검증: `ApiVersionApiTest`

## 갱신 (2026-09-22) — 새 엔드포인트의 버전 규칙 (BY-721)

병행 기간(ADR-0020)에 새 엔드포인트의 버전이 갈렸다. `GET /api/stats/study-days`는 클래스 레벨
`version = "2"`를 물려받아 2였고, 과목 API(`/api/subjects`)는 1이었다(ADR-0021). 규칙이 없으니 FE가
"모든 요청에 2"로 세팅했다가 과목 API에서 400을 맞았다. 규칙을 하나로 정한다.

1. **구 앱(v1.2.x)이 부르던 경로만 `2`다.** 토큰 도입으로 계약이 바뀌어 신·구를 갈라야 하는
   경로(ADR-0020 표의 등록 + 14개)이고, 헤더 없음/1은 구 앱 어댑터가 받는다.
2. **구 앱 대응이 없는 새 경로는 기본버전 `1`이다** — `/api/subjects`, `/api/stats/study-days`, 그리고
   앞으로 추가되는 모든 엔드포인트. 깨지는 변경이 생기면 그때 그 엔드포인트만 결정 2대로 +1 한다.
   - 버전 속성을 아예 빼는 대안(모든 버전에 매칭)은 기각 — FE가 아무 값을 보내도 붙지만 Swagger에
     헤더 파라미터가 실리지 않아 "이 엔드포인트의 버전"이 드러나지 않고, 엔드포인트마다 버전이 있다는
     모델이 흐려진다.
   - 예외는 `POST /api/auth/refresh` 하나다(ADR-0020 결정 2 그대로 버전 속성 없음). access 만료 뒤
     복구하는 경로가 버전 불일치로 400이 나면 앱이 통째로 잠기고, 구 앱 대응도 계약 차이도 없어 가를
     것이 없다. 어떤 값을 보내도 매칭되며 Swagger에 `API-Version` 파라미터가 없다.
3. **버전은 라우팅만 가른다.** 인가는 `SecurityConfig`가 정하므로 버전 1 경로도 구 앱 예외 목록
   (`LegacyApiRequestMatcher`)에 없으면 토큰이 필요하다.
4. **FE는 헤더를 전역 인터셉터에 고정하지 않고 API 정의마다 버전을 둔다.** 원본은 Swagger의 각
   오퍼레이션 `API-Version` 파라미터 기본값이다 — `OpenApiConfig`가 실제 매핑
   (`RequestMappingHandlerMapping`의 `version` 조건)에서 읽어 넣으므로 손으로 고칠 목록이 없다.

`study-days`를 1로 옮겼다(`StudySessionStatsController`는 메서드 레벨 버전). ADR-0020 결정 1의
"모든 HTTP 요청에 2"는 "구 앱 대응이 있는 경로에 2"로 읽는다. 검증: `ApiVersionApiTest`(새 경로에 2를
보내면 400, refresh는 어떤 버전으로도 매칭), `ApiVersionSwaggerDocsTest`(문서 기본값이 매핑 버전).
