# ADR-0042: 소셜 로그인 link 단일화, 계정 병합, 탈퇴 하드 삭제

- 상태: 승인
- 날짜: 2026-11-03
- 티켓: BY-1126
- 관련: ADR-0002(앱 네이티브 소셜 로그인), ADR-0013(소셜 로그인 재도입), ADR-0015(API 버전), ADR-0019(비회원 토큰), ADR-0020(구 앱 계약 병행)
- 설계서: `docs/superpowers/specs/2026-11-03-social-login-design.md`

## 맥락

그룹(BY-1123)은 한 번 만들면 사라지지 않는데 사람의 신원은 기기 UUID(`DEVICE`)라서, 앱을 지웠다 다시 깔면 다른 사람이 되고
그룹장이면 그 그룹은 주인 없이 남는다. 다시 깔아도 같은 사람으로 돌아오는 수단으로 소셜 로그인(구글·카카오·애플)을 붙인다.

ADR-0013에서 정하고 ADR-0019 결정 8과 이전 주석에서 "소셜 로그인은 파킹"이라고 적었던 상태를 이 ADR이 대체한다. 8월 명세(BY-383)의 계약을 기본으로
하되, PR #8처럼 514커밋 낡은 브랜치를 머지하지 않고 지금 dev 위에서 다시 짠다.

## 결정

### 계약

1. 로그인 API는 `POST /api/auth/link` 하나다. 앱은 항상 비회원 토큰을 가진 채 로그인 화면에 오므로 따로 `login`을 두지 않는다.
   - 처음 쓰는 소셜 ID면 **전환**: 같은 users 행의 `(DEVICE, deviceId)`를 `(프로바이더, 소셜 ID)`로 바꾼다. userId가 그대로라 기록·그룹·방이
     모두 이어진다(방도 유지). `isNewUser: true`.
   - 이미 있는 소셜 ID면 **병합**: 이 기기 비회원("옮기는 쪽")의 데이터를 기존 소셜 계정("남는 쪽")으로 옮기고 옮기는 쪽을 지운다.
     부딪히면 남는 쪽이 이긴다. `isNewUser: false`.
2. 잘못된 ID 토큰은 401이 아니라 400 `INVALID_SOCIAL_TOKEN`이다(8월 명세의 401을 바꿈). 앱은 401을 받으면 refresh부터 하므로, 우리 토큰
   문제가 아닌 실패에 401을 쓰면 헛된 refresh가 돈다. 위조·만료·aud 불일치·이미 쓴 토큰·nonce 불일치/누락·DEVICE 프로바이더를 모두 이
   code로 낸다. 알 수 없는 provider 문자열은 요청 형식 오류로 400 `BAD_REQUEST`다. 이미 소셜 계정이면 409 `ALREADY_LINKED`.
   프로바이더가 응답하지 않거나(연결·타임아웃) 5xx·429·읽을 수 없는 응답을 주거나 애플 JWKS를 못 가져오면 토큰 문제가 아니므로
   503 `SOCIAL_PROVIDER_UNAVAILABLE`이다 — 400으로 내면 앱이 장애 때 사용자를 소셜 로그인 처음으로 돌려보낸다.
3. **nonce**: 앱이 원문을 link 요청에 싣고 SDK에는 SHA-256 해시를 넘긴다. ID 토큰에 nonce가 있으면 원문의 해시와 같아야 한다(애플은 필수).
   새어 나간 ID 토큰을 다른 비회원이 link에 넣어 남의 계정 토큰을 받는(병합 경로) 탈취를 막는다. FE가 만든 뒤 넣으면 깨지는 변경이라
   처음부터 계약에 둔다. 구글·카카오는 토큰에 nonce가 있을 때만 맞춰 본다(SDK가 nonce를 못 넣는 경우가 있다).
   - **ID 토큰은 한 번만 받는다**(2026-11-03 사용자 결정 "1회용만 추가"). link 트랜잭션의 첫 문장에서 `used_social_id_token`(V42)에
     서명이 덮는 `header.payload`의 SHA-256 hex와 exp + 5분을 `ON CONFLICT DO NOTHING`으로 넣고, 0행이면 400 `INVALID_SOCIAL_TOKEN`이다.
     토큰 전체가 아니라 앞 두 조각을 키로 하는 이유: 서명 조각은 같은 바이트를 여러 문자열로 쓸 수 있어(base64url의 남는 비트·패딩, jjwt
     RS256으로 확인) 서명만 고쳐 쓴 토큰이 새 토큰으로 통과한다(최종 점검 뒤 발견, 2026-11-04 수정). 5분 여유는 검증하는 프로바이더
     서버의 시계가 DB보다 늦을 때를 위한 것이다. 기한이 지난 기록은 같은 자리에서 지운다(지운 뒤에는 프로바이더 검증이 먼저 거부한다).
     트랜잭션 안이라 전환 경쟁으로 롤백된 시도는 토큰을 쓰지 않은 것이
     되어 재시도가 같은 토큰을 쓰고, 같은 토큰이 동시에 두 번 오면 나중 쪽이 기본 키에서 기다렸다가 0행을 받는다. 원문도 해시도
     로그에 남기지 않는다. **받아들인 위험**: 첫 사용 전에 가로챈 토큰은 여전히 한 번 받힌다 — nonce가 없는 구글·카카오 토큰은 이것만
     막지 못한다. 앱(FE)은 바뀌지 않는다(로그인마다 SDK가 새 토큰을 준다).
4. 허용 aud는 프로바이더마다 목록이다. 환경변수는 `OAUTH_GOOGLE_CLIENT_IDS`, `OAUTH_KAKAO_APP_KEYS`, `OAUTH_APPLE_BUNDLE_ID`와
   선택값 `OAUTH_APPLE_*`(Services ID, Team ID, Key ID, 개인 키, 웹 반환 주소, 안드로이드 콜백 딥링크)다. 운영 yaml은 셋 다 빈 값을
   기본으로 둔다 — 그룹 릴리즈가 로그인 앱보다 먼저 나가므로 값 없이도 기동해야 한다. 허용 aud 목록이 빈 프로바이더는 프로바이더를
   부르지 않고 모든 토큰을 400으로 거부하며, 기동 때 프로바이더마다 WARN을 한 번 남긴다. 쉼표 목록의 빈 항목은 버린다.
5. `POST /api/auth/logout`은 이 기기의 refresh만 지운다. 내 토큰이 이미 회전된 것이면 재사용 감지처럼 전량 폐기, 남의 토큰이면 무시한다.
6. 새 경로는 모두 `version = "1"` 고정이다(ADR-0015).
7. 프로바이더 호출(구글·카카오 tokeninfo, 애플 JWKS·토큰 교환·해지)은 전용 RestClient로 한다. 공유 `RestClient.Builder`에는 타임아웃이
   없고 yaml의 `spring.http.client.*`도 닿지 않아, 그대로면 프로바이더가 멈출 때 요청 스레드가 무한히 묶인다. Slack·Amplitude 발송기처럼
   빌더를 `clone()`해 연결 5초·읽기 5초를 얹는다. 이 호출의 예외에는 원인 예외를 붙이지 않는다 — I/O 예외 메시지의 tokeninfo URL에
   ID 토큰이 실려 있다.

### 병합 규칙

원칙: 옮기는 쪽 행을 남는 쪽 `user_id`로 바꾼다. 남는 쪽과 부딪히는 행은 옮기지 않고 지운다.

| 대상 | 규칙 |
|---|---|
| 공부 세션 | 겹치는 세션은 옮기는 쪽을 폐기한다(같은 시간을 두 번 세지 않는다). 아래 "세션 겹침" 참고 |
| 같은 이름 과목 | NFC 정규화·앞뒤 공백 제거 후 같으면 남는 쪽 과목으로 합치고, 구간·할 일·완료 기록과 옮긴 진행 중 기록(`subject_segments` JSON)의 참조를 바꾼다. 옮기는 쪽 과목은 지우지 않고 남는 쪽의 **지운 과목**으로 둔다 — 링크한 앱의 진행 중 세션이 병합 뒤에도 그 ID로 하트비트·최종 제출을 보내므로, 행이 없으면 소유 검증 400과 자동 확정의 영원한 FK 재시도가 난다. 다른 이름은 뒤 순서로 옮긴다 |
| 푸시 토큰 | 전부 옮긴다(이 기기의 토큰이라 병합 뒤에도 푸시가 와야 한다) |
| 푸시 실험 배정·발송 기록 | 옮기는 쪽 것을 폐기한다(실험 단위가 사람이라 섞으면 분석이 흐려진다) |
| 랭킹 | 같은 순위판·기간에 남는 쪽 기록이 있으면 옮기는 쪽을 지운다. 옮기는 쪽 `ranking_best`는 더 좋은 순위일 때 넘기되, 그 최고가 남는 쪽도 든 마감(남는 쪽에 같은 판·기간의 다른 순위 기록이 있거나 남는 쪽 최고가 같은 판·기간)의 것이면 넘기지 않는다. 메달(1~3위) 밖 순위는 기록 없이 최고만 남아 "기록이 옮겨졌을 때만"으로는 거를 수 없다 |
| 프로필, D-day, 유입 경로 | 남는 쪽 그대로. 없는 것만 옮긴다 |
| refresh 토큰 | 옮기는 쪽 것을 전부 지운다 |
| 그룹장(`study_group.owner_id`) | 옮기는 쪽이 그룹장인 그룹(지운 그룹 포함)은 남는 쪽이 그룹장이 된다. 살아 있는 그룹의 공부방이 열려 있으면 커밋 뒤 `OWNER_CHANGED`를 보내고, 푸시는 보내지 않는다(같은 사람이다) |
| 그룹 멤버 | 같은 그룹에 둘 다 살아 있는 멤버면 옮기는 쪽 행을 지운다. 나머지(나간·내보내진 이력 포함)는 옮긴다 |
| 그룹 신청 | 같은 그룹에 둘 다 `PENDING`이면 옮기는 쪽을 `CANCELED`로 닫는다 — 신청 신고(`user_report.application_id`)가 가리킬 수 있어 지우지 않는다. 옮긴 뒤 남는 쪽이 멤버인 그룹의 `PENDING`도 `CANCELED`다. 닫을 때는 답하기와 같이 `answered_at`을 채운다. 나머지는 옮긴다 |
| 멤버 공부 알림 기록(`group_study_alert`) | 같은 그룹 기록이 남는 쪽에 있으면 옮기는 쪽을 지우고, 나머지는 옮긴다 |
| 그룹 신고(`user_report`) | 신고한 쪽·받은 쪽을 옮기고, 두 계정 사이의 신고(합치면 자기 자신 신고)는 지운다 |
| 차단(`user_block`) | 건 차단·받은 차단을 모두 옮기고, 두 계정 사이의 차단(자기 자신 차단)과 남는 쪽에 이미 있는 쌍은 버린다(남는 쪽 행의 차단 시각이 남는다) |
| `amplitude_*` | 건드리지 않는다(사용자 결정) |

세션 겹침: 두 세션 s, t는 시작 시각이 같거나(`UNIQUE(user_id, started_at)`) `s.start < t.end AND t.start < s.end`이면 충돌이다.
유효 종료는 `GREATEST(start, COALESCE(ended_at, start + study_sec))`라서 `ended_at`이 NULL인 옛 세션도 500 없이 처리된다. 끝과 시작이
맞닿은 경계는 겹침이 아니라 옮긴다. 옮기는 쪽의 완료 세션이 남는 쪽의 진행 중 세션(draft, 끝 = `GREATEST(started_at, last_seen_at)`)과
겹쳐도 폐기한다 — 남는 쪽이 다른 기기에서 공부 중이면 확정 뒤 같은 시간이 두 번 세진다. 옮기는 쪽 draft가 남는 쪽 세션이나 draft와 겹치면 폐기한다.
`AccountData.merge`는 옮기는 쪽과 남는 쪽이 같으면 거부한다.

### 빠뜨림 방지

- 병합·탈퇴는 테이블마다 `UserDataHandler`(`user/account/`) 구현체가 맡고, 도메인 패키지가 자기 테이블의 처리기를 둔다. 순서는 상수로
  정한다: 세션 100, 과목 200, 그룹 250, 차단 260, 방 300, 랭킹 400, RTC 450, 디데이·유입·푸시 500, user 패키지 900(users 행 자체).
  그룹이 방보다 먼저라, 탈퇴에서 그룹 공부방 자리를 정리(`MEMBER_LEFT`)한 뒤 방 처리기가 참가 행을 지운다.
- `UserDataCoverageTest`가 DB에서 users를 참조하는 컬럼을 읽어, 처리기에 등록되지 않은 컬럼이 있으면 실패시킨다. FK 없이 `user_id`를
  가진 테이블은 처리기에 직접 적고 같은 테스트가 이름으로 확인한다. 그룹 테이블이 더해지면 이 테스트가 실패해 병합·탈퇴 규칙을 같이 넣게 한다.
- `amplitude_*`는 의도적으로 제외 목록에 둔다.

### 동시성

- link는 ID 토큰 검증(외부 HTTP)을 트랜잭션 밖에서 하고, 소셜 사용자를 잠금 없이 조회한 뒤 두 유저 행을 ID 작은 쪽부터 잠근다(ADR-0019의
  `findByIdForUpdate`). 전용 `REQUIRES_NEW` 트랜잭션에서 돌고, 같은 소셜 ID를 동시에 전환하다 unique 인덱스에서 지면 한 번 재시도한다.
- **그룹 행을 users 행보다 먼저 잡는다**(BY-1126 그룹 단계). 그룹 쪽(BY-1124)은 그룹 행을 `FOR UPDATE`로 잡은 뒤 멤버·신청 행을 넣고, 그
  FK가 users 행에 `FOR KEY SHARE`를 건다. 병합·탈퇴가 users 행을 먼저 `FOR UPDATE`로 잡으면 순서가 거꾸로라 교착할 수 있어,
  `UserDataHandler.lockBeforeUsers`(기본은 아무것도 안 함)를 두고 `AccountData.lockBeforeUsers`가 처리기 순서대로 부른다. 탈퇴는
  `AccountEraser`가 users 행을 잠그기 전에, 병합은 `AccountLinker.merge`가 두 users 행을 잠그기 전에 옮기는 쪽으로 부른다(전환은
  userId가 그대로라 부르지 않는다). 그룹 처리기는 그 사람이 살아 있는 멤버이거나 그룹장이거나 `PENDING` 신청을 낸 살아 있는 그룹을 한 문장에서
  ID 순으로 `FOR NO KEY UPDATE`로 잡는다(사용자별 부분 인덱스 세 개의 UNION으로 찾는다). `FOR UPDATE`가 아닌 이유: 그룹 쪽 ①(`lockLive`의
  `FOR UPDATE`, `shareLive`의 `FOR SHARE`)과는 그대로 막히지만, ①을 잡지 않고 users 행 다음에 그룹 행을 FK로 확인하는 신고(`user_block` →
  `user_report`)·멤버 공부 알림 기록 넣기(`FOR KEY SHARE`)는 막지 않는다 — `FOR UPDATE`면 그 트랜잭션이 users 행 FK 잠금을 쥔 채 그룹 행을
  기다리고 탈퇴는 그 users 행을 기다려 교착한다(리뷰에서 재현, 2026-11-04 수정). 탈퇴·병합이 그룹 행에 쓰는 변경(그룹장·삭제 표시·코드)은
  FK가 가리키는 키를 바꾸지 않아 그 FK 검사와도 부딪히지 않는다. 잡는 그룹과 모드는 `GroupAccountLockTest`가 고정한다.
  대상을 고르는 읽기는 잠그지 않아, 그 문장과 users 행 잠금 사이에 새로 들어간 그룹은 잡히지 않는다 — 병합 SQL은 그룹 목록이
  아니라 조건으로 행을 고르므로 그 그룹의 행도 처리하고, 탈퇴는 그룹마다 같은 모드로 다시 잠그며 읽는다(그때는 순서가 거꾸로라 드물게 교착할 수
  있고, 그러면 DB가 한쪽을 실패시킨다. 다시 시도하지 않는다). user 패키지는 그룹·차단 패키지를 모른다(확장점 방향 유지).
- **받아들인 위험 — 병합의 남는 쪽 경쟁**: 병합은 옮기는 쪽이 얽힌 그룹만 먼저 잡는다. 남는 쪽 users 행을 `FOR UPDATE`로 쥔 채 옮기는
  동안, 남는 쪽 users 행을 기다리는 다른 트랜잭션이 같은 `(남는 쪽, x)` 쌍의 unique 항목을 먼저 넣어 두었으면(멤버 공부 알림의 `claim`이
  `(남는 쪽, 그룹)` 기록을 넣는 중이거나, 남는 쪽이 같은 사람을 동시에 차단하는 중) 병합이 그 항목을 기다려 교착하고, DB가 한쪽을 실패시킨다.
  그 사이 상대가 먼저 커밋하면 병합 쪽이 기본 키 위반으로 실패한다. 둘 다 병합하는 그 순간에 스케줄러나 차단이 같은 쌍을 건드려야 해서 매우
  드물고, 실패한 쪽은 다시 시도하면 된다. 코드로 막지 않는다.
- 방에서 나가는 처리는 병합 경로가 실제로 돌 때만 한다(전환 경쟁 재시도 직전 포함). 전환은 방을 유지한다.
- 기기 등록(`POST /api/users`)은 유저 행 잠금 아래에서 그 행이 아직 `(DEVICE, deviceId)`인지 다시 확인한 뒤 토큰을 발급한다. 아니면 새
  비회원을 만든다. 등록과 전환이 겹쳐도 deviceId만으로 소셜 계정의 토큰이 나가지 않는다.
- 클래스는 `AuthService`에서 `TokenIssuer`(발급·회전)와 `AccountLinker`(전환·병합)를 분리했다. checkstyle의 파라미터 7개 제한 때문이기도 하다.

### 탈퇴

- `DELETE /api/users/me`는 즉시 하드 삭제다. 모든 기기 로그아웃, 비회원도 가능, 멱등(이미 없으면 204), 같은 소셜 ID로 다시 로그인하면 새 가입.
- 순서: 그룹 행 잠금(ID 순) → 유저 행 잠금 → 처리기 순서대로 그룹 처리·데이터 삭제 → users 행 삭제 → 커밋 → (커밋 뒤) 프로필 사진 파일
  삭제, 애플 해지, 그룹 푸시·공부방 메시지.
- 이 사람이 만든 `rooms`는 다른 사람 기록이 걸려 있어 지우지 않고 `created_by`를 NULL로 둔다. V41이 NULL을 허용한다.
- **그룹장 자동 승계**(사용자 결정): 그룹장이 탈퇴하면 그 그룹에서 가장 먼저 들어온 다른 살아 있는 멤버(들어온 시각, 같으면 멤버 행 ID 순)가
  그룹장이 되고 탈퇴한 사람은 그룹에서 빠진다. 새 그룹장에게 `group_owner_transferred` 푸시, 공부방이 열려 있으면 `OWNER_CHANGED` —
  그룹장 넘기기 API와 같은 처리(`GroupOwnership.handOver`)다. 새 그룹장의 "그룹장 2개" 한도는 보지 않는다(넘기기와 같다). 다른 멤버가 없으면
  나가기의 그룹 지우기를 탄다(`GroupOwnership.closeAbandoned`: 그룹 지우기, 기한 안의 `PENDING` 신청을 `GROUP_DELETED`로 닫고
  `group_application_room_closed` 푸시). 그룹장이 아닌 그룹은 공부방 자리가 남아 있으면 지운다(`MEMBER_LEFT`, 보통은 탈퇴 전 방 나가기가
  이미 했다).
- 그 뒤 그 사람의 그룹 행을 지운다: 멤버 행(나간 이력 포함)·신청·멤버 공부 알림 기록·신고(신고한 쪽·받은 쪽)·차단(양쪽). 그 사람의 신청을
  가리키는 `user_report.application_id`는 먼저 NULL로 둔다. 지운 그룹은 신고·공부방이 가리켜 행을 남기고, 그 사람이 그룹장이던 지운 그룹은
  `owner_id`를 NULL로 둔다 — **V43**이 `owner_id`의 NOT NULL을 풀고 `CHECK (deleted_at IS NOT NULL OR owner_id IS NOT NULL)`로 살아 있는
  그룹에는 그룹장을 강제한다. 그런 행의 `GroupRow.ownerId`는 0이고, 지운 그룹을 읽는 곳은 만료 푸시의 그룹 이름뿐이다.
- 그래서 `OWNER_CHANGED`와 `group_owner_transferred`는 그룹장 넘기기 API 말고도 그룹장 탈퇴 때 나가고, `OWNER_CHANGED`는 병합으로
  그룹장이 남는 쪽으로 바뀔 때도 나간다(메시지 모양은 그대로, `websocket.html` 변경 이력).
- **애플 해지**: 앱이 탈퇴 직전에 애플 로그인을 다시 띄워 받은 `authorizationCode`와 `appleClient`(IOS/ANDROID)를 넘기면 서버가 토큰으로
  바꿔 해지한다. 로그인 때 애플 토큰을 저장하는 방법보다 저장할 비밀이 없다. 코드를 보내면 `appleClient`도 필수다 — 코드를 만든
  클라이언트로만 바꿀 수 있어 짐작하지 않고, 없으면 지우기 전에 400 `VALIDATION_FAILED`다(정의되지 않은 값은 본문을 못 읽어 400
  `BAD_REQUEST`). 코드가 없거나 해지가 실패해도 탈퇴는 진행한다(해지 실패로 탈퇴를 못 하는 편이 더 나쁘다). 그 경우는 모두 로그와 함께
  `Sentry.captureMessage`로 직접 남긴다 — `sentry-logback`이 없어 로그만으로는 Sentry에 가지 않는다(코드베이스 관례, 예:
  `HttpAmplitudeExportSource`). 고정 문구·앱 종류·예외 클래스·HTTP 상태만 싣고 코드·client secret·애플 토큰은 싣지 않는다. 해지용
  비밀값(Team ID·Key ID·개인 키)이 없으면 기동은 되고 해지만 건너뛰며, 그것도 Sentry 경고로 남긴다.
- **카카오**는 앱이 SDK의 연결 끊기를 먼저 부른 뒤 탈퇴 API를 부른다. 서버는 하지 않는다(어드민 키가 더 필요해진다).

### 안드로이드 애플 콜백

안드로이드에서도 애플 로그인을 보여 주기 위해 웹 로그인(Services ID)을 쓴다. 이메일을 받으려면 애플이 결과를 `form_post`로 보내므로,
이를 받아 앱 딥링크로 넘기는 `POST /api/auth/apple/callback`을 인증 없이(`permitAll`) 둔다. 인증을 걸 수 없는 이유는 호출자가 앱이
아니라 애플이고 비회원 토큰이 없기 때문이다. 이 경로는 받은 값을 설정값으로 정해 둔 딥링크에 붙여 303으로 넘기기만 하고 토큰 검증이나
로그인 처리는 하지 않는다. 넘길 주소는 요청에서 받지 않으며(열린 리다이렉트 방지) 설정값이 없으면 404고, 본문은 로그에 남기지 않는다.
`permitAll`에 더한 것은 이 경로 하나뿐이다(2026-11-03 사용자 승인).

### 하지 않는 것

- **서버에서 비회원의 그룹 API 호출을 막지 않는다.** 로그인 버전 출시 때 강제 업데이트로 옛 앱을 없애고, 새 앱이 그룹 탭 진입에서
  로그인을 요구하는 것으로 충분하다. 서버 차단은 앱보다 서버가 먼저 배포되는 시점 문제까지 다뤄야 해 얻는 것보다 비싸다.
- 세션 겹침 DB 제약(exclusion constraint)은 걸지 않는다. 운영에 이미 겹친 기록이 있으면 배포가 깨지고, 필요한 건 병합 때 겹침을 거르는 것뿐이다.
- 여러 프로바이더를 한 계정에 연결하거나 계정을 통합하지 않는다(8월 명세의 알려진 한계). 탈퇴 재인증(step-up), 레이트 리밋도 파킹한 그대로다.

### 옛 앱 무인증 경로

구 앱 경로(ADR-0020, `LegacyApiRequestMatcher`의 14개)와 STOMP `?userId=` 폴백은 토큰 없이 숫자 userId만으로 사용자를 고른다. 소셜
계정이 생기면 숫자만 알면 그 계정의 기록을 읽고 쓸 수 있게 되므로, **비회원(DEVICE)이 아닌 userId는 없는 사용자와 똑같이 404
`USER_NOT_FOUND`로 거부한다**(STOMP는 CONNECT 거부, 2026-11-03 사용자 결정 "소셜 userId는 거부"). 구 앱 사용자는 늘 비회원이라 정상
호출은 그대로다. 세션 상세처럼 리소스 ID를 받는 경로도 조회 조건이 (id, userId)라 같은 확인으로 막힌다. 확인은
`LegacyGuestGuard` 하나로 모아 모든 Legacy* 컨트롤러와 STOMP 폴백이 부른다. 이 경로 자체는 로그인 출시의 강제 업데이트 뒤 ADR-0020
절차(호출 0 확인 → contract)로 후속 티켓에서 걷는다.

## 결과

- 병합·탈퇴 뒤 최대 30분 동안 옛 access 토큰이 남는다(로그아웃 뒤도 같다, 상태 없는 JWT). 앱이 바로 토큰을 바꾸므로 받아들인다. 그 토큰의
  쓰기가 지워진 users 행을 가리키는 FK 위반(SQLState 23503, `is not present in table "users"`)은 `GlobalExceptionHandler`가 404
  `USER_NOT_FOUND`로 낸다. 다른 무결성 위반은 지금처럼 500이다. FK가 없는 `rtc_connection_stat`는 쓰기 전에 사용자를 확인해 404로 끊는다.
  진행 중 스냅샷(`PUT /api/study-sessions/active`)은 버퍼를 거쳐 204가 나가고, flush에서 그 행만 FK 위반으로 버려진다(Sentry에 남는다).
- 병합·탈퇴 때 열려 있던 STOMP 구독은 끊지 않는다(ADR-0019의 알려진 후속 과제).
- 방 나가기 미리 보기(`mergeAhead`)는 잠그지 않고 읽는다. 미리 보기와 실제가 엇갈려 방에 남은 채 병합되면 병합 처리기가 참가를 닫는다.
- 안드로이드 애플 콜백의 딥링크는 운영에서 검증된 HTTPS App Link로 둬야 다른 앱이 가로채지 못한다(운영·FE 확인 목록).
- 탈퇴한 사람의 지난 랭킹 기록이 빠져 지난 순위판에 빈 순위가 생길 수 있다("즉시 전부 삭제" 정책).
- 합친 결과가 그룹 개수 제한을 넘어도 그대로 둔다. 제한은 새로 하는 행동에만 건다.
- 새 users 참조 테이블을 더하는 PR은 `UserDataCoverageTest`가 실패해 처리기를 함께 넣는다. 그룹 테이블(BY-1124)은 dev를 받은 뒤 이 브랜치가
  이어 붙였다(그룹 처리기 250, 차단 처리기 260). 이 테스트는 FK와 `user_id`·`*_user_id` 이름만 본다 — 그룹의 `owner_id`·`receiver_id`·
  `reporter_id`·`blocker_id`·`blocked_id`는 모두 users FK가 있어 잡힌다. FK 없이 다른 이름으로 users를 가리키는 컬럼은 여전히 놓친다.
- 운영 전 확인: 로그인 앱 출시 전에 운영 SSM·태스크 정의에 `OAUTH_*` 환경변수(목록형 이름 `OAUTH_GOOGLE_CLIENT_IDS` 등이 없으면 바뀌기 전 이름 `OAUTH_GOOGLE_CLIENT_ID`·`OAUTH_KAKAO_APP_KEY`·`OAUTH_APPLE_CLIENT_ID`를 읽어, 이미 넣어 둔 값을 그대로 쓴다. 더 넣을 것은 애플 Services ID부터), 애플 해지용 비밀값, Services ID의
  반환 주소 등록, 개인정보처리방침의 소셜 로그인·이메일 수집 문구. 위키의 "계정 삭제는 이메일 요청" 문구는 인앱 탈퇴로 바꾼다. 값이 비어
  있으면 기동은 되지만 그 프로바이더 로그인이 전부 400이라(그룹 탭이 로그인을 요구하므로 그룹 탭이 통째로 막힌다), `OAuthConfigCheck`가
  기동이 끝난 뒤 빈 항목의 환경변수 이름을 로그와 Sentry 경고로 한 번 남긴다(값은 싣지 않는다). 그룹 릴리즈 때 아직 값을 넣지 않았으면
  배포마다 같은 경고가 하나씩 쌓인다.
- 번호: ADR 0040·마이그레이션 V36~V39는 그룹(BY-1124), V40은 구글 광고 유입(BY-1138), ADR 0041·V50·V51은 사용자 시간대(BY-1133)가 쓰고 있어 ADR 0042, 마이그레이션 V41(`rooms.created_by` NULL 허용)·
  V42(`used_social_id_token`)·V43(`study_group.owner_id` NULL 허용)을 쓴다(2026-11-04). dev에 번호가 더 생기면 머지 직전에 다시 맞춘다.
