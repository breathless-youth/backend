# ADR-0051: 프리미엄 사전 신청은 사용자당 한 행으로 저장하고 이메일은 평문으로 두며 파기는 런북으로 한다

- 상태: 승인
- 날짜: 2026-11-24
- 티켓: BY-1394 (상위 BY-1392)
- 관련: ADR-0043, ADR-0050

## 맥락

프리미엄 구독을 만들기 전에 사람들이 얼마에 신청하는지 보는 페이크도어 실험을 한다(2,900원과 5,900원, 결과 화면과 홈). 프론트가 신청 완료 때 한 번, 기대 기능을 고를 때 같은 본문으로 한 번 더 부른다. 신청 수는 서버에서 세고, 비용 근거는 `rtc_connection_stat`에서 뽑는다.

## 결정

1. `PUT /api/premium-waitlist/me`(API-Version 2, 인증 필수, 204)가 `premium_waitlist`에 사용자당 한 행을 `INSERT ... ON CONFLICT (user_id) DO UPDATE` 한 문장으로 저장한다. 같은 사용자의 두 호출이 겹쳐도 unique(user_id)가 직렬화한다.
2. 두 번째 호출의 `expectedFeature`가 null이면 기존 값을 지우지 않고 유지한다. 한 번 고른 기능을 다시 null로 되돌리는 화면이 없고, 재시도나 순서가 뒤바뀐 요청이 선택을 지우는 쪽이 더 나쁘다. 가격·위치·나이·이메일은 마지막 호출 값으로 덮어쓴다.
3. 이메일은 만 14세 이상이고 직접 입력한 사람만 저장한다. 14세 미만은 본문에 이메일이 와도 저장하지 않고 `email`, `consented_at`을 null로 둔다. `consented_at`은 이메일을 저장한 시각이고, 같은 이메일로 다시 저장하면 바꾸지 않는다.
4. 이메일은 평문으로 저장한다. `users.email`이 이미 평문이고, 출시 알림을 보내려면 원문이 필요하다. 해시나 암호화는 발송 때 어차피 풀어야 해서 보호 효과가 없고 키 관리만 늘린다. 대신 쓰는 곳을 줄인다. Amplitude·GA4·Sentry·Meta로 이메일을 보내지 않고, 로그에 본문을 남기지 않는다.
5. `users`를 참조(FK)하고 `UserDataHandler`를 구현한다. 탈퇴는 행을 지우고, 병합은 target에 행이 없을 때만 옮기고 아니면 source 행을 지운다(target이 이긴다). 탈퇴한 사용자의 옛 토큰이 오면 FK 위반(500) 대신 404가 되도록 저장 전에 사용자를 확인한다.
6. 파기는 스케줄러 없이 사람이 런북 SQL로 한다(`docs/runbooks/premium-waitlist.md`). 시점은 출시 알림을 보낸 직후, 늦어도 2027-05-31(실험 종료 후 6개월)이다. 행은 지우지 않고 `email`만 null로 만든다. 가격별·위치별 신청 수 같은 집계가 행에 있기 때문이다.
7. 집계는 `docs/analytics/premium_waitlist.sql`에 둔다. TURN 원가 근거는 연결별 첫·마지막 샘플 시각 차를 가중치로 쓴 시간 가중 relay 비율과 relay 바이트 합이다.

## 갱신 (2026-11-25)

- 웹이 이메일·동의 단계를 빼고 "사전 신청하기" 한 번으로 신청을 받는다. 그래서 만 14세 이상도 이메일 없이 저장한다(결정 3의 "이메일 필수"를 바꿈).
- 이메일 없이 온 요청은 먼저 받은 `email`, `consented_at`을 지우지 않는다. 14세 미만으로 오면 지운다.
- 웹은 버튼 위 안내로 만 14세 이상과 개인정보 이용 동의를 갈음한다. 새 신청의 `age_over14=true`는 따로 체크한 값이 아니고, `consented_at`은 이메일을 저장한 시각이라 새 신청에서는 null이다.
- 실험 종료는 2026-12-03 23:59:59 KST로 늘었고, 먼저 받은 이메일의 파기 기한은 실험 종료 뒤 6개월인 2027-06-03이다.

## 실험 종료 후

- 웹이 카드를 내리면(2026-11-30 23:59:59 KST 이후) 이 API는 호출되지 않는다. 엔드포인트는 파기와 집계를 마칠 때까지 둔다.
- 집계를 마치고 이메일을 파기한 뒤에도 정식 프리미엄 출시 결정 전까지 테이블은 둔다. 더 쓰지 않기로 하면 컨트롤러·서비스·처리기를 지우는 변경과 함께 `DROP TABLE premium_waitlist` 마이그레이션을 새로 만든다.

## 결과

- 이메일이 DB에 평문으로 남는 기간은 최대 2027-05-31까지다. 파기는 사람이 잊으면 안 되므로 출시 알림 발송 체크리스트에 런북 링크를 넣는다.
- 스케줄러를 만들지 않아 코드는 줄지만, 파기가 자동이 아니다.
- 기대 기능을 null로 되돌릴 수 없다. 필요해지면 별도 계약이 필요하다.
