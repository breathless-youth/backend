# ADR-0035: 서버가 기기 토큰을 저장해 FCM으로 직접 보내고, 토큰은 UNREGISTERED일 때만 지운다

- 상태: 승인
- 날짜: 2026-10-27
- 티켓: BY-1029 (상위 BY-1028, 짝 FE BY-1030)
- 설계: `docs/superpowers/specs/2026-10-27-by1029-push-token-infra-design.md`
- 관련: ADR-0010(콘솔 캠페인 발송, frontend), ADR-0015(API 버전), ADR-0019(게스트 기기 토큰 인증)

## 맥락

지금은 Firebase 콘솔에서 GA 오디언스를 골라 캠페인으로만 알림을 보낸다(ADR-0010). 앱은 FCM 토큰을 받지만 서버로 보내지 않는다.
오늘 공부 안 함, D-Day, 플래너 결과처럼 사람마다 대상과 문구가 다른 알림은 서버 데이터로 판단해야 해서 콘솔로는 보낼 수 없다.
ADR-0010이 "1:1 알림이 필요해지면 서버 저장 + Admin SDK"로 미뤄 둔 시점이 왔다. 이번 결정은 발송 기반까지이고, 시나리오는 따로 붙인다.

## 결정

1. **토큰은 V1의 `push_token`에 저장하고 사용자당 개수를 제한하지 않는다.** 소셜 로그인이 들어오면 한 계정이 여러 기기를 쓴다.
   등록(`PUT /api/push-tokens`)은 `ON CONFLICT (token)` 업서트 한 문장이다. 같은 토큰이면 갱신 시각만 바뀌고, 다른 사용자에게 붙어
   있던 토큰이면 지금 사용자로 옮긴다. 엔티티 저장은 값이 같으면 UPDATE를 건너뛰어 `updated_at`(마지막 사용 시각)이 멈춘다.
2. **등록 때 OS 알림 권한 상태(`notifications_enabled`, V32)를 같이 받는다.** 서버는 iOS 기기 도착을 알 수 없어서, 클릭률의 분모를
   "권한이 켜진 기기로 보낸 수"로 근사한다.
3. **발송은 firebase-admin `sendEachForMulticast`로 500개씩 한다.** 서버 키 방식은 2024년에 종료돼 서비스 계정 OAuth만 된다.
   인증 갱신과 오류 코드 해석을 손으로 짜는 것보다 공식 SDK가 안전하다. Firestore·Storage가 딸려 오지만 빼면 `FirebaseOptions`의
   기본 JSON 처리기까지 빠져 초기화가 깨져서 통째로 받는다.
4. **토큰은 `UNREGISTERED`일 때만 지운다.** `INVALID_ARGUMENT`·`SENDER_ID_MISMATCH`·`THIRD_PARTY_AUTH_ERROR`는 메시지 형식이나
   잘못 넣은 키 같은 우리 쪽 문제로도 모든 토큰에서 나온다. 지우면 멀쩡한 토큰이 통째로 사라지고, 사용자가 앱을 다시 열 때까지 보낼 방법이
   없다. 그 밖의 실패는 발송 한 번에 Sentry 이벤트 하나(오류 코드별 개수)로 알린다.
   알림 권한이 꺼진 기기(`notifications_enabled = false`)에도 보낸다. 그 값은 마지막 앱 실행 때 것이라 설정에서 다시 켠 기기를
   놓치고, 보내도 OS가 표시하지 않을 뿐이며, 걸러 내면 그 기기의 죽은 토큰이 `UNREGISTERED`로 지워질 기회도 사라진다.
5. **오래된 토큰을 주기적으로 지우는 정리 잡은 두지 않는다.** 앱을 지운 기기의 토큰은 발송 때 `UNREGISTERED`로 지워진다. 오래 앱을 안 연
   사용자에게 복귀 알림을 보낼 수 있어야 하고, 앱 재등록 버그가 조용한 토큰 손실로 번지지 않게 하려는 것이다. 최근 활동 기기만 셀 때는
   `updated_at`을 조회 조건으로 쓴다.
6. **알림 데이터 계약은 `link`(스킴 없는 경로)와 `type`(알림 종류)이다.** `type`은 `fcm_options.analytics_label`에도 실어 콘솔
   보고 탭에서 종류별 발송·열림 수를 본다. 발송 기록 테이블과 `push_id`는 첫 시나리오에서 더한다. 앱은 BY-1030에서 열림 이벤트에
   `push_id`·`route`·`fallback`을 실을 준비를 먼저 한다 — 앱 바이너리가 퍼지는 데 시간이 걸려서다.
7. **자격증명이 없으면 발송만 끈 채 기동하고, 읽은 키의 `project_id`를 로그에 남긴다.** 토큰은 발급한 Firebase 프로젝트(dev·prod)의
   키로만 보낼 수 있어, 키를 바꿔 넣는 실수를 기동 로그 한 줄로 알아보게 한다.
8. **테스트 발송(`POST /api/push-tokens/test`)은 `app.push.test-send.enabled`로 dev에서만 켠다.** `@Profile`은 쓰지 않는다(BY-640).

## 결과

- 시나리오는 대상 쿼리와 문구를 정해 `PushSender.send(userIds, message)`만 부르면 된다. FCM 인증·토큰 조회·무효 토큰 삭제는 `push` 패키지 안에 있다.
- 서버에는 보낸 내용이 남지 않는다. 결과 개수만 INFO 로그 한 줄(`푸시 발송 type=… sent=… failed=… removed=…`)로 남는다. 상한·중복
  방지·효과 측정이 필요해지는 첫 시나리오에서 발송 기록과 비교군을 더한다.
- `push_token.user_id` FK에 삭제 연쇄가 없어, 탈퇴 기능이 생기면 토큰을 먼저 지워야 한다. 로그아웃 때 그 기기의 토큰 삭제도 소셜 로그인
  작업에서 한다.
- iOS 기기 도착 수와 사용자 단위 Android 도착은 보지 않는다(NSE·BigQuery 미도입).
