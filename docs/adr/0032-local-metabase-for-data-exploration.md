# ADR-0032: 운영 데이터 탐색은 각자 맥의 Metabase로 하고, 저장소는 운영 RDS에 두고 같이 쓴다

- 상태: 승인
- 날짜: 2026-10-24
- 티켓: BY-981
- 관련: ADR-0012(BI 보류 — 결정 1 개정), ADR-0030(Amplitude 적재), ADR-0031(수동 기록 source)
- 사용법: infra 저장소 `metabase/README.md`, 탐색 SQL 원본: `docs/analytics/`

## 맥락

10/22부터 리텐션이 낮고 서비스 방향이 정해지지 않은 문제를 데이터로 찾는 탐색을 시작했다. 이틀 동안 서로 다른 SQL 11개를
db-shell의 psql에 붙여 넣고 결과 텍스트를 다시 옮기는 식으로 봤다. 차트도, 저장도, 팀 공유도 없었다.

ADR-0012는 BI 도구를 미뤘다. 개발자 3명이 가끔 보는데 상시 컨테이너(월 $30 안팎)·RDS 보안그룹·별도 인증을 두는 건 과하고,
지표 정의가 테스트 없는 BI 안에만 있으면 앱과 조용히 어긋난다는 이유였다. 그리고 "시각화가 실제로 아쉬워지면 재검토"를 남겼다.
지금이 그 경우다. 팀 조건은 셋이다. 추가 비용이 없어야 하고, 팀원도 같이 봐야 하며, 팀원은 운영 AWS 계정에 SSO로 들어올 수 있다.

## 결정

1. **Metabase OSS를 각자 맥의 Docker에서 띄운다.** `127.0.0.1`에만 열고 외부 주소나 서버는 두지 않는다.
2. **운영 DB에는 SSM 포트 포워딩으로 붙고, 통로는 이미 떠 있는 운영 API 태스크의 ECS Exec이다.** 새 리소스, IAM, 보안그룹 변경이
   없어 비용이 0이다. db-shell처럼 태스크를 새로 띄우면 쓰는 시간만큼 비용이 생긴다.
3. **질문·대시보드·계정은 운영 RDS의 별도 DB `metabase`(계정 `metabase_app`)에 둔다.** 모든 인스턴스가 같은 저장소, 같은 버전,
   같은 암호화 키(SSM)를 쓰므로 누가 만든 질문이든 모두가 본다.
4. **Metabase는 읽기 전용 계정 `analytics_ro`로만 운영 데이터를 읽는다.** `default_transaction_read_only = on`에 권한도 SELECT뿐이라
   읽기 전용을 풀어도 테이블에 쓰지 못한다. 쿼리는 30초에 끊는다. 마이그레이션이 만드는 새 테이블도 기본 권한으로 읽힌다. 앱 계정과
   권한은 그대로다. 이 계정은 **실수와 부하를 막는 장치**다. 터널을 열 수 있는 SSO 권한이면 원래 ECS Exec으로 API 컨테이너에도
   들어갈 수 있어서, 악의적인 내부 사용자를 막는 경계로 보지 않는다. 소유자 권한으로 도는 `SECURITY DEFINER` 함수는 지금 없다.
   생기면 그 마이그레이션에서 PUBLIC의 EXECUTE를 회수한다(`setup.sql`이 개수를 출력한다).
5. **연결 상한은 역할별로 둔다**(`metabase_app` 30, `analytics_ro` 10). 넘쳐도 Metabase만 막히고 앱 연결은 남는다. 앱은 태스크당
   기본 풀 10이고, 롤링 배포 중에는 태스크가 2개라 20이다. 그래서 `max_connections`는 65(40 + 20 + 여유 5)보다 커야 한다.
   Metabase 하나가 저장소 연결을 약 9개(스케줄러 포함, 로컬 실측) 쓰므로 동시에 쓸 수 있는 건 3명 정도다.
6. **비밀번호는 평문이 서버로 가지 않게 SCRAM 검증값으로만 넘긴다**(`setup-db.sh`). 비밀 3개는 SSM에 두고 Terraform은 자리만
   만든다(기존 `app_secrets` 방식).
7. **ADR-0012 결정 1을 고친다.** 공식 지표(일일 리포트)의 정의는 계속 백엔드 코드와 테스트에 두고, Metabase는 탐색용이다. 탐색 SQL은
   `docs/analytics/`에 원본을 두고 공통 정의(측정만, 1분·10분 기준, 관리자 제외 등)를 README에 적는다. 탐색에서 굳어진 지표는 코드로
   옮긴다.
8. **`users`는 전체를 읽게 둔다.** 지금은 전원 DEVICE 가입이라 이메일이 비어 있다. 소셜 로그인을 다시 열면 `analytics_ro`의 `users`
   권한을 열 단위로 줄인다.

## 검토한 대안

- **직접 만든 어드민 페이지**: 기각. 차트 하나마다 API, 화면, 배포가 필요하고 관리자 역할부터 만들어야 한다. 지금 인증은 `ROLE_USER`
  하나뿐이고, 2026-08-09 리포트 설계도 이 때문에 관리자 API를 열지 않았다. 질문이 매일 바뀌는 탐색에 맞지 않는다. 저장한 SQL을
  실행하는 작은 콘솔(3~4일)도 검토했지만, 인터넷에 열린 API에 SQL 실행 창구가 생긴다.
- **AWS 상시 서버**(Fargate + 기존 ALB 규칙): 보류. 월 $15~20이 들고 외부 주소와 인증이 필요하다. 맥에 의존하는 게 불편해지면
  옮긴다. 저장소를 그대로 쓰므로 질문은 유지된다.
- **Cloudflare 터널로 한 사람의 맥을 공유**: 기각. 비용은 0이지만 그 사람 맥이 켜져 있어야 팀이 본다.
- **저장소를 각자 맥에**(H2나 로컬 Postgres): 기각. 대시보드가 사람마다 따로 생긴다.
- **Oracle 무료 서버**(coturn): 기각. 운영 DB를 그쪽에서 접근하게 열어야 하고, 통화 중계와 CPU를 나눠 쓴다.
- **Amplitude 화면만**: 기각. 공부 기록(`study_session`)이 없어 공부 시간과 합쳐 볼 수 없다.

## 결과

- 추가 비용 없이 팀원 누구나 `./metabase/metabase.sh` 하나로 운영 데이터를 SQL과 차트로 보고, 저장한 질문을 같이 쓴다.
- 운영 RDS(db.t4g.micro)에 분석 쿼리 부하가 생긴다. 30초 제한과 연결 상한으로 묶고, 쓰는 동안 CloudWatch의 RDS CPU를 본다. 부담이
  보이면 읽기 복제본이나 사양 상향을 검토한다.
- 운영 API 태스크가 통로라 배포 때 터널이 잠깐 끊긴다. 스크립트가 새 태스크로 다시 붙는다.
- Metabase 버전은 모두 같이 올린다(저장소 백업 후). 암호화 키를 바꾸면 저장된 DB 연결을 다시 넣어야 한다.
- 탐색 SQL은 테스트가 없다. 앱의 정의(스트릭 10분 등)를 바꾸는 PR은 `docs/analytics/README.md`도 같이 고친다.
