# ADR-0012: 헤비유저 정의와 일일 지표 집계를 백엔드 도메인 코드에 둔다

- 상태: 승인
- 날짜: 2026-08-09

## 맥락

서비스의 헤비유저·가입 추이를 정기적으로 확인할 방법이 없어, 매일 오전 10시(KST) Slack으로
지표 4개(총 가입 수, 어제 신규 가입, 헤비유저, 어제 10분 이상 세션 수)를 자동 발송하는
기능을 추가했다. 이 기능을 설계하며 두 가지를 결정해야 했다 — 지표 정의를 어디에 둘지,
그리고 "헤비유저"를 무엇으로 정의할지.

### 지표 정의를 BI 도구가 아닌 백엔드에 두는 이유

처음에는 Redash 같은 BI 도구로 대시보드를 만드는 방향을 검토했다. 그러나 실제 사용자는
개발자 3명이고 확인 빈도는 "가끔"이다. 이 규모에 상시 컨테이너(월 $30 내외) + RDS 접근
보안그룹 + 별도 인증 관리를 유지하는 것은 비용 대비 효용이 낮다.

더 결정적인 이유는 **지표 정의 자체가 도메인 규칙이라는 점**이다. 헤비유저 기준은
ADR-0009가 정한 스트릭 인정 기준(`focusSec >= 600`)의 재사용이다. 이 판정 SQL이 BI 도구
안에만 존재하면, ADR-0009가 바뀌어도 BI 쿼리는 아무 테스트도 걸리지 않은 채 조용히
어긋난다. 백엔드 안에 두면 기존 스트릭 로직과 같은 상수(`StudySessionThresholds`)를
공유하고, 어긋나는 순간 테스트가 실패한다.

## 결정

### 1. 지표 정의는 백엔드 도메인 코드 안에, 별도 BI 인프라는 두지 않는다

지표 산출 로직(헤비유저 판정, 임계값)은 `project.study.studysession`·`project.study.metrics`
패키지의 서비스·상수로만 존재한다. 매일 Slack 발송으로 "가끔 확인"의 대부분을 대체하고,
시각화가 실제로 아쉬워지면 그때 웹 대시보드를 검토한다.

### 2. 헤비유저 = 기준일 포함 최근 7일 중 스트릭 인정일 3일 이상

**헤비유저 = 기준일(anchorDate)을 포함한 최근 7일 중, ADR-0009의 스트릭 인정 기준을
만족한 날이 3일 이상인 유저.**

스트릭 인정 기준은 ADR-0009를 그대로 재사용한다 — "그 날짜의 세션 중 **하나라도**
`focusSec`이 10분(600초) 이상이면 그 날은 스트릭에 잡힌 날로 인정한다. 하루 합계가
아니라 세션 단위 기준이다." 새 기준을 만들지 않고 기존 것을 재사용하는 이유는, 헤비유저
판정과 앱이 사용자에게 보여주는 스트릭 판정이 같은 잣대를 써야 대시보드 숫자와 사용자
경험이 어긋나지 않기 때문이다.

세 가지 대안을 검토하고 기각했다.

- **`studySec`(총 공부시간) 기준**: 기각. ADR-0009가 명시적으로 `focusSec`을 택했다 —
  방에 머문 시간이 아니라 실제로 집중한 시간을 기준으로 삼는다. `studySec`을 쓰면 제품
  안에 "공부한 날"의 정의가 두 개 생긴다.
- **하루 합계 10분 기준**(짧은 세션 여러 개를 합산): 기각. 같은 이유로 ADR-0009의 세션
  단위 기준과 어긋난다 — 앱 스트릭에는 안 잡히는데 헤비유저로는 잡히는 유저가 생긴다.
- **자정 분할 조각 병합 후 판정**: 기각. 아래 3번에서 별도로 다룬다.

### 3. 자정 분할 조각은 병합하지 않는다

ADR-0005에 따라 자정을 넘긴 세션은 날짜별로 분할되며, `focusSec`도 시간 비율대로 나뉜다
(예: 12분 세션 → 23:xx의 5분 조각 + 00:xx의 7분 조각). 두 조각 모두 10분 미만이라 각각은
스트릭 인정 기준을 만족하지 못한다.

이 조각들을 다시 합쳐서 "실제로는 12분 공부했으니 인정"으로 판정하는 방안을 검토했지만
기각했다. 합쳐서 판정하면 **헤비유저로는 잡히는데 앱이 사용자에게 보여주는 스트릭에는
안 잡히는** 유저가 생긴다. 대시보드 숫자가 사용자가 실제로 보는 화면과 어긋나는 것이,
자정 경계에서의 판정 정확도보다 나쁘다고 판단했다. 자정 처리 방식 자체를 바꾸고 싶다면
ADR-0005·ADR-0009를 함께 고쳐 앱 스트릭과 헤비유저 판정이 같이 움직이게 해야 한다.

이 결정은 `HeavyUserQueryIntegrationTest`의
`자정_분할로_조각난_세션은_각_조각이_10분_미만이면_인정되지_않는다` 테스트가 고정하고
있다. 이 ADR이 없으면 그 테스트는 나중에 "왜 12분 공부한 사람이 헤비유저에 안 잡히지?"라는
의문과 함께 버그로 오인되어 수정될 위험이 있다 — 이 테스트를 고칠 일이 생기면 먼저 이
ADR을 개정해야 한다.

### 4. 집계 기준일은 "KST 어제"

발송 시각이 오전 10시(KST)라 발송 당일은 아직 하루가 끝나지 않아 세션이 부분적으로만
쌓인 상태다. 오늘을 기준일로 포함하면 같은 유저 집합이라도 발송 시각(또는 재발송 시각)에
따라 집계 수치가 흔들려 날짜 간 비교가 성립하지 않는다. 완결된 하루인 "어제"를 기준일로
고정하면 항상 같은 조건으로 비교할 수 있다. 헤비유저 조회 구간도 이에 맞춰
`[어제 - 6일, 어제]`(어제를 포함한 7일)로 잡는다.

## 결과

- 헤비유저 판정 로직이 `StudySessionMetricsService`에, 임계값이
  `StudySessionThresholds`에 있으며 앱 화면의 스트릭 판정과 상수를 공유한다. ADR-0009가
  바뀌면 헤비유저 판정도 같이 움직인다.
- 별도 BI 인프라·비용이 없다. 대시보드가 필요해지면 이 ADR의 결정을 재검토해야 한다.
- 자정 분할 조각을 병합해 헤비유저 판정을 "개선"하려는 시도는 이 ADR을 먼저 개정해야
  한다 — `HeavyUserQueryIntegrationTest`가 그 전까지 회귀를 막는다.
- 상세 산출 방식(SQL 형태, 임계값 상수의 소속 클래스 등)은
  `docs/superpowers/specs/2026-08-09-daily-metrics-slack-report-design.md`에 있다.
