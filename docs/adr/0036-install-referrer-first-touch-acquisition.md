# ADR-0036: 설치 정보로 사용자별 첫 유입 경로를 한 번만 저장하고, 메타 광고는 암호문 유무로 판별한다

- 상태: 승인
- 날짜: 2026-10-29
- 티켓: BY-1066 (상위 BY-1065, 짝 FE BY-1068, 키 전달 BY-1067)
- 설계: `docs/superpowers/specs/2026-10-29-by1066-install-attribution-design.md`
- 관련: ADR-0015(API 버전), ADR-0019(게스트 기기 토큰 인증), ADR-0035(키가 없으면 그 기능만 끄고 기동)

## 맥락

메타 영상 광고 10개(iOS 5, Android 5)를 집행하기 시작했고, 광고별로 끝까지 남는 사용자를 비교하려면 사용자마다 처음 들어온 경로가 필요하다.
Android의 메타 광고 정보는 플레이 설치 정보(Install Referrer) 안에 암호화돼 오고, 복호화 키를 앱에 넣으면 앱을 뜯어 꺼낼 수 있어서 서버가 푼다.
iOS는 설치 정보가 없어서 메타 지연 딥링크의 `fm_ad` 값(`ios_v1`~`ios_v5`)으로만 광고를 안다.
앱(BY-1068)이 설치 정보 원문과 딥링크 값을 로그인 뒤 한 번 보내고, 서버는 판별해 저장한 결과를 돌려준다.

## 결정

1. **메타 광고 판별은 암호문 유무로 하고 `utm_source`는 보지 않는다.** 메타 문서가 암호화된 캠페인 메타데이터 밖의 매개변수(`utm_source` 등)는
   보장되지 않으니 페이스북 설치의 지표로 쓰지 말라고 적고 있다
   (https://developers.facebook.com/docs/app-ads/install-referrer). `utm_content` JSON에 `source.data`와 `source.nonce`가 있으면
   메타 광고로 본다. `utm_*`는 판별에는 안 쓰지만 있으면 항상 저장해 분석 때 다시 나눌 수 있게 한다.
2. **판별 순서는 메타 암호문 > 친구 초대(`code`, 숫자 4자리) > 딥링크 > 오가닉 > 그 밖의 링크 > 알 수 없음이다.** 초대를 딥링크보다
   먼저 보는 이유는 플레이 설치 정보가 스토어로 들어가기 직전에 누른 링크이고 메타 딥링크는 메타 기준 기간 안에서 붙은 값이라, 마지막
   클릭인 초대 링크가 더 정확하기 때문이다. 딥링크를 오가닉보다 먼저 보는 이유는 메타 광고를 누른 뒤 플레이에서 직접 검색해 설치하면
   설치 정보는 오가닉이고 딥링크만 광고를 가리키기 때문이다. `utm_source=(not set)`처럼 플레이가 값을 비워 보낸 경우는 `OTHER_LINK`로
   가고, 원문이 남아 있어 나중에 SQL로 다시 나눌 수 있다.
3. **복호화 결과의 필드는 광고 관리자 계층과 한 단계씩 어긋나므로 매핑해 저장하고, 결과 JSON 전체를 `meta_payload`(jsonb)에 남긴다.**
   `campaign_group_*`는 캠페인, `campaign_*`는 광고 세트, `adgroup_*`는 광고다(Adjust 매핑표 기준,
   https://help.adjust.com/en/article/facebook-raw-data-reporting-for-android). 메타 예시의 `ad_id`는 `adgroup_id`와 값이 다르고 어느
   계층인지 문서에 없다. 그래서 광고 ID는 `adgroup_id`를 쓰고, 첫 실데이터가 들어오면 광고 관리자의 광고 ID와 대조한다. 어긋나면
   `meta_payload`에서 다시 꺼낸다.
4. **사용자당 한 행만 두고 첫 값을 덮어쓰지 않는다.** 저장은 `INSERT … ON CONFLICT (user_id) DO NOTHING` 한 문장이고, 그 뒤 행을 읽어
   돌려준다. 같은 사용자의 요청이 동시에 와도 먼저 들어간 행이 남고 두 요청이 같은 응답(200)을 받는다. 두 번째 요청의 값은 버리며
   버려진 값에 대한 로그는 없다(충돌 자체는 조용하다. 판별이 저장보다 먼저라 그 값의 복호화가 실패하면 5번의 WARN은 남는다). 앱이 실패 뒤 다시 보내도 안전해야 하고, "처음 들어온 경로"가 이 데이터의 의미라서다. `users`에 컬럼을 더하지 않고
   `user_acquisition`(V33)을 따로 둔 이유는 분석용 nullable 컬럼 열댓 개가 모든 사용자 조회에 딸려 오지 않게 하려는 것이다.
5. **키가 없거나 복호화에 실패해도 원문만 남기고 200으로 응답하고, 기동은 막지 않는다.** 키가 비었거나 hex 64자가 아니면 기동 때 WARN 한
   줄을 남기고 복호화만 끈다(ADR-0035와 같은 판단). 풀지 못한 메타 암호문은 `META_AD`로 저장하되 ID·이름·`meta_payload`는 비운다. 실패
   로그는 예외 종류(`getClass().getSimpleName()`)만 남긴다. 예외 메시지에 입력 일부가 섞일 수 있어서이고, 키는 응답·로그·예외 메시지
   어디에도 남기지 않는다. 키 하나 때문에 API 전체가 못 뜨거나 앱이 매번 재시도하는 쪽이 더 나쁘다.
6. **메타 ID는 DB(`varchar`)와 응답(JSON string) 모두 문자열이다.** 18자리라 JS `number`의 정밀도(2^53)를 넘는다. 초대코드도 앞자리 0이
   있어 문자열로 둔다.

## 결과

- 운영 배포 전에 키(`META_INSTALL_REFERRER_KEY`, 프로퍼티 `app.acquisition.meta-install-referrer-key`)를 먼저 넣어야 한다. 첫 값을 덮어쓰지
  않는 규칙 때문에 키 없이 저장된 행은 나중 요청으로 채워지지 않는다. 배포 순서는 키 주입 → 배포 → FE 앱 업데이트 제출이다.
- 키 없이 저장된 행은 원문이 남아 있어 일회성 작업으로 다시 풀 수 있다. 그 작업은 이번 범위 밖이다.
- 앱 업데이트가 깔리면 기존 사용자도 한 번씩 보낸다. 이들의 행은 플레이가 기억하는 설치 정보(설치 후 90일)이거나 `UNKNOWN`이라, 광고
  분석은 `users.created_at`이 광고 집행 시작 뒤인 사용자로 거른다. 게스트는 앱을 다시 설치하면 새 사용자가 되어 새 행이 생긴다.
- `user_acquisition.user_id` FK에 삭제 연쇄가 없어, 탈퇴 기능이 생기면 이 행을 먼저 지워야 한다(`push_token`과 같다).
