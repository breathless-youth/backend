# ADR-0007: 스트릭은 세션 이력에서 조회 시 계산

- 상태: 승인
- 날짜: 2026-07-25

## 맥락
연속 공부일(스트릭)을 users에 카운터(streak, max_streak)로 저장하고 제출·조회 시
갱신하는 구현을 먼저 검토했다. 저장 방식은 읽기가 O(1)이지만 값의 정확성이 "모든
쓰기·읽기 경로가 갱신 규칙을 지킨다"에 의존한다. 실제 초기 구현에서 갱신 시점
문제가 연달아 나왔다 — 저장 후 카운트라 첫 세션 판정이 불가능했고, 조회 API가
상태를 리셋해 오늘 공부한 유저의 스트릭을 지웠으며, 클라이언트 호출 순서에 따라
값이 달라졌다. 파생값 사본의 전형적인 동기화 문제다.

## 결정
- 스트릭을 저장하지 않고 `GET /api/study-sessions/streak`에서 study_session의
  distinct stat_date 이력으로 매번 계산한다
- 현재 스트릭: 오늘(오늘 기록이 없으면 어제)부터 거꾸로 이어진 연속 공부일 —
  오늘이 지나기 전엔 끊긴 것으로 보지 않는다. 어제도 오늘도 없으면 0
- 최장 스트릭: 전체 이력에서 가장 긴 연속 구간
- KST 오늘 이후 날짜는 계산에서 제외한다 (종료 시각 5분 오차 허용으로 자정 직후
  조각이 내일 날짜로 저장될 수 있음)
- stat_date는 NOT NULL로 강제(V4, 레거시 NULL은 started_at의 KST 날짜로 백필),
  사용하지 않던 users.streak/max_streak 컬럼은 제거(V3)
- 기록 없음·존재하지 않는 userId는 0/0 — 목록 조회와 같은 계약

## 결과
- 파생값 사본이 없어 갱신 시점 버그 클래스가 통째로 사라진다. 진실은 세션 테이블 하나
- 조회 비용은 유저당 distinct 날짜 수에 비례 — 10년 매일 공부해도 수천 행이라
  MVP 규모에선 무시 가능한 수준
- 이력이 커져 조회가 실제로 아프면 순서대로 재검토: SQL 집계(gaps-and-islands) →
  조회 윈도우 제한 → 쓰기 경로에서만 갱신하는 저장형 복귀
