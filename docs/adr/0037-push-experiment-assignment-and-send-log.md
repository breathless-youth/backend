# ADR-0037: 푸시 실험은 서버가 배정을 기록하고, 발송은 미리 잡은 하루 한 자리로만 나간다

- 상태: 승인
- 날짜: 2026-10-29
- 티켓: BY-1070
- 설계: `docs/superpowers/specs/2026-10-29-by1070-first-session-push-ab-design.md`
- 관련: ADR-0035(서버 직접 FCM 발송), ADR-0030(일일 리포트·Amplitude 적재)

## 맥락

첫 서버 발송 시나리오는 "첫 세션 순공 5분이 리텐션을 올리는가"를 확인하는 A/B 실험이다. 비교하려면 알림을 받지 않은 대조군이
있어야 하고, 돌아오지 않은 사람까지 포함해 모든 배정자의 집단을 알아야 한다. 앱은 앱을 연 사람만 기록할 수 있어 대조군과
알림을 누르지 않은 사람을 표시할 수 없다. ADR-0035는 발송 기록·`push_id`·비교군을 첫 시나리오로 미뤄 두었다.

## 결정

1. **배정은 서버가 `push_experiment_assignment`에 남긴다.** 키는 `(experiment, user_id)`이고 control도 남긴다. 대상으로 처음
   잡힌 순간 `SecureRandom`으로 반씩 나누고 바꾸지 않는다. 대조군은 알림을 받을 수 있는 사람(권한이 켜진 토큰) 안에서 뽑는다.
2. **결과는 DB에서 계산해 일일 리포트에 싣는다.** Amplitude로 집단을 보내지 않는다 — Amplitude 이벤트는 이미 매일 DB로
   적재된다(ADR-0030). 리포트 스레드는 일곱 개가 된다.
3. **결과(첫 세션·D7)는 배정 행에 한 번 채우고 바꾸지 않는다.** 첫 세션은 측정 세션 중 묶음 키(`submission_started_at`)가 가장
   이른 묶음이고, 순공은 자정 분할 조각의 합이다. D7은 가입 7일 뒤 그날의 Amplitude `study_session_started`이고, 그날과 다음
   날 적재가 끝난 뒤 채운다. 리포트가 읽기 전에 채운다 — 발송을 끈 뒤에도, 리포트의 61·68일 창을 넘겨도 결과가 남아야 해서다.
4. **발송 기록 `push_send`에 보내기 전에 자리를 잡는다.** 유니크 `(user_id, send_date)`가 사람당 하루(KST) 1회 상한이다. 자리를
   잡지 못하면 보내지 않고, 잡은 뒤 FCM 호출이 실패해도 그날 다시 보내지 않는다. 행의 `push_id`가 FCM data에 실려 앱 열림
   이벤트와 이어진다.
5. **발송 작업은 10분 틱이고 놓친 창을 따라잡지 않는다.** 틱 시각을 10분 격자로 반올림하고, 후보 창이 틱 간격과 같아 한 사람은
   한 틱에서만 잡힌다. 실제 사용자에게 보내므로 `app.push.first-session-experiment.enabled`가 없으면 꺼진다.
6. **대상 판정은 사용자·세션·토큰 테이블을 테이블명으로만 읽는다.** 지표 쿼리(SessionFactQueries)와 같은 방식이다.

## 결과

- 다음 실험은 실험 키만 바꿔 같은 배정 테이블을 쓰고, 다음 시나리오는 `push_send`로 하루 상한을 함께 지킨다.
- 하루 상한이 DB 제약이라 하루 2회 이상이 필요해지면 제약을 바꾸는 마이그레이션이 필요하다.
- 실험 사실을 읽지 못하면 실험 스레드만 "계산 실패"가 되고 나머지 리포트는 나간다.
- 리포트는 유의성 검정을 하지 않는다. 판정 인원(집단당 680명)이 찬 뒤 사람이 판정한다.
- 자리를 잡은 뒤 FCM이 실패한 사람은 그 단계를 받지 못한다. 실패는 `fcm_accepted = 0`과 PushSender의 Sentry 경고로 보인다.
