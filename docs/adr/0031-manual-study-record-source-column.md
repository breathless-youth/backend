# ADR-0031: 수동 기록은 study_session의 source 열로 가르고, 측정의 공정성에 기대는 집계는 측정만 읽는다

- 상태: 승인
- 날짜: 2026-10-16
- 티켓: BY-921 (스토리 BY-915)
- 명세: `.ai` 위키 `product/specs/BY-915-수동-기록.md` §5·§7·§8
- 관련: ADR-0005(자정 분할), ADR-0009(1분·10분 임계값), ADR-0015(API 버전), ADR-0028(랭킹은 조회 때 집계)

## 맥락

타이머를 켜는 걸 잊었거나 기기 없이 공부한 날은 플래너와 달력이 빈다. 사용자가 시작·종료 시각과 과목을 직접 넣는 수동 기록을 더한다.
측정 결과는 고칠 수 없다는 원칙과 "랭킹은 Vision AI가 측정한 순공 기준"은 그대로 둔다. 그래서 수동 기록은 개인 기록(일간 합계,
기간 통계, 과목 누적)에만 더하고, 랭킹·연속 공부·집중률·최대 집중·세션 복구·인터뷰 모집·Slack 리포트에는 넣지 않는다.

## 결정

1. **별도 테이블 없이 `study_session.source` 열로 가른다.** `MEASURED`(기본)·`MANUAL` 두 값이고, 수동 타이머 모드가 생기면 `TIMER`를
   더한다. V29가 `VARCHAR(16) NOT NULL DEFAULT 'MEASURED'`로 더해 기존 행은 전부 측정이 된다. 인덱스는 더하지 않는다.
2. **수동 기록은 이벤트 없는 세션이다.** `studySec = focusSec = 길이`, `events = []`이고 과목을 골랐으면 전체 구간 하나를 과목 구간으로
   남긴다. 완료 할 일·시간대 구간(`study_session_slot`) 행은 만들지 않는다. 시각은 분 단위로 버려 저장한다.
3. **다른 기록과 겹치는 구간은 빼고 남는 조각만 저장한다.** 겹침은 같은 사용자의 모든 출처를 대상으로 하고, 끝이 닿는 것은 겹침이
   아니다. 측정 세션 경계는 초 이하까지 있으므로 남는 조각을 안쪽으로 분 단위에 맞추고, 1분 미만 조각은 버린다. 남는 조각이 없으면
   409다. 미래 판정에는 측정 제출의 5분 시계 오차 여유를 두지 않는다.
   겹침을 읽고 저장하는 추가·수정은 사용자 단위 advisory 락(`pg_advisory_xact_lock`, 키 2^41 + userId)으로 줄 세워, 같은 사용자의 동시
   요청 둘이 같은 빈 시간을 읽고 둘 다 저장하지 않게 한다.
4. **조각은 첫 조각의 시작 시각을 `submissionStartedAt`으로 공유하는 한 묶음이다.** 겹침으로 잘린 조각마다 기존 `StudySessionSplitter`의
   자정 분할을 다시 거친다. 수정·삭제는 어느 조각 id로 불러도 같은 `submissionStartedAt`의 `MANUAL` 행 전체에 적용된다. 수정은 묶음을
   지우고 다시 만들므로 조각 id가 바뀌고, 지운 묶음은 겹침 계산에서 자연히 빠진다. 측정 세션 id로 부르면 409다.
   요청한 시작 시각을 키로 쓰지 않는 것은 앞이 잘린 두 요청이 같은 키를 가져 한 묶음으로 합쳐지기 때문이다. 측정 14:00~14:30이 있을 때
   `14:00~16:00`과 `14:00~17:00`을 차례로 넣으면 둘 다 14:00을 키로 가져, 어느 쪽 id로 지워도 둘 다 지워진다.
5. **제출 키 조회는 출처를 함께 본다.** 첫 조각의 시작은 `(user_id, started_at)` 유니크라 수동 묶음끼리도, 측정 루트 키와도 충돌하지
   않는다. 그래도 측정 쪽 조회(멱등 재제출, 자동 확정 대체, 세션 복구, 세션 뒤 오른 랭킹)의 `MEASURED` 필터는 출처가 섞이지 않게 방어용으로
   둔다.
6. **측정 세션 제출은 수동 기록과 겹쳐도 받는다.** 측정이 원본이고 거부하면 측정 기록을 잃는다. 겹친 수동 기록은 사용자가 고친다.
7. **측정만 읽는 곳과 수동을 포함하는 곳을 나눈다.**

   | 측정만 | 수동 포함 |
   |---|---|
   | 랭킹 집계 5종(`periodTotals`·`slotTotals`·`periodTotalsAt`·`studyDays`·`maxStreaks`) | 일간 조회 `sessions`·`sessionCount`·`totalStudySec`·`totalFocusSec`·`studiedDatesInMonth` |
   | 랭킹 누적 일수 페이스(`RankingSource.studiedDays`), 세션 뒤 오른 랭킹·추월 팝업 | 기간 통계(`GET /api/stats/period`) |
   | 연속 공부(`GET /api/stats/streak`), 누적 공부일(`GET /api/stats/study-days`) | 과목 누적 시간(`GET /api/subjects`) |
   | 일간 조회의 `focusRate`·`longestFocusSec` | |
   | 세션 복구 판정, 인터뷰 모집 판정, 일일 Slack 리포트, 시간대 구간 백필 | |
   | 측정 제출의 멱등 조회 | |

## 결과

- 새 API `POST /api/study-sessions/manual`, `PATCH`·`DELETE /api/study-sessions/manual/{id}`(`API-Version` 1, 토큰 필요).
- `StudySessionResponse`·`StudySessionSummaryResponse`에 `source`가 실린다. 수동 행의 `focusRate`는 늘 100이다.
- 일간 조회의 합계와 집중률이 서로 다른 세션 집합에서 나온다. 수동 기록이 있는 날은 `totalFocusSec ÷ totalStudySec`가 `focusRate`와 다르다.
- 측정만 봐야 하는 새 집계를 만들 때는 `source = 'MEASURED'`를 직접 걸어야 한다. 기본이 수동 포함이라 빠뜨리면 조용히 섞인다.
- 수동 기록은 시간대 구간 행이 없어 시간대 랭킹에는 필터 없이도 들어가지 않지만, 랭킹 쿼리는 공통으로 필터를 건다.
- 측정 세션이 정확히 수동 조각의 시작 시각(밀리초까지)에 시작하면 `(user_id, started_at)` 유니크 제약에 걸려 409가 난다. 측정 시각은
  밀리초까지 있어 실제로는 거의 생기지 않는다고 보고 두었다.

## 고려한 대안

- **별도 테이블(`manual_study_record`)**: 측정 테이블을 건드리지 않지만, 수동을 포함해야 하는 개인 집계 4곳(일간·기간·달력·과목 누적)에
  합산 로직이 따로 생긴다. 측정만 보는 곳이 더 많아도 수동 포함 쪽이 사용자에게 보이는 숫자라 어긋나면 바로 드러난다.
- **겹치면 거부**: 구현은 단순하지만 사용자가 시각을 다시 맞춰야 하는 막다른 길이다. 시트가 같은 계산으로 잘릴 구간을 미리 보여 주므로
  알리지 않고 값이 바뀌는 일도 없다.
- **조각 경계를 측정 세션의 초 단위 그대로 두기**: 겹침은 정확히 메워지지만 수동 기록만 분 단위라는 규칙이 깨지고, 길이를 초 단위로
  절삭하면서 합이 어긋날 수 있다.
