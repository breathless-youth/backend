# ADR-0009: 세션 저장·조회·스트릭 인정 기준을 분리

- 상태: 승인
- 날짜: 2026-07-28

## 맥락

지금까지는 "세션은 10분 이상이어야 한다"(`StudySessionValidator.MIN_DURATION`)라는 단일 규칙이
저장 여부와 스트릭 반영 여부를 동시에 결정했다. 10분 미만 세션은 저장 자체가 거부(400)되었고,
스트릭(ADR-0007)은 저장된 세션의 `statDate` 존재 여부만 보므로 "저장 안 됨 = 스트릭 안 잡힘"이
자연스럽게 성립했다.

그런데 아주 짧은 세션(몇 초~몇 분)도 기록으로 남기고 싶다는 요구가 생겼다 — 예를 들어 방에 잠깐
들어왔다 나간 것도 사용자 활동 이력으로는 의미가 있다. 저장 자체를 막는 단일 규칙으로는 이
요구를 반영할 수 없다. 저장·조회·스트릭 세 가지를 독립된 기준으로 분리해야 한다.

## 결정

- **저장**: 세션 길이 제한을 없앤다. `endedAt > startedAt`, 24시간 이내, 종료 시각이 미래가
  아님만 검증하고 저장한다 (`MIN_DURATION` 삭제)
- **일별 목록 조회(`GET /api/stats`)**: 순공시간(`focusSec`)이 1분(60초) 미만인 세션은 저장은
  되지만 조회에는 보이지 않는다. 캘린더 표시용 `studiedDatesInMonth`도 같은 기준을 적용한다
- **스트릭 인정**: 그 날짜의 세션 중 **하나라도** `focusSec`이 10분(600초) 이상이면 그 날은
  스트릭에 잡힌 날로 인정한다. 하루 합계가 아니라 세션 단위 기준이다 — 짧은 세션 여러 개를
  합쳐도 스트릭엔 반영되지 않고, 긴 세션 하나만 있으면 같은 날 다른 짧은 세션이 있어도 인정된다
- 조회·스트릭 기준값은 모두 `focusSec`(순공시간)을 본다 — 세션 길이(`endedAt - startedAt`)나
  `studySec`(총 공부시간)이 아니다. 방에 머문 시간이 아니라 실제로 집중한 시간을 기준으로
  삼는다는 점에서 ADR-0006(순공시간을 앱 제출값으로 신뢰)의 연장선이다
- 스트릭 조회 API(`GET /api/stats/streak`)에 선택적 `from`/`to` 쿼리 파라미터를 추가한다.
  둘 다 주면 그 기간 중 스트릭 인정 기준을 만족한 날짜만 담은 `studiedDatesInRange`를 추가로
  내려주고(오름차순, sparse), 하나만 주면 400. 기존 `streak`/`maxStreak` 계산 방식(ADR-0007)은
  그대로 유지한다

## 결과

- 리포지토리 쿼리 3개(`findByUserIdAndStatDateBetween...`, `findDistinctStatDates`,
  `findDistinctStatDatesBetween`)가 `minFocusSec` 파라미터를 받도록 바뀐다 — 목록 조회(1분)와
  스트릭(10분)이 같은 쿼리 형태를 임계값만 다르게 재사용한다
- 짧은 세션도 DB에는 남아 향후 분석(예: 총 방문 횟수, 앱 사용 패턴)에 쓸 수 있지만, 사용자가
  보는 통계·스트릭에는 노이즈로 끼어들지 않는다
- 스키마 변경은 없다 — `focusSec`은 이미 저장되어 있던 값이고, 임계값은 애플리케이션 상수다
- 조회 기준(1분)과 스트릭 기준(10분)이 서로 다르므로, "목록엔 보이는데 스트릭엔 안 잡히는 날"이
  생길 수 있다(순공시간 1~10분 세션만 있는 날) — 의도된 동작이며 API 문서에 명시한다
