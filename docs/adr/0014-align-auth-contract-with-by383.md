# ADR-0014: BY-383 인증 계약 정렬 — link 단일화·병합·탈퇴

- 상태: 승인
- 날짜: 2026-08-18

## 맥락
ADR-0013으로 구글/카카오/애플 소셜 로그인을 재도입했지만, 로그인 진입점이
`POST /api/auth/login`(신규 로그인)과 `POST /api/auth/link`(DEVICE 유저 연동)로
이원화되어 있었다. 그런데 클라이언트는 첫 실행 시 항상 DEVICE 등록으로 익명 토큰을
먼저 발급받은 뒤에만 소셜 로그인 화면에 진입하므로, 실제로는 "로그인 시점에 익명
토큰이 없는" 케이스가 존재하지 않는다. 즉 `/api/auth/login`은 계약상 죽은 경로이면서,
동시에 익명 세션을 병합 없이 그대로 유실시키는 별도 경로로 남아 실수로 쓰일 위험이
있었다.

또한 link 병합 시 기존 계정과 익명 계정의 공부 세션이 시간대상 겹칠 수 있는데,
겹침을 방치하면 순공시간·스트릭 집계가 왜곡된다. 세션 저장(제출) 경로에서도
동일한 유저의 세션이 시간상 겹치는 것을 애초에 막을 수단이 없었다 — 애플리케이션
레벨 검증만으로는 동시 요청·경합 상태에서 겹침을 완전히 막지 못한다.

마지막으로, ADR-0004(로그인 MVP 제외) 폐기 이후 남아있던 소프트 삭제(`UserStatus`,
`delete_at`) 잔재가 실제 탈퇴 요구사항(BY-383)과 맞지 않았다 — 재로그인 시 이전
데이터를 되살릴지 여부가 불명확한 채로 방치되어 있었다.

근거 문서: `.ai` 리포 `product/specs/BY-383-소셜로그인-인증인가.md`

## 결정

### 1. 로그인 진입을 link로 단일화 (`/api/auth/login` 제거)
클라이언트가 항상 DEVICE 등록으로 먼저 익명 토큰을 확보한 뒤 소셜 로그인에
진입하는 구조이므로, "익명 토큰 없이 소셜 로그인"을 가정한 `/api/auth/login`
경로는 실사용되지 않으면서 병합 누락의 함정만 남긴다. 이 엔드포인트와
SecurityConfig의 permitAll 등록을 제거하고, 신규 유저든 기존 유저든 소셜 로그인은
항상 `POST /api/auth/link` 한 경로로만 처리한다.

### 2. link 병합 경로 — 겹치는 세션은 기존 계정 우선으로 폐기
소셜 계정이 이미 존재하는 상태에서 link가 호출되면(재설치, 기기 변경 등),
익명(DEVICE) 계정의 공부 기록을 기존 계정으로 이관한다. 이때 두 계정의 세션이
시간대상 겹치는 경우, **겹치는 익명 세션은 폐기하고 기존 계정 세션을 우선**한다.
겹침을 그대로 두면 순공시간 합산과 스트릭 계산이 중복·왜곡되기 때문이다.
병합 절차는 다음 순서로 수행한다.

1. 겹치는 익명 세션 id를 native `tstzrange` 겹침 연산으로 조회
2. 겹치는 세션을 엔티티 단위로 삭제(`status_event`는 cascade)
3. flush
4. 겹치지 않는 나머지 익명 세션을 벌크 reassign(기존 계정으로 소유권 이전)
5. 익명 유저 행과 그 refresh 토큰을 소멸

병합 건수(폐기된 세션 수)는 API 응답에는 포함하지 않고 로그로만 남긴다 —
클라이언트가 소비할 계약이 아니라 운영 관측용이기 때문이다.

### 3. 유저별 세션 무겹침을 DB exclusion constraint로 불변식화
애플리케이션 레벨 검증만으로는 동시 제출·경합 상태에서 겹침을 완전히 막을 수
없고, 위 2번의 병합 로직도 애플리케이션 버그가 있으면 겹침을 놓칠 수 있다.
두 경우 모두를 최후 방어선에서 막기 위해 PostgreSQL exclusion constraint로
DB 레벨 불변식을 건다.

- V9 마이그레이션: `study_session.ended_at`을 `NOT NULL`로 변경하고,
  `btree_gist` 확장을 활성화한 뒤 다음 제약을 추가한다.

  ```sql
  ALTER TABLE study_session
    ADD CONSTRAINT ex_study_session_user_period
    EXCLUDE USING gist (
      user_id WITH =,
      tstzrange(started_at, ended_at, '[)') WITH &&
    );
  ```

  반개구간(`[)`)을 사용해 한 세션의 종료 시각과 다음 세션의 시작 시각이 정확히
  맞닿는 경우(연속 세션)는 겹침으로 취급하지 않는다.

- 제약 위반 시 409 Conflict로 "이미 같은 시간대에 저장된 세션이 있습니다"를
  반환한다. Hibernate/JDBC 드라이버가 exclusion constraint 위반 시 제약 이름을
  안정적으로 노출하지 않으므로, SQLState `23P01`(`exclusion_violation`) 코드와
  에러 메시지 매칭을 fallback으로 함께 사용해 예외를 식별한다.

### 4. 탈퇴는 하드 삭제
`DELETE /api/users/me`는 유저의 세션(cascade)과 refresh 토큰 전량을 삭제한 뒤
유저 행 자체를 삭제한다. 소프트 삭제(상태 플래그) 대신 즉시 전부 삭제하며,
탈퇴 후 같은 소셜 계정으로 재로그인하면 완전히 새로운 신규 가입으로 취급된다
(이전 데이터 복구 없음). 이 API는 멱등하게 설계한다.

이에 따라 V10 마이그레이션에서 `users` 테이블의 `status`, `delete_at` 컬럼을
drop하고, `UserStatus` enum과 `rejectIfDeleted` 검증 로직을 제거한다 — 소프트
삭제 개념 자체가 더 이상 존재하지 않으므로 관련 코드를 코드베이스에 남겨두지
않는다.

## 트레이드오프: 겹침 스킵 vs 클립
겹치는 익명 세션을 처리하는 방법은 두 가지가 있었다.

- **스킵(채택)**: 겹치는 세션을 통째로 폐기한다. 구현이 단순하고, 겹침 판정에
  경계 조건 버그가 생길 여지가 적다. 대신 부분적으로만 겹치는 세션은 겹치지
  않는 꼬리 부분의 기록도 함께 손실된다.
- **클립**: 겹치는 구간만 잘라내고 겹치지 않는 부분은 살린다. 데이터 손실은
  최소화되지만, 세션 분할·재계산 로직이 복잡해지고 status_event 등 하위
  레코드의 시간 재정합까지 필요해진다.

BY-383 단계에서는 손실을 감수하고 스킵을 선택했다. link를 통한 계정 병합은
빈도가 낮은 이벤트이고, 겹침 자체도 흔치 않을 것으로 예상하기 때문이다. 병합
로그에 남는 폐기 건수를 관측하다가, 실제로 유의미한 손실이 반복된다고 확인되면
그때 클립으로 업그레이드한다.

## 폐기
- `POST /api/auth/login` 엔드포인트와 SecurityConfig permitAll 등록 → 제거
- `UserStatus` enum, `users.status`/`users.delete_at` 컬럼, `rejectIfDeleted` → 제거

## 결과
- 로그인 진입점이 `POST /api/auth/link` 하나로 통일되어 익명 세션 이관 누락
  가능성이 구조적으로 사라졌다
- 세션 시간 겹침이 애플리케이션 버그·동시 요청과 무관하게 DB 레벨에서 항상
  방지된다 (제출 시점 충돌 방어 + 병합 누락 방어를 동일 제약 하나로 커버)
- 탈퇴 즉시 하드 삭제로 데이터 보존 정책이 단순해졌다

### 한계
- 탈퇴 하드 삭제는 `study_session`(cascade)과 `refresh_token`만 명시적으로
  정리한다. 유저를 FK로 참조하는 다른 테이블(예: `push_token`)은 현재 쓰기
  경로 자체가 없어 이번 범위에서 제외했다 — 코드에 가드 주석으로 표시해
  두었다. 해당 기능이 실제로 쓰이기 시작하면 탈퇴 삭제 경로에 포함해야 한다.
- 겹침 병합은 스킵 전략이라 부분 겹침 시 꼬리 구간 기록이 손실된다 (위
  트레이드오프 참조).
