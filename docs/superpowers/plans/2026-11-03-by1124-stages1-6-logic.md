## 모든 작업이 따르는 공유 결정

**저장 방식.** 그룹 테이블(`study_group`, `study_group_member`, `study_group_application`, `group_study_alert`, `user_block`, `user_report`)은 JPA 엔티티 없이 `JdbcClient` + record 행 리포지토리로 다룬다(`RoomRepository` 방식). 상태를 바꾸는 갱신은 건수를 돌려주고 호출자가 0건을 "상황이 바뀜"으로 처리한다.

**락 순서 (교착 방지, 바꾸지 않는다).** ① `study_group` 행 `FOR UPDATE`(한 작업에 그룹 하나) → ② 그룹 한도용 사용자 advisory lock `pg_advisory_xact_lock((1::bigint << 42) + userId)` (2^41은 수동 기록 lock, 2^40은 초대코드 lock, 9,724,000,000은 과목 lock이 이미 쓴다) → ③ 룸의 기존 사용자 lock(`RoomRepository.lockUser`) → ④ `rooms` 행(id 오름차순) → ⑤ `room_participations` 행. 앞 단계를 건너뛸 수는 있어도 거꾸로 잡지 않는다.

**시각.** 모두 `Clock` 빈. 오늘 = `LocalDate.ofInstant(now, Asia/Seoul)`, 이번 주 시작 = 오늘이 속한 주 월요일. 신청 기한 = 만든 시각 + 3일. 내보낸 뒤 3일 = `leave_reason='KICKED' AND left_at > now - 3일`.

**기한 지난 신청.** `status='PENDING' AND expires_at > now`만 "답을 기다리는 신청"이다. 개수 제한·목록·applyState·새 신청 수 모두 이 조건이다(만료 작업이 아직 안 돌았어도).

**글자.** 요청 DTO의 `@TextLength`가 길이를 본다. 서비스는 `Graphemes.normalize`(NFC+strip)한 값을 저장하고, 소개(description)는 비면 null로 저장한다. 이름·소개·신청 소개 글은 `ContactDetector.containsContact`가 참이면 400 `CONTACT_NOT_ALLOWED`.

**커밋 뒤 효과.** `project.study.common.tx.AfterCommit.run(Runnable)` (Task 2가 만든다): 트랜잭션 동기화가 켜져 있으면 `afterCommit`에 등록하고, 아니면 바로 실행한다. 실행 중 예외는 잡아서 로그+Sentry만 남기고 던지지 않는다. STOMP 발송과 푸시는 전부 이것으로만 보낸다. 푸시는 그 안에서 다시 별도 실행기(가상 스레드)로 넘겨 요청 스레드를 붙잡지 않는다.

**스케줄러.** 새 스케줄러는 `@ConditionalOnProperty(name = "app.group.scheduler.enabled", havingValue = "true", matchIfMissing = true)`. 테스트 `src/test/resources/application.yaml`에 `app.group.scheduler.enabled: false`를 넣고, 테스트는 서비스 메서드를 직접 부른다. 모든 스케줄 작업은 조건부 UPDATE로 한 행을 한 태스크만 처리한다(ShedLock 없음).

**푸시 문구** (BY-1124 표, 그대로 쓴다. `{그룹 이름}`·`{닉네임}`은 값 그대로 끼운다):

## Review Focus

1. **동시 요청이 한도를 넘는 경우** — 같은 그룹에 두 사람이 동시에 코드 참여·수락해 7명이 되거나, 한 사람이 동시에 그룹 3개를 만들거나 신청 4개를 보내는 경우. 락 순서대로 그룹 행 → 사용자 advisory를 잡고 센다. Task 2·7에 병렬 스레드 테스트를 둔다.
2. **초대코드 방·옛 앱이 그대로인지** — 초대코드 방 SNAPSHOT·MEMBER_JOINED JSON에 `micOn`·`onBreak`·`owner` 키가 아예 없고, `/state`의 `micOn`은 저장·방송되지 않는다. Task 6에 JSON 키 부재 테스트를 둔다. 기존 room 테스트는 고치지 않고 통과해야 한다.
3. **롤백되면 아무것도 안 나가는지** — 업무 트랜잭션이 롤백되면 푸시·STOMP가 없다. Task 2에 `AfterCommit` 롤백 테스트, Task 7에 "재발급 실패 → 내보내기 롤백, 푸시 없음" 테스트를 둔다.
4. **기한 지난 PENDING 신청** — 만료 작업 전이라도 개수·목록·applyState에서 빠지고, 같은 그룹에 다시 신청하면 부분 unique에 막히지 않는다. Task 4에 테스트를 둔다.
5. **드러나면 안 되는 것** — 책상은 다른 곳이 어디인지(싱글룸·다른 그룹) 드러내지 않고, `PEER_BLOCKED`는 양쪽이 같은 모양이며, 비공개 그룹은 공개 보기·신청에서 404다. Task 5·9에 테스트를 둔다.
