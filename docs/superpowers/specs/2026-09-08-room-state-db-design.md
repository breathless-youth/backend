# 룸 상태 DB 원본화 설계

- 상태: v3 확정 — Codex 1차(14건)·2차(10건) 점검 반영, 사용자 검토 완료(2026-09-09)
- 날짜: 2026-09-08 (v3: 2026-09-09)
- 대체: ADR-0017(배포 시 룸 스냅샷 이어받기, 철회)
- 티켓: BY-626 (스냅샷 방식 티켓을 재사용, 본문 갱신)

## 0. 목표와 범위

`RoomService`는 방·참가자 상태를 전부 인메모리(HashMap + 단일 `synchronized` 락)로 관리한다. ECS 롤링
배포에서 옛 태스크가 SIGTERM을 받으면 방이 전부 사라지고, 프론트는 STOMP 재접속 후 `/topic/room/{id}`를
다시 구독하고 스냅샷을 재요청할 뿐 HTTP `join`을 다시 부르지 않아 좀비 방에 갇힌다. ADR-0017의 종료
스냅샷 방식은 땜빵이고 크래시를 못 덮어 철회했다.

**결정**: 방·참가자 상태의 진실 원천을 PostgreSQL로 옮긴다. 근거는 (1) 부하테스트에서 RDS는 4~9%로
병목이 아니고 첫 병목은 Spring CPU였다(단, 이 수치는 state 프레임마다 쓰기가 없던 때의 값이라 §7의
통과 기준으로 재측정한다), (2) 단일 락이 주던 원자성은 DB 제약 + 방 행 락 + "락 아래에서 다시 읽기" +
조건부 갱신으로 재현된다, (3) 크래시·OOM까지 덮는다, (4) 수평 확장 때도 멤버십 진실 원천은 DB로 남길 수 있다.

**범위 안**
- 라이브 상태를 기존 이력 테이블 `rooms`·`room_participations`에 통합한다. 행을 지우지 않는 것이 이력이다.
- 룸 도메인 이벤트 4종·`RoomHistoryRecorder`·비동기 실행기·`ClosedInviteCodes`·인메모리 `Room`/`Participant` 제거.
- 크래시로 죽은 태스크가 쥔 참가자를 정리하는 태스크 리스(`live_task`) + 오판 시 펜싱.
- `studySeconds` → `focusSec` 이름 변경(컬럼·STOMP 인바운드·아웃바운드 전부). 옛 이름은 받지 않는다.
- 소셜 지표 쿼리의 `left_at IS NULL` 처리를 "지금까지 진행 중"으로 변경.

**FE 계약 변경·후속 (티켓 댓글로 전달)**
- 계약 변경 1: `StateUpdatePayload.focusSec`(인바운드), `SNAPSHOT`/`MEMBER_JOINED`의 `members[].focusSec`,
  `STUDY_TIME.focusSec`(아웃바운드). 룸 기능이 함께 출시되므로 FE가 처음부터 새 이름을 쓴다.
- 계약 변경 2: `members[]`에 `disconnected: boolean` 추가. 끊김 유예 중인 멤버를 "재접속 중"으로 표시하고
  후속 1의 재대조 시점을 잡는 데 쓴다.
- 후속 1: **피어 연결이 `disconnected`/`failed`가 되면 `/app/room/{id}/snapshot`을 즉시 재요청하고, 실패한
  피어가 남아 있는 동안 10초 주기로(최소 유예 30초를 넘겨서) 재요청해 목록과 화면을 대조**한다. 즉시 한 번만
  요청하면 상대가 아직 유예 중이라(`disconnected: true`) 목록에 남아 있어 유령을 못 지운다. 배포 겹침
  구간에 상대 태스크에서 처리된 MEMBER_LEFT 유실(§4)을 메우는 유일한 경로다.
- 후속 2: `/user/queue/room`으로 `{type: "ROOM_UNAVAILABLE"}`을 받으면 join을 다시 부르거나 종료 안내를 띄운다
  (서버는 구독 거부·확정 실패 시 요청 세션에만 보낸다, §2.9). 이 메시지의 배달은 보장되지 않으므로
  **SNAPSHOT 재요청이 모두 소진돼도 SNAPSHOT이 안 오면 같은 상태로 취급**한다.

**범위 밖 (감수하는 한계)**
- **배포 겹침 구간의 태스크 간 메시지 전달.** STOMP 심플 브로커는 프로세스 안의 인메모리 브로커라, 한 방의
  멤버가 옛/새 태스크로 갈리면 브로드캐스트·시그널·유저 큐 메시지가 상대 태스크의 소켓에 닿지 않는다.
  온전하게 하려면 태스크 간 릴레이(Postgres LISTEN/NOTIFY 또는 Redis pub/sub)가 필요하고, 별도 티켓이다.
- 트랜잭션 커밋 직후 태스크가 크래시하면 그 커밋의 MEMBER_LEFT 브로드캐스트는 유실된다(영속 이벤트 없음).
  후속 1이 메운다.

**바뀌지 않는 상수**: 정원 6, 예약 TTL 30초, 끊김 유예 30초, 빈 방 TTL 600초, 초대코드 묘비 600초.

## 1. 스키마

마이그레이션 `V15__room_live_state.sql`. 룸 기능 미출시라 `rooms`·`room_participations`에는 QA 행만 있어
DROP 후 재생성한다.

```sql
DROP TABLE room_participations;
DROP TABLE rooms;

CREATE TABLE live_task (
    task_id      varchar     PRIMARY KEY,     -- ECS 태스크 ID(로그 스트림과 일치), 없으면 UUID
    heartbeat_at timestamptz NOT NULL,
    reclaimed_at timestamptz                  -- NOT NULL = 다른 태스크가 이 태스크를 죽었다고 보고 참가자를 회수함(펜싱 신호)
);

CREATE TABLE rooms (
    id           bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    invite_code  char(4)     NOT NULL,
    created_by   bigint      NOT NULL REFERENCES users (id),
    created_at   timestamptz NOT NULL,
    closed_at    timestamptz,                  -- NULL = 열린 방. 닫힌 방은 영구 보존(이력)
    close_reason varchar(20)                   -- LAST_LEFT | EMPTY_EXPIRED
);
CREATE UNIQUE INDEX rooms_open_code_uidx   ON rooms (invite_code) WHERE closed_at IS NULL;  -- 열린 방끼리 코드 유일
CREATE INDEX        rooms_code_latest_idx  ON rooms (invite_code, created_at DESC);         -- join: 코드의 최신 방
CREATE INDEX        rooms_open_created_idx ON rooms (created_at) WHERE closed_at IS NULL;   -- 빈 방 만료

CREATE TABLE room_participations (
    id                 bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    room_id            bigint      NOT NULL REFERENCES rooms (id),
    user_id            bigint      NOT NULL REFERENCES users (id),
    nickname           varchar,
    goal               varchar,
    category           varchar,
    camera_on          boolean     NOT NULL DEFAULT false,
    focus_state        varchar(20) NOT NULL DEFAULT 'FOCUS',
    focus_sec          integer     NOT NULL DEFAULT 0,
    reserved_at        timestamptz NOT NULL,
    stomp_confirmed    boolean     NOT NULL DEFAULT false,
    stomp_session_id   varchar,
    session_opened_at  timestamptz,               -- 마지막으로 확정된 세션의 소켓 오픈 시각. 옛 세션의 뒤늦은 confirm이 새 세션을 덮지 못하게 한다
    task_id            varchar,
    disconnected_at    timestamptz,
    joined_at          timestamptz,               -- 최초 STOMP 확정 시각. NULL = 확정된 적 없는 예약
    left_at            timestamptz,               -- NULL = 지금 자리를 가진 참가자
    leave_reason       varchar(20)                -- EXPLICIT | DISCONNECT_TIMEOUT | SWITCHED_ROOM
) WITH (fillfactor = 70);                        -- state 프레임마다 UPDATE → HOT 여유 공간 확보(§7에서 실측)
CREATE UNIQUE INDEX rp_live_user_uidx      ON room_participations (user_id)          WHERE left_at IS NULL;  -- 동시 1룸
CREATE UNIQUE INDEX rp_live_room_user_uidx ON room_participations (room_id, user_id) WHERE left_at IS NULL;  -- 중복 예약 방지·핫패스
CREATE INDEX rp_session_idx      ON room_participations (stomp_session_id) WHERE stomp_session_id IS NOT NULL;
CREATE INDEX rp_reserved_idx     ON room_participations (reserved_at)      WHERE left_at IS NULL AND NOT stomp_confirmed;
CREATE INDEX rp_disconnected_idx ON room_participations (disconnected_at)  WHERE left_at IS NULL AND disconnected_at IS NOT NULL;
CREATE INDEX rp_task_idx         ON room_participations (task_id)          WHERE task_id IS NOT NULL;
CREATE INDEX rp_user_joined_idx  ON room_participations (user_id, joined_at);   -- 기존 유지 (지표 조인)
```

**불변식과 보장 주체**

| 불변식 | 보장 |
|---|---|
| 열린 방끼리 초대코드 유일 | `rooms_open_code_uidx` |
| 묘비 기간(닫힌 지 10분) 코드 재발급 금지 | 코드 단위 advisory lock(§2.1·§2.3): 발급과 닫힘이 같은 코드에서 직렬화됨 |
| 유저는 동시에 한 방에만 | `rp_live_user_uidx` |
| 같은 방에 같은 유저 자리 하나 | `rp_live_room_user_uidx` |
| 정원 6 | 방 행 `FOR UPDATE` 아래에서 count |
| 마지막 자리가 비면 방 즉시 닫힘 | 자리를 비우는 트랜잭션이 방 행 락 아래에서 count 후 닫음 |
| 확정된 적 없는 예약은 이력 없음 | `joined_at IS NULL`이면 만료 때 DELETE, 아니면 `left_at` 갱신 |
| 소켓 없는 "연결됨" 행은 남지 않음 | 리스 스윕(§3): 살아 있는 리스가 없는 `task_id`의 참가자를 끊김으로 전환 |
| 옛 세션이 새 세션을 덮지 않음 | `session_opened_at` 단조 조건(§2.5) |

**현재 코드 → 스키마 매핑**: `Room.id/inviteCode/createdAt` → `rooms`; `Room.uid` 삭제(안정적 ID로 대체,
`rtc_connection_stat.room_id`도 이 값을 가리키게 됨); `Participant.*` → `room_participations` 동명 컬럼,
`studySeconds` → `focus_sec`, `firstConfirmedAt` → `joined_at`; `sessionToUser` → `rp_session_idx`;
`userToRoomId` → `rp_live_user_uidx`; `expiryCandidates` → `rp_reserved_idx`+`rp_disconnected_idx`;
`emptyRooms` → `rooms_open_created_idx`; `ClosedInviteCodes` → `closed_at` 보존 행 + 코드 advisory lock.

**시각은 전부 앱이 파라미터로 넘긴다.** DB `now()`를 쓰지 않아 테스트가 `cleanupExpired(now.plusSeconds(31))`로
시간을 조작할 수 있다. 태스크 간 시계 차이는 NTP 수준(ms)이라 30초 단위 판정에 무해하다.

## 2. 연산별 SQL · 락 · 트랜잭션

**세 가지 원칙**

1. **락 순서**: 유저 advisory lock → 방 행(id 오름차순) → 참가자 행 → 코드 advisory lock(닫을 때만, 항상 마지막).
   `create`는 코드 advisory lock만 잡는다. 리스 회수(§2.10-1)는 리스 행 → 참가자 행만 잡고 방·`live_task` 외의
   락은 잡지 않는다. 단일 행 조건부 갱신(confirm, disconnect, state)은 락을 잡지 않는다.
2. **락 아래에서 다시 읽는다**: 락을 잡기 전에 읽은 값은 판단 근거로 쓰지 않는다. 방 락을 잡은 뒤 참가자 행을
   `FOR UPDATE`로 다시 읽고 그 값으로 분기한다. 이것이 인메모리 전역 락이 주던 "읽기와 쓰기 사이에 아무도
   끼어들지 않음"을 대신한다.
3. **쓰기·락 경로는 네이티브 SQL + record 프로젝션**(`JdbcClient`). JPA 영속성 컨텍스트는 같은 트랜잭션에서 한
   번 읽은 엔티티를 다시 조회해도 DB 값을 반영하지 않으므로, 관리 엔티티와 네이티브 갱신을 같은 트랜잭션에서
   섞지 않는다. JPA 엔티티(`Room`, `RoomParticipation`)는 `ddl-auto: validate` 스키마 검증과 테스트 조회에만 쓴다.

모든 UPDATE/DELETE는 갱신 건수 또는 `RETURNING`을 확인하고, 0건을 "상황이 바뀜"으로 처리한다.

### 2.1 create(userId, now)

```sql
-- 최대 100회 시도. 코드 = SecureRandom 4자리. 시도마다 트랜잭션 1개
SELECT pg_advisory_xact_lock(hashtext(:code));            -- 같은 코드의 닫힘(§2.3)과 직렬화
INSERT INTO rooms (invite_code, created_by, created_at)
SELECT :code, :userId, :now
WHERE NOT EXISTS (SELECT 1 FROM rooms WHERE invite_code = :code AND closed_at > :now - interval '600 seconds')
ON CONFLICT (invite_code) WHERE closed_at IS NULL DO NOTHING
RETURNING id
```

- 0행이면 다음 코드로 재시도. 예외·롤백 없이 한 문장으로 "열린 방 충돌"(ON CONFLICT)과 "묘비 충돌"(NOT EXISTS)을
  같이 거른다.
- 코드 advisory lock을 잡는 동안 같은 코드의 방은 닫힐 수 없으므로(닫는 쪽도 같은 락을 잡는다) NOT EXISTS가
  본 스냅샷이 커밋 시점까지 유효하다. v2에서 "감수"했던 닫힘-발급 동시 레이스가 사라진다. 락은 문장 하나
  동안만 유지되고 다른 락과 겹치지 않는다.

### 2.2 join(userId, code, profile, now) — 트랜잭션 1개

1. `SELECT pg_advisory_xact_lock(:userId)` — 같은 유저의 동시 join 직렬화. 다른 유저·leave·cleanup은 이 락을 안
   잡으므로 이것만으로는 아래 4~5의 다시 읽기를 생략할 수 없다.
2. 대상 방: `SELECT id, closed_at FROM rooms WHERE invite_code = :code ORDER BY created_at DESC LIMIT 1`.
   없음 → `INVITE_CODE_NOT_FOUND`. `closed_at` 있음 → 10분 이내면 `ROOM_CLOSED`, 아니면 `INVITE_CODE_NOT_FOUND`.
3. 현재 자리(락 없음, 잠글 방을 알기 위한 사전 조회): `SELECT room_id FROM room_participations WHERE user_id = :userId AND left_at IS NULL`.
4. 방 행 락: `SELECT id, invite_code, closed_at FROM rooms WHERE id IN (:target, :currentRoom) ORDER BY id FOR UPDATE`.
   락 획득 후 대상 방의 `closed_at`을 **이 결과로** 재확인(2와 4 사이에 닫혔으면 `ROOM_CLOSED`).
5. 현재 자리를 **락 아래에서 다시 읽는다**: `SELECT * FROM room_participations WHERE user_id = :userId AND left_at IS NULL FOR UPDATE`.
   행이 사라졌으면(그 사이 cleanup/leave가 자리를 비움) 자리 없음으로 진행한다. 3과 **다른 방**의 라이브 행이
   보이면 1의 유저 락이 막아야 할 상태이므로 불변식 위반으로 예외를 던져 트랜잭션을 롤백한다(잠그지 않은
   방을 건드리지 않기 위해).
6. 분기(5의 값으로만 판단)
   - 현재 자리가 대상 방이고 `disconnected_at`이 있으면 **유예 복귀**: `UPDATE ... SET disconnected_at = NULL,
     stomp_confirmed = false, stomp_session_id = NULL, task_id = NULL, reserved_at = :now, nickname/goal/category
     WHERE id = :id AND disconnected_at IS NOT NULL` → 1행 확인 → `graceRejoin = true, cameraOn = 행의 camera_on`.
     `session_opened_at`은 지우지 않는다(옛 세션의 뒤늦은 confirm 차단 유지). 참가자 행을 잠근 채 판단하므로
     동시 `confirmStomp`는 이 트랜잭션 커밋 뒤에 적용되어 최종 상태가 "확정됨"이 된다. confirm이 먼저
     커밋됐다면 5에서 `disconnected_at`이 NULL로 보여 이 분기를 타지 않는다.
   - 현재 자리가 대상 방이면(예약 재시도·확정 멤버의 중복 join) `reserved_at`·프로필만 갱신 → `graceRejoin = false`.
     `stomp_confirmed`·세션은 건드리지 않는다.
   - 그 외(자리 없음 또는 다른 방):
     a. `count(*) WHERE room_id = :target AND left_at IS NULL` ≥ 6 → `ConflictException("방이 가득 찼어요")`.
        기존 방 자리를 건드리기 전에 검사한다(대상 방이 가득이면 기존 자리를 잃지 않는다).
     b. 다른 방에 자리가 있으면 `removeParticipant(그 행, SWITCHED_ROOM)`(§2.3, 그 방도 4에서 잠겨 있다)
        → `autoLeave = (그 방, userId)`.
     c. `INSERT INTO room_participations (room_id, user_id, nickname, goal, category, reserved_at)`.
7. 응답: `roomId`, `graceRejoin`, `cameraOn`, TURN 자격(기존 `TurnCredentialIssuer`), `autoLeave`.
   컨트롤러는 지금처럼 `autoLeave`가 있으면 옛 방 토픽에 MEMBER_LEFT를 브로드캐스트한다.

부분 유니크 인덱스 두 개는 이 로직에 버그가 있어도 라이브 행이 둘이 되는 것을 막는 최후 방어선이다.

### 2.3 removeParticipant(행 id, roomId, inviteCode, reason, now, 추가 조건) — 호출자가 방 행 락을 쥔 상태

멱등이어야 한다. 최종 문장에 라이브 조건(과 호출 맥락의 만료 조건)을 넣고 `RETURNING`으로만 결과를 판단한다.

```sql
-- 확정된 적 없는 예약: 이력 없이 삭제
DELETE FROM room_participations
 WHERE id = :id AND left_at IS NULL AND joined_at IS NULL [AND <만료 조건>]
RETURNING id;
-- 확정된 참가자: 이력으로 남김
UPDATE room_participations
   SET left_at = :now, leave_reason = :reason, stomp_session_id = NULL, task_id = NULL, disconnected_at = NULL
 WHERE id = :id AND left_at IS NULL AND joined_at IS NOT NULL [AND <만료 조건>]
RETURNING id;
-- 위 둘 중 하나라도 1행이면: 마지막 자리였는지 확인해 방을 닫는다. 코드 락은 방 락 뒤, 항상 마지막
SELECT pg_advisory_xact_lock(hashtext(:inviteCode));
UPDATE rooms SET closed_at = :now, close_reason = 'LAST_LEFT'
 WHERE id = :roomId AND closed_at IS NULL
   AND NOT EXISTS (SELECT 1 FROM room_participations WHERE room_id = :roomId AND left_at IS NULL)
RETURNING id;
```

- `<만료 조건>`은 cleanup 경로에서만 붙는다: `(NOT stomp_confirmed AND reserved_at < :reservationDeadline) OR
  disconnected_at < :graceDeadline`. 후보를 읽은 뒤 복귀·확정한 행은 조건이 안 맞아 0행이 되고, 그러면
  MEMBER_LEFT도 방 종료도 일어나지 않는다.
- 이미 나간 행(`left_at` 있음)에 다시 불려도 0행이라 `left_at`·`leave_reason`이 덮이지 않는다.
- 반환값 `Removed(removed: boolean, roomClosed: boolean)`. 호출자는 `removed`일 때만 `AutoLeave`/MEMBER_LEFT를 만든다.

### 2.4 leave(roomId, userId, now) — 트랜잭션 1개

방 행 `FOR UPDATE`(없거나 닫힘 → `removed = false`) → 라이브 행 `(room_id, user_id)`를 `FOR UPDATE`로 조회(없음 →
false) → `removeParticipant(EXPLICIT)` → `LeaveResult(removed, roomStillOpen = !roomClosed)`. 컨트롤러는
`removed && roomStillOpen`일 때만 MEMBER_LEFT를 브로드캐스트한다(지금의 `roomExists` 재조회 제거).

### 2.5 confirmStomp(roomId, userId, sessionId, sessionOpenedAt, taskId, now)

옛 세션의 뒤늦은 SUBSCRIBE(인바운드 큐에 밀려 있다가 세션이 닫힌 뒤 처리되는 경우)가 죽은 세션을 다시
등록하거나 새 세션을 덮는 것을 막는다. 지금의 인메모리 코드에도 같은 레이스가 있지만, 펜싱(§3)이 소켓을
한꺼번에 닫는 순간에는 확률이 커지므로 세 겹으로 막는다.

1. **사전 검사**: `SessionRegistry.isOpen(sessionId)`가 false면 빈 목록. 펜싱·정상 종료는 소켓을 닫기 전에
   레지스트리에서 먼저 닫힘으로 표시한다.
2. **단조 조건부 UPDATE**:
   ```sql
   UPDATE room_participations
      SET stomp_confirmed = true, stomp_session_id = :sessionId, session_opened_at = :openedAt,
          task_id = :taskId, disconnected_at = NULL, joined_at = COALESCE(joined_at, :now)
    WHERE room_id = :roomId AND user_id = :userId AND left_at IS NULL
      AND (session_opened_at IS NULL OR session_opened_at <= :openedAt)
   ```
   `openedAt`은 그 세션의 소켓 오픈 시각(레지스트리가 기록). 더 늦게 열린 세션이 이미 확정돼 있으면 옛 세션은
   0행이 되어 무시된다. 이 값은 같은 태스크의 시계라 세션 간 비교가 정확하다.
3. **사후 검사**: UPDATE 뒤 `SessionRegistry.isOpen(sessionId)`가 false가 됐으면(UPDATE 중에 닫힘)
   `handleDisconnect(sessionId)`(§2.6)로 보정한다. 세션 ID가 일치할 때만 지우므로 그 사이 새 세션이 확정됐다면
   건드리지 않는다.

0행이면 빈 목록(방/참가자 없음 또는 옛 세션) → `StompEventListener`는 요청 세션에 `ROOM_UNAVAILABLE`(§2.9)을
보낸다. 1행이면 확정 멤버 목록(`WHERE room_id = :roomId AND left_at IS NULL AND stomp_confirmed`, 각 멤버의
`disconnected = disconnected_at IS NOT NULL` 포함)을 SNAPSHOT용으로 반환. 방 락은 잡지 않는다(인원이 안 바뀐다).
join이 이 행을 잠그고 있으면 join 커밋 뒤에 적용된다(§2.2 6).

### 2.6 handleDisconnect(sessionId, now)

```sql
UPDATE room_participations
   SET disconnected_at = :now, stomp_session_id = NULL, task_id = NULL
 WHERE stomp_session_id = :sessionId AND left_at IS NULL
```

세션 ID로 바로 행을 찾는다. 재접속이 옛 세션의 끊김보다 먼저 도착한 경우 `stomp_session_id`가 이미 새 값이라
0행으로 무시된다. 확정된 적 없는 세션도 0행. `session_opened_at`은 남겨 둔다. `sessionToUser` 맵이 필요 없다.

### 2.7 updateState(roomId, userId, sessionId, cameraOn?, focusState?, focusSec?) — 핫패스

핸들러가 **SQL 전에 지금처럼 필드별로 검증**한다. `focusState`가 FOCUS/DISTRACTED가 아니거나 `focusSec`가
음수면 그 필드만 null로 바꿔 무시하고 나머지는 반영한다(요청 전체를 거절하지 않는다). 세 필드가 전부 null이면
SQL을 보내지 않는다.

```sql
UPDATE room_participations
   SET camera_on   = COALESCE(:cameraOn, camera_on),
       focus_state = COALESCE(:focusState, focus_state),
       focus_sec   = COALESCE(:focusSec, focus_sec)
 WHERE room_id = :roomId AND user_id = :userId AND left_at IS NULL
   AND stomp_confirmed AND stomp_session_id = :sessionId
```

갱신 행 수 1 = 인가(현재 세션의 확정 멤버) + 저장. 지금의 `isActiveSession` + `updateCamera` +
`updateFocusState` + `updateStudyTime`(락 4회)을 한 문장으로 대체한다. 핸들러는 지금처럼 null이 아닌 필드마다
`CAMERA_CHANGED`/`FOCUS_CHANGED`/`STUDY_TIME`(키 `focusSec`)을 브로드캐스트한다. 갱신 컬럼이 인덱스에 없고
`fillfactor = 70`이라 HOT 업데이트가 유지된다(§7 통과 기준으로 실측).

### 2.8 authorizeSignal(roomId, fromUserId, sessionId, toUserId)

`SELECT user_id, stomp_confirmed, stomp_session_id FROM room_participations WHERE room_id = :roomId AND user_id IN
(:from, :to) AND left_at IS NULL` 한 번으로 "발신자가 현재 세션의 확정 멤버"와 "수신자가 확정 멤버"를 판정한다
(`from = to`인 자기 시그널도 처리).

### 2.9 스냅샷 재요청 · SUBSCRIBE 인가 · ROOM_UNAVAILABLE

- `getMembersForActiveSession`: 확정 멤버 목록 조회에 `EXISTS(요청자가 현재 세션의 확정 멤버)`를 붙인 한 문장.
  지금처럼 인가와 조회가 한 번의 원자 호출이다. 빈 목록이면 지금처럼 조용히 무시한다(세션 확정 전 재시도가
  실패하는 정상 레이스이므로 `ROOM_UNAVAILABLE`을 보내지 않는다).
- `hasParticipant(roomId, userId)`(SUBSCRIBE 인가, `WebSocketConfig`): `EXISTS ... WHERE room_id, user_id, left_at IS NULL`.
  예약자(미확정 포함)만 구독 가능한 규칙 유지.
- **`ROOM_UNAVAILABLE`은 두 곳에서, 요청 세션에만 보낸다**(`handleSnapshotRequest`와 같은 세션 스코프 헤더;
  같은 유저의 정상 세션에 새지 않게): (1) `allowSubscribe`가 false를 돌려줄 때, (2) `handleSubscribe`에서
  `confirmStomp`가 빈 목록을 돌려줄 때(인가는 통과했는데 그 사이 cleanup이 자리를 회수한 경우). 배달은 보장되지
  않는다 — 유저 큐 구독 등록이 아직 안 됐으면 사라진다. 그래서 FE 후속 2는 "SNAPSHOT 재요청 소진"도 같은
  상태로 취급한다.

### 2.10 cleanupExpired(now) — 5초 스케줄러, 모든 태스크가 실행

`cleanupExpired`는 **트랜잭션을 열지 않는 진행자**다. 단계마다 `TransactionTemplate`로 짧은 트랜잭션을 열고
커밋한다. 락을 단계 사이로 넘기지 않으므로 데드락 경로가 없다. advisory lock으로 스윕을 단일화하지
않는다 — 모든 문장이 조건부·멱등이라 두 태스크가 동시에 스윕해도 같은 행을 두 번 처리하지 못한다.
**방 하나를 커밋할 때마다 그 방의 MEMBER_LEFT를 즉시 브로드캐스트하고, 방마다 예외를 격리한다**(한 방의 DB
오류가 다른 방의 처리·알림을 막지 않는다). 커밋과 브로드캐스트 사이의 크래시는 §0의 감수 항목이다.

1. **죽은 태스크 회수** (§3의 연속성 조건을 만족할 때만. 리스 행마다 트랜잭션 1개):
   ```sql
   -- 후보: heartbeat가 30초 넘게 끊겼고 아직 회수 안 된 리스
   SELECT task_id FROM live_task WHERE heartbeat_at < :now - interval '30 seconds' AND reclaimed_at IS NULL;
   -- 리스 행을 잠그며 회수 표시. 그 태스크의 heartbeat UPDATE와 같은 행에서 직렬화된다
   UPDATE live_task SET reclaimed_at = :now
    WHERE task_id = :t AND heartbeat_at < :now - interval '30 seconds' AND reclaimed_at IS NULL
   RETURNING task_id;
   -- 1행일 때만 그 태스크의 참가자를 끊김으로 전환
   UPDATE room_participations
      SET disconnected_at = COALESCE(disconnected_at, :now), stomp_session_id = NULL, task_id = NULL
    WHERE task_id = :t AND left_at IS NULL;
   ```
   리스 행을 먼저 잠그므로, 그 태스크가 같은 순간 heartbeat를 찍으면 둘 중 하나만 이긴다. heartbeat가 이기면
   회수 UPDATE는 `heartbeat_at < ...`가 거짓이라 0행이고 참가자를 건드리지 않는다. 회수가 이기면 heartbeat는
   `reclaimed_at`을 돌려받아 펜싱한다(§3). v2의 "참가자는 회수됐는데 리스는 살아남아 펜싱이 영영 안 되는" 구멍이
   여기서 막힌다.
   리스 행이 아예 없는 `task_id`의 참가자(등록 전에 죽은 태스크, 이론상 §3의 등록-먼저로 불가)는 잠글 행이 없고
   heartbeat도 불가능하므로 같은 전환을 바로 적용한다.
   회수된 지 10분 지난 리스 행은 지운다(`DELETE FROM live_task WHERE reclaimed_at < :now - interval '10 minutes'`).
   자기 리스를 되살린 태스크는 `reclaimed_at`을 NULL로 되돌리므로(§3) 살아 있는 태스크의 행은 안 지워진다.
2. **만료 후보** (방마다 트랜잭션 1개 → 커밋 → 그 방 브로드캐스트): `SELECT id, room_id FROM room_participations
   WHERE left_at IS NULL AND ((NOT stomp_confirmed AND reserved_at < :reservationDeadline) OR disconnected_at <
   :graceDeadline)`(락 없음) → 방별로 묶어 방 행 `FOR UPDATE` → 후보마다 `removeParticipant(DISCONNECT_TIMEOUT,
   만료 조건 포함)`(§2.3) → `removed`인 것만 MEMBER_LEFT.
3. **빈 방** (방마다 트랜잭션 1개): `SELECT id, invite_code FROM rooms WHERE closed_at IS NULL AND created_at <
   :emptyDeadline AND NOT EXISTS (라이브 참가자)` → 방 행 락 → 코드 advisory lock → `UPDATE rooms SET closed_at = :now,
   close_reason = 'EMPTY_EXPIRED' WHERE id = :id AND closed_at IS NULL AND NOT EXISTS (라이브 참가자)`.

**confirm ↔ cleanup 레이스**: cleanup이 후보를 읽은 뒤 confirm이 커밋되면, §2.3의 조건부 DELETE/UPDATE는 새 행
버전에서 만료 조건이 거짓이라 0행 → 확정 유지, MEMBER_LEFT 없음. 반대로 cleanup이 먼저 지우면 confirm은 0행 →
`ROOM_UNAVAILABLE`(§2.9)이 요청 세션에 간다.

### 2.11 트랜잭션 경계 요약

| 연산 | 트랜잭션 | 잡는 락 |
|---|---|---|
| create | 시도마다 1개 | 코드 advisory |
| join | 1개 | 유저 advisory → 방(들) → 참가자 행 → (방 닫을 때) 코드 advisory |
| leave | 1개 | 방 → 참가자 행 → (방 닫을 때) 코드 advisory |
| confirmStomp / handleDisconnect / updateState / authorizeSignal / 스냅샷 / hasParticipant | 각 1개(단일 문장) | 행 락만(갱신 시) |
| cleanupExpired | 없음(진행자). 리스·방마다 1개 | 회수: 리스 행 → 참가자 행. 방별: 방 → 참가자 행 → 코드 advisory |
| heartbeat(§3) | 1개(단일 문장, 전용 커넥션·전용 스레드) | 리스 행 |

## 3. 크래시 복구 — 태스크 리스와 펜싱

- **태스크 ID**: `ECS_CONTAINER_METADATA_URI_V4`가 있으면 `/task`의 `TaskARN` 마지막 조각(CloudWatch 로그
  스트림 이름과 일치), 없으면 기동 시 UUID. `TaskIdentity` 빈이 기동 시 한 번 정한다.
- **생명주기 phase(검증됨, Spring 7.0.8·Boot 4.1.0)**: STOMP `SubProtocolWebSocketHandler`는 phase **0**
  (`AbstractMessageBrokerConfiguration.initPhase()`), 웹서버 정지는 `MAX-2048`, graceful shutdown은 `MAX-1024`.
  stop은 높은 phase부터 실행되므로 정상 종료 순서는 graceful shutdown → 웹서버 정지 → … → STOMP 핸들러가
  세션을 `GOING_AWAY`로 닫음(0) → 그 아래 phase. **`TaskLease`는 phase `-1000`**으로 둔다: start는 STOMP
  핸들러보다 먼저(소켓이 생기기 전에 리스 등록), stop은 핸들러보다 뒤(소켓이 다 닫힌 뒤까지 heartbeat 유지).
- **heartbeat 스레드는 `TaskLease`가 직접 소유하는 `ScheduledExecutorService`**다. Spring의
  `ThreadPoolTaskScheduler`는 `ContextClosedEvent` 시점에 `initiateEarlyShutdown()`을 호출해(검증:
  `ExecutorConfigurationSupport.onApplicationEvent`) graceful shutdown이 끝나기 전에 주기 작업을 멈춘다. 그러면
  드레인 중(소켓은 살아 있음)에 heartbeat가 끊겨 다른 태스크가 정상 드레인 중인 참가자를 회수한다. 자체
  executor는 `stop()`에서만 멈춘다.
- **heartbeat 커넥션은 전용**: 최대 1개짜리 별도 `HikariDataSource`(`connectionTimeout` 5초). HTTP·STOMP·cleanup이
  기본 풀 10개를 다 점유해도 heartbeat는 기다리지 않는다. "전용 스레드"만으로는 커넥션 대기를 못 피한다.
- **등록은 먼저**: `start()`에서 `INSERT INTO live_task (task_id, heartbeat_at, reclaimed_at) VALUES (:me, :now, NULL)
  ON CONFLICT (task_id) DO UPDATE SET heartbeat_at = EXCLUDED.heartbeat_at, reclaimed_at = NULL`. 요청을 받기
  전에 행이 존재하므로 "첫 heartbeat 전에 confirm이 커밋되고 죽는" 고아가 생기지 않는다. DB가 없으면 기동
  실패(datasource 정책과 동일).
- **heartbeat(5초)**: `UPDATE live_task SET heartbeat_at = :now WHERE task_id = :me RETURNING reclaimed_at`.
  성공적으로 커밋된 시각을 로컬 `lastCommittedBeat`에 기록한다(실패·타임아웃은 기록하지 않는다).
  - 1행이고 `reclaimed_at IS NULL` → 정상.
  - 1행이고 `reclaimed_at IS NOT NULL`, 또는 0행(행이 사라짐) → **펜싱 대상**. 신호가 행에 남아 있으므로 커밋은
    됐는데 응답을 못 받은 경우에도 다음 heartbeat에서 다시 보인다(v2의 `xmax = 0` 일회성 신호 문제 해결).
- **삭제하지 않는다**: 정상 종료 때도 리스 행을 지우지 않는다. 낡게 두면 §2.10-1이 그 태스크의 남은 참가자
  (끊김 처리가 실패한 것 포함)를 전환하고 회수 표시한 뒤 10분 뒤 행을 치운다.
- **판정**: 살아 있는 리스가 없는 `task_id`의 참가자 = 소켓이 죽었다고 본다. `disconnected_at = 지금`으로
  바꾸고 기존 유예 30초 경로에 맡긴다. **회수 시점은 "살아 있는 태스크가 죽음을 감지한 뒤 30초"**다. 태스크가
  1개뿐일 때 크래시하면 대체 태스크가 뜰 때까지 아무도 감지하지 않으므로, 대체 태스크 기동 후 30초 안에
  재접속하면 자리가 그대로다.
- **남을 죽였다고 판정하려면 나부터 연속이어야 한다**: 스윕 태스크는 자기 `lastCommittedBeat` 기록이 **최근 30초
  동안 5초 간격으로 끊김 없이 이어졌을 때만** §2.10-1을 실행한다(관찰 기간). DB 순단 뒤에는 양쪽 다 30초간
  회수를 건너뛰고 heartbeat만 찍으므로, 늦게 회복한 쪽이 아직 커넥션을 못 잡았더라도 먼저 회복한 쪽이 곧바로
  회수하지 않는다. 30초가 지나도 못 돌아온 태스크는 실제로 요청도 못 받는 상태이므로 회수한다.
- **펜싱**(heartbeat가 회수 신호를 받았을 때, 이 순서로):
  1. `SessionRegistry.fence()`: 모든 세션을 레지스트리에서 닫힘으로 표시한 뒤 `GOING_AWAY`로 닫는다. 이후
     들어오는 `confirmStomp`는 §2.5-1의 사전 검사에서 거절된다.
  2. 리스 되살리기: `INSERT ... ON CONFLICT (task_id) DO UPDATE SET heartbeat_at = :now, reclaimed_at = NULL`.
     `lastCommittedBeat` 이력을 비워 관찰 기간(30초)을 다시 시작한다(되살아난 직후에 남을 회수하지 않는다).
  3. FE가 5초 뒤 재접속하면 자리는 유예 30초 안이라 `confirmStomp`가 복원하고 `task_id`가 다시 나를 가리킨다.
  회수는 참가자 세션을 이미 비웠으므로 살아 있는 소켓의 프레임은 전부 거부되고 FE는 소켓이 안 끊겼으니
  재접속하지 않는다. 펜싱이 이 상태를 "5초 깜빡임"으로 바꾼다. 세션 목록은 `WebSocketConfig`에
  `WebSocketHandlerDecoratorFactory`를 걸어 `WebSocketSession`과 오픈 시각을 태스크 메모리에 등록/해제하는
  `SessionRegistry`가 쥔다(룸 상태가 아니라 소켓 핸들이다).
- **정상 종료 경로와의 수렴**: SIGTERM → Boot graceful shutdown → 웹서버 정지 → STOMP 핸들러가 모든 세션을
  `GOING_AWAY`로 닫음 → 세션마다 `SessionDisconnectEvent` → `handleDisconnect`가 `disconnected_at` 기록 →
  `TaskLease.stop()`. 그동안 heartbeat는 계속 찍혀 다른 태스크가 드레인 중인 참가자를 회수하지 않는다.
  stopTimeout 안에 못 끝나 SIGKILL이 와도, 또 일부 `handleDisconnect`가 실패해도, heartbeat가 멈추므로 다른
  태스크의 스윕이 같은 상태로 수렴시킨다.

## 4. 배포 겹침 구간 동작 (A안)

| 단계 | 상태 | 동작 |
|---|---|---|
| 새 태스크 헬스체크 통과 | ALB가 새 타깃 추가 | 신규 연결이 양쪽에 분산될 수 있음 |
| 옛 타깃 드레인 | 기존 소켓은 옛 태스크에 유지 | 신규 연결은 새 태스크로만. 같은 방 멤버가 갈릴 수 있음 |
| 갈린 구간 | DB는 공유, 브로커는 분리 | join·구독·스냅샷·state 저장은 정상. 상대 태스크 멤버에게 브로드캐스트·시그널·유저 큐 미도달 |
| 옛 태스크 SIGTERM | 소켓 닫힘, 유예 시작 | FE 5초 뒤 재접속 → 새 태스크 → `hasParticipant` 통과 → `confirmStomp` 유예 해제 → SNAPSHOT·MEMBER_JOINED |

**자가 치유의 범위**: SNAPSHOT은 구독한 사람에게만 가고, 방에 있는 동안의 멤버 목록은 브로드캐스트로만
갱신된다. 따라서 재접속한 사람은 새 SNAPSHOT으로 정확해지지만, **이미 새 태스크에 붙어 있어 한 번도 안 끊긴
사람은 상대 태스크에서 처리된 MEMBER_LEFT(명시 퇴장·만료 모두)를 영영 받지 못해 유령 멤버가 남을 수 있다.**
어느 태스크가 그 퇴장을 처리하느냐는 ALB 분배와 어느 스윕이 먼저 도느냐에 달린 우연이다. 이 유령은 방이
닫힐 때까지 남는다. 서버만으로는 태스크 간 릴레이 없이 못 없애며, **FE 후속 1**이 이를 메운다. 단, 피어가
끊긴 직후의 SNAPSHOT에는 상대가 유예 중(`disconnected: true`)으로 아직 실려 있으므로, 유예가 끝난 뒤(30초 이후)
다시 대조해야 유령이 지워진다. 그래서 후속 1은 "실패 피어가 남아 있는 동안 10초 주기"다.

갈린 구간의 길이는 ALB 타깃 그룹 deregistration delay가 결정한다(인프라 레포에서 조정).

## 7. 롤아웃 · 운영

- V15는 파괴적(DROP). 룸 미출시·QA 행뿐임을 확인하고 적용.
- 머지 후 첫 배포는 옛 태스크가 인메모리라 한 번은 방이 사라진다(미출시라 영향 없음). 이후 배포부터 유지.
- STOMP 인바운드 스레드가 이제 JDBC로 블로킹된다. 기본 풀은 코어×2라 0.5vCPU에서 2개 → `clientInboundChannel`
  executor를 8 안팎으로 올린다. Hikari 기본 10 유지 + 리스 전용 1개.
- **부하 재측정과 통과 기준**(다음 라운드, 동접 2000·실제 FE state 빈도 기준):

  | 지표 | 어디서 | 통과 기준 |
  |---|---|---|
  | `room_participations` HOT 비율 `n_tup_hot_upd / n_tup_upd` | `pg_stat_user_tables` | ≥ 90% (30분 소크 후) |
  | `hikaricp.connections.pending` | actuator metrics | 유지 구간 0, 입장 버스트 p99 < 1초 |
  | heartbeat 지연(예정 대비 커밋 시각) | 앱 로그/메트릭 | p99 < 2초, 5초 초과 0건 |
  | state 처리 p95(수신→브로드캐스트) | k6/APM | < 100ms |
  | RDS CPU / WAL 생성량 | CloudWatch | CPU < 30%, WAL은 기준선 대비 기록 |
  | 데드락(`deadlocks` in `pg_stat_database`) | RDS | 0 |

  기준 미달이면 state 코얼레싱(BY-470과 같은 방식) 또는 `focus_sec` 쓰기 주기 완화를 다음 조치로 검토한다.
  기존 RDS 4~9%는 이 쓰기 패턴이 없던 때의 값이라 근거로 쓰지 않는다.
- 문서: ADR-0018(룸 상태 DB 원본화, 0017 대체), `docs/erd.dbml` 갱신, 티켓 댓글로 FE 계약 변경 2건·후속 2건.
