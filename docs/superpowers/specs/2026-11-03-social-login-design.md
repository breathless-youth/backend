# 소셜 로그인 백엔드 설계 (그룹 신원 이어가기)

- Jira: BY-1126, 브랜치 `feature/BY-1126-social-login`
- 원본 계약: 위키 `.ai/product/specs/BY-383-소셜로그인-인증인가.md` (2026-08-18 확정본)
- 참고 구현: PR #8 `feature/BY-383-auth-contract` — dev보다 514커밋 뒤라 머지하지 않고 지금 dev 위에서 다시 짠다
- 함께 보는 설계: BY-1124 그룹 공부방 백엔드 설계 (`feat/BY-1124-group-rooms` 브랜치의 `docs/superpowers/specs/2026-11-03-by1124-group-study-rooms-design.md`)
- 분기 기준: origin/dev `b49b680`. BY-1124가 V36~V39·ADR-0040을 잡아 이 작업은 V40·V41·ADR-0041을 쓴다(2026-11-04 맞춤). 그룹 쪽이 번호를 더 쓰면 머지 직전에 다시 맞춘다
- 표기: **[사용자]** 이번 인터뷰에서 사용자가 정한 것, **[명세]** 8월 명세에 확정된 것, **[BE 판단]** 백엔드가 정한 것

## 왜

그룹(BY-1123)은 한 번 만들면 사라지지 않는다. 그런데 지금 사람의 신원은 기기 UUID(`provider=DEVICE`)라서 앱을 지웠다 다시 깔면 다른 사람이 되고, 그룹장이면 그 그룹은 영원히 관리할 사람이 없어진다 **[사용자]**.
다시 깔아도 같은 사람으로 돌아오는 수단으로 소셜 로그인(구글·카카오·애플)을 붙인다.

지금 dev에서 살아 있는 건 비회원 토큰 체계(ADR-0019)뿐이다. 프로바이더 ID 토큰 검증기(`user/oauth/*`)와 link·login DTO는 주석 처리된 채 남아 있고, 로그인·로그아웃·탈퇴 API는 없다.

## 목표

- 비회원이 소셜 계정으로 로그인하면 지금까지의 기록이 그 계정으로 이어진다. 처음 쓰는 소셜 계정이면 지금 계정이 그대로 소셜 계정이 되고(전환), 이미 있는 소셜 계정이면 이 기기의 기록을 그 계정으로 합친다(병합) **[명세]**
- 재설치한 그룹장이 로그인하면 그룹장 자리와 그룹 멤버십을 되찾는다 (병합 경로)
- 기기별 로그아웃, 앱 안에서 계정 삭제(탈퇴)를 제공한다. 탈퇴는 스토어 심사 필수 요건이다 **[명세]**
- 그룹장이 탈퇴하면 그룹이 주인 없이 남지 않는다 **[사용자]**

## 비목표

- 로그인 강제. 혼자 공부하는 사람은 계속 비회원으로 쓴다. 로그인은 그룹 탭 진입에서만 요구하고, 그 판단은 앱이 한다 **[사용자]**
- 서버에서 비회원의 그룹 API 호출 막기. 로그인 버전 출시 때 강제 업데이트를 걸어 옛 앱을 없애고, 새 앱이 그룹 탭에서 로그인을 요구하는 것으로 충분하다 **[사용자]** (서버 차단은 앱보다 서버가 먼저 배포되는 시점 문제까지 다뤄야 해 얻는 것보다 비싸다 **[BE 판단]**)
- 한 사람이 여러 프로바이더를 한 계정에 연결하기, 계정 통합 (8월 명세의 알려진 한계 그대로)- 세션 겹침 DB 제약 (PR #8의 V9 exclusion constraint). 운영에 이미 겹친 기록이 있으면 배포가 깨지고, 이번 목적에 필요한 건 병합 때 겹침을 거르는 것뿐이다 **[BE 판단]**
- 탈퇴 재인증(step-up), 레이트 리밋 (PR #8에서 파킹한 그대로)
- 로그인 화면·문구·만 14세 고지·프로필 설정 이동 같은 앱 동작 (FE 몫, 8월 명세에 확정). 이번 작업은 BE 구현만 하고, FE 전달사항은 BE가 끝난 뒤 간단한 요약으로 따로 정리한다 **[사용자]**
- Amplitude 쪽 데이터. 탈퇴·병합 때 Amplitude 서비스의 이벤트도, 우리 DB에 적재한 `amplitude_*` 테이블도 건드리지 않는다 **[사용자]**

## 반목표 (돌아가도 이러면 실패다)

- 병합이나 탈퇴가 users를 참조하는 테이블 하나를 빠뜨려 FK 위반 500으로 실패한다. 지금 users를 FK로 참조하는 테이블이 18개, FK 없이 `user_id`를 가진 테이블까지 치면 20개가 넘고, 앞으로 그룹 테이블이 더해진다
- 병합 뒤 푸시가 사라진 비회원 계정으로 가서 그룹 알림을 못 받는다
- 병합으로 순공 시간·스트릭·랭킹이 부풀려진다 (같은 시간을 두 번 센다)
- deviceId만으로 소셜 계정의 토큰이 발급된다 (전환 뒤 옛 deviceId로 `POST /api/users`를 부르면 새 비회원이 생겨야 한다) **[명세]**
- 탈퇴했는데 그 사람의 기록·프로필 사진·토큰이 남는다 ("즉시 전부 삭제" 정책)
- 그룹장이 탈퇴한 그룹이 그룹장 없이 남는다
- 옛 앱(API-Version 없음) 계약이나 지금 비회원 등록·refresh 동작이 바뀐다

## 제약

- CLAUDE.md의 Boot 4 주의사항, Flyway 전용 스키마 변경, `@Profile` 금지, 생성자 주입, record DTO를 따른다
- 새 경로는 모두 `version = "1"` 고정이다 (ADR-0015, BY-721 규칙). 테스트는 `asUser` 앞에 버전 1 헤더를 둔다
- 발급·회전·전량 폐기는 유저 행 잠금(`UserRepository.findByIdForUpdate`) 아래에서만 한다 (ADR-0019)
- 프로바이더 검증(외부 HTTP)은 DB 트랜잭션 밖에서 한다
- link·logout·탈퇴는 모두 인증이 필요하다. `permitAll`에는 안드로이드 애플 로그인의 콜백 경로 하나만 더한다 (CLAUDE.md 규칙 6, 2026-11-03 사용자 승인)
- 새 의존성은 없어야 한다. 애플 client secret(ES256 JWT) 서명은 이미 있는 jjwt로 한다. 필요해지면 먼저 이유를 설명하고 승인받는다

## 계약

응답 에러는 지금처럼 `ErrorResponse{code, message}`이다. 401 `UNAUTHORIZED`는 `AuthExceptionHandler`가 그대로 낸다.

### `POST /api/auth/link` (v1, 인증 필요)

```jsonc
// 요청
{ "provider": "GOOGLE",   // GOOGLE | KAKAO | APPLE
  "idToken": "eyJ...",    // 프로바이더 SDK가 준 ID 토큰, 길이 상한을 둔다
  "nonce": "..." }        // 앱이 만든 nonce 원문. SDK에는 이 값의 SHA-256을 넘긴다. 애플은 필수

// 200 — 전환·병합 같은 모양
{ "accessToken": "...", "refreshToken": "...", "isNewUser": true }
```

| 상태·code | 언제 | 앱이 할 일 |
|---|---|---|
| 200 | 전환(`isNewUser: true`) 또는 병합(`false`) | 토큰 쌍을 바꿔 저장 |
| 400 `INVALID_SOCIAL_TOKEN` | ID 토큰 위조·만료·다른 앱용(aud 불일치), 이미 한 번 쓴 ID 토큰, nonce 불일치·누락, 지원하지 않는 프로바이더, 그 프로바이더의 허용 aud가 설정되지 않음 | 소셜 로그인부터 다시 |
| 400 `VALIDATION_FAILED` | 요청 형식 | |
| 401 `UNAUTHORIZED` | 우리 access 토큰이 없거나 무효 | 기존 refresh 흐름 |
| 404 `USER_NOT_FOUND` | 토큰의 사용자가 없다 (지워진 비회원) | 토큰 삭제 후 재등록 |
| 409 `ALREADY_LINKED` | 이미 소셜 계정인 사용자가 link를 불렀다 | 이미 로그인 상태, 로그인 화면 닫기 |
| 503 `SOCIAL_PROVIDER_UNAVAILABLE` | 프로바이더 검증 서버가 응답하지 않거나(연결 5초·읽기 5초 타임아웃) 5xx·429, 애플 JWKS를 못 가져옴 | 같은 소셜 로그인을 잠시 뒤 다시 |

동작:

1. 트랜잭션 밖에서 ID 토큰을 검증해 `(provider, providerUserId, email)`을 얻는다.
2. 트랜잭션 안에서 옮기는 쪽을 잠그고 DEVICE인지 확인한다.
3. 그 소셜 ID의 사용자가 없으면 **전환**: 식별자를 바꾸고 이메일을 저장, 옮기는 쪽의 refresh를 전량 지운 뒤 새 쌍을 발급한다.
4. 있으면 **병합**: 아래 "병합 규칙"대로 옮긴 뒤 옮기는 쪽의 refresh와 users 행을 지우고, 남는 쪽의 새 쌍을 발급한다. 남는 쪽의 다른 기기 refresh는 건드리지 않는다.
5. 같은 소셜 ID로 동시에 전환하다 unique 위반으로 지면, 새 트랜잭션에서 병합 경로로 한 번 더 한다 (PR #8 방식).

### `POST /api/auth/logout` (v1, 인증 필요)

요청 `{refreshToken}`, 응답 204. 호출자 소유의 사용되지 않은 토큰만 한 문장으로 지운다. 내 토큰인데 이미 회전된 것이면 재사용 감지처럼 그 사용자의 refresh를 전량 지운다. 남의 토큰이면 아무것도 안 한다 (PR #8 방식).

### `POST /api/auth/apple/callback` (인증 없음, 안드로이드 애플 웹 로그인 전용)

- 애플이 `application/x-www-form-urlencoded`로 보내는 `code`, `id_token`, `state`, `user`(첫 로그인 때만 이름)를 받아, 설정값으로 정해 둔 안드로이드 딥링크 주소로 그대로 붙여 303으로 넘긴다.
- 넘길 주소는 요청에서 받지 않고 설정값만 쓴다 (열린 리다이렉트 방지). 설정값이 없으면 404.
- 토큰 검증·로그인 처리는 하지 않는다. 앱이 딥링크로 받은 `id_token`과 nonce로 평소처럼 link를 부른다. `state` 확인은 앱이 한다.
- 요청 본문을 로그에 남기지 않는다.
- 다른 새 경로처럼 `version = "1"`이다. 애플은 `API-Version` 헤더를 보내지 않는데, 헤더가 없으면 기본 버전 1로 매칭된다 (`ApiVersionConfig.DEFAULT_VERSION`).

### `DELETE /api/users/me` (v1, 인증 필요)

```jsonc
// 요청 (본문 선택)
{ "appleAuthorizationCode": "c1a2...",  // 애플 계정일 때만. 앱이 탈퇴 직전에 애플 로그인을 다시 띄워 받는다
  "appleClient": "IOS" }                // IOS | ANDROID — 코드를 만든 클라이언트(번들 ID·Services ID)로 바꿔야 해서 받는다
// 204
```

- `appleAuthorizationCode`를 보내면 `appleClient`도 필수다. 없으면 지우기 전에 400 `VALIDATION_FAILED`, 정의되지 않은 값이면 400 `BAD_REQUEST`(최종 리뷰 — 서버가 IOS로 짐작하지 않는다).
- 사용자가 이미 없으면 204 (멱등).
- 애플 계정인데 코드가 없거나, 해지가 실패해도 탈퇴는 진행하고 경고 로그와 Sentry를 남긴다 **[BE 판단]** 해지 실패로 사용자가 탈퇴를 못 하는 편이 더 나쁘다.
- 순서: 유저 행 잠금 → 그룹 처리 → 사용자 데이터 삭제 → users 행 삭제 → 커밋 → (커밋 뒤) 프로필 사진 파일 삭제, 애플 해지, 그룹 푸시.
- `LegacyApiRequestMatcher`에 걸리지 않는 경로인지 확인한다 (지금 목록에 `/api/users/me`는 없다).

`POST /api/users`, `POST /api/auth/refresh`, 옛 앱 경로는 바꾸지 않는다.

## 병합 규칙

원칙: 옮기는 쪽 행을 남는 쪽 `user_id`로 바꾼다. 남는 쪽과 부딪히는 행은 옮기지 않고 지운다.

| 테이블 | 규칙 |
|---|---|
| `study_session` (+ `status_event`, 과목 구간·슬롯·완료 할 일은 세션을 따라간다) | 남는 쪽 세션이나 남는 쪽 진행 중 기록(draft)과 기간이 겹치는 세션은 지우고, 나머지를 옮긴다. `UNIQUE(user_id, started_at)` 충돌도 겹침에 들어간다. `status_event`는 ON DELETE CASCADE가 없으므로 먼저 지운다 |
| `active_study_session` | 같은 `started_at`이 남는 쪽에 있으면 지우고, 아니면 옮긴다 |
| `study_subject`, `study_task` | 살아 있는 과목 중 이름이 같은 것(NFC·앞뒤 공백 제거 후 비교)은 남는 쪽 과목으로 합친다. 옮기는 쪽 과목을 가리키던 세션 구간·할 일·완료 기록·옮긴 draft의 구간을 남는 쪽 과목으로 바꾸고, 옮기는 쪽 과목은 남는 쪽의 지운 과목으로 둔다(최종 리뷰 — 링크한 앱의 진행 중 세션이 병합 뒤에도 옛 과목 ID를 보낸다). 이름이 다른 과목은 남는 쪽 과목들 뒤 순서로 옮긴다 **[BE 판단]** 재설치한 사람이 같은 과목을 다시 만들었을 때 두 개로 보이지 않게 |
| `daily_completion` | 위 과목·할 일 ID를 바꾼 뒤 옮기고, unique 충돌은 지운다 |
| `user_dday` | 남는 쪽에 있으면 지우고, 없으면 옮긴다 |
| users의 프로필 값 (닉네임·사진·목표·카테고리·색·이메일) | 남는 쪽 그대로. 옮기는 쪽 프로필 사진 파일은 커밋 뒤 지운다 |
| `push_token` | 전부 옮긴다 (이 기기의 토큰이다) |
| `push_experiment_assignment`, `push_send` | 옮기는 쪽 것을 지운다 **[BE 판단]** 실험 단위가 사람이라 섞으면 분석이 흐려진다 |
| `user_acquisition` | 남는 쪽에 있으면 지우고, 없으면 옮긴다 (처음 들어온 경로) |
| `refresh_token` | 옮기는 쪽 것을 전부 지운다 |
| `rooms.created_by`, `room_participations` | 옮긴다. 옮기는 쪽이 지금 방 안에 있으면(`left_at IS NULL`) 지금의 방 나가기 처리로 먼저 끝낸다 (다른 사람에게 `MEMBER_LEFT`) |
| `ranking_record`, `ranking_best` | 남는 쪽이 같은 순위판·기간에 기록이 있으면 옮기는 쪽 기록을 지우고 나머지를 옮긴다. `ranking_best`는 더 좋은 순위가 이기되, 옮기는 쪽 최고가 남는 쪽도 든 마감(같은 판·기간)의 것이면 넘기지 않는다 |
| `rtc_connection_stat`, `amplitude_*` | 그대로 둔다 (FK 없는 분석 기록) |
| `report`, `inquiry`, `user_notification`, `study_stats_*` | 옮긴다 (지금 쓰는 코드는 없지만 FK가 있다) |
| 그룹: `study_group.owner_id` | 남는 쪽으로 바꾼다 |
| 그룹: `study_group_member` | 같은 그룹에 둘 다 살아 있는 멤버면 옮기는 쪽 행을 지운다. 나머지는 옮긴다 (나간 행 포함) |
| 그룹: `study_group_application` | 답을 기다리는 신청이 남는 쪽이 이미 멤버이거나 신청한 그룹이면 지운다. 나머지는 옮긴다 |
| 그룹: `user_block` | 합치고, 자기 자신 차단·중복은 지운다 |
| 그룹: 신고·`group_study_alert` | 옮기고, 충돌은 지운다 |

- 합친 결과가 그룹 개수 제한(5·3·2)을 넘어도 그대로 둔다. 제한은 새로 하는 행동에만 건다 **[BE 판단]**. 멤버 6명 제한은 같은 사람의 행이 하나로 줄 뿐이라 넘지 않는다.
- 옮기거나 지운 건수는 로그로만 남긴다.
- 잠금 순서: BY-1124는 그룹 행 → 사용자 행 순서로 잡는다. 병합도 옮기는 쪽이 속한 그룹 행들(ID 순)을 먼저 잡고, 두 사용자 행을 ID 순으로 잡는다.

## 탈퇴 규칙

지울 사용자를 잠근 뒤 아래를 한 트랜잭션에서 한다.

1. **그룹** (그룹 테이블이 있을 때)
   - 그룹장인 그룹마다: 다른 멤버가 있으면 가장 먼저 들어온 멤버에게 넘긴다 (`group_owner_transferred` 푸시, 공부방이 열려 있으면 `OWNER_CHANGED`). 없으면 지금 "나가기"의 그룹 지우기를 탄다 (답을 기다리던 신청은 `GROUP_DELETED`, `group_application_room_closed` 푸시).
   - 그룹 공부방에 있으면 자리를 지우고 `MEMBER_LEFT`.
   - 멤버 행·신청·차단(양쪽)·신고·알림 제한 행을 지운다.
   - 푸시는 커밋 뒤 보낸다 (BY-1124 규칙과 같음).
2. **기록**: `study_session`(+`status_event`, 세션 하위 테이블), `active_study_session`, `daily_completion`, `study_task`, `study_subject`, `user_dday`, `study_stats_*`
3. **알림·토큰**: `push_token`, `push_send`, `push_experiment_assignment`, `user_notification`, `refresh_token`
4. **그 밖**: `user_acquisition`, `room_participations`, `report`(신고한 쪽·받은 쪽), `inquiry`, `ranking_record`, `ranking_best`, `rtc_connection_stat`(본인 행 삭제, 상대로 적힌 `peer_user_id`는 NULL). `amplitude_*`는 건드리지 않는다 **[사용자]**
5. **방**: 이 사람이 만든 `rooms`는 다른 사람 기록이 걸려 있으니 지우지 않고 `created_by`를 NULL로 둔다 (마이그레이션으로 NULL 허용) **[BE 판단]**
6. users 행 삭제
7. 커밋 뒤: 프로필 사진 파일 삭제, 애플 해지

탈퇴한 사람의 지난 랭킹 기록이 빠져 지난 순위판에 빈 순위가 생길 수 있다. "즉시 전부 삭제" 정책을 따른다 **[BE 판단]**.

## 운영·출시 확인

- 로그인 앱 출시 전에 운영에 `OAUTH_GOOGLE_CLIENT_IDS`·`OAUTH_KAKAO_APP_KEYS`·`OAUTH_APPLE_BUNDLE_ID`(목록형으로 바뀐 이름)를 넣는다. 그룹 릴리즈가 먼저 나가므로 값이 없어도 기동한다 — 비어 있는 프로바이더는 로그인이 전부 400이고, 기동 뒤 빈 항목이 로그와 Sentry 경고로 남는다(최종 리뷰, Sentry는 2026-11-04)
- 애플 해지용 새 비밀값: Team ID, Key ID, Sign in with Apple 개인 키(.p8). 운영 SSM·태스크 정의, dev `.env`에 넣는다. 값이 없으면 기동은 되고 해지만 건너뛰며 경고를 남긴다 (`app.<기능>.enabled` 프로퍼티 규칙)- 안드로이드 애플 웹 로그인: 애플 개발자 계정에 Services ID를 만들고, 반환 주소로 API 서버의 `/api/auth/apple/callback`(dev·운영 도메인)을 등록한다. 콜백이 넘길 안드로이드 딥링크 주소는 FE가 정해 설정값으로 넣는다
- 개인정보처리방침에 소셜 로그인과 이메일 수집이 들어 있는지 확인한다
- 위키 `app-review-checklist.md` §0-1은 "계정 생성이 없는 앱이라 삭제는 이메일 요청"으로 확정돼 있고, `user-flow.md` S6도 "로그아웃·계정 삭제 없음"이다. 로그인이 생기면 둘 다 인앱 탈퇴로 바꿔야 한다 (기획 몫, 출시 전 확인 목록)
- 로그인 버전 앱 출시 때 강제 업데이트 최소 버전을 올린다 (FE, BY-537 장치)
- FE 전달: BE 구현이 끝난 뒤 간단한 요약으로 정리한다 **[사용자]**. 담을 것: 경로·code, nonce, 안드로이드 애플 콜백과 딥링크, 애플 탈퇴 재인증, 카카오 연결 끊기 순서, 8월 명세와 달라진 것(잘못된 ID 토큰 400, nonce, 애플 `authorizationCode`·`appleClient`)

## 전달 순서

1. link(전환·병합, 그룹 밖 테이블, nonce, 허용 aud 목록)·로그아웃, 빠뜨림 방지 테스트, ADR
2. 탈퇴(그룹 밖 테이블), 애플 해지, 안드로이드 애플 콜백
3. 그룹 테이블의 병합·탈퇴 규칙과 그룹장 넘기기 — 그룹 테이블이 dev에 들어온 만큼. 로그인이 먼저 들어갔다면 그룹 PR이 테이블을 더할 때 함께 넣는다

단계마다 서비스 단위 테스트와 API 통합 테스트(MockMvcTester, Testcontainers)를 쓰고, `./gradlew check`와 크로스 리뷰(`codex exec`, 인증 변경이라 보안 적대 점검 포함)를 거친다.
테스트로 꼭 보는 것: 전환 뒤 옛 deviceId 재등록은 새 비회원, 병합 겹침 폐기, 과목 이름 합치기, 푸시 토큰 이전, 방 안에서 병합, 동시 전환 경쟁, 로그아웃 레이스·소유권, 탈퇴 다기기 전량 폐기·멱등, 그룹장 탈퇴 넘기기·혼자면 그룹 지우기.

## 빌더에게 맡기는 것

- 클래스·메서드·code 이름, 병합·탈퇴 처리기를 테이블별로 나눌 모양
- 빠뜨림 방지 테스트를 어떻게 짤지 (`pg_constraint` 조회 등)
- 병합·탈퇴 뒤 30분 동안 남는 옛 access 토큰과 그 토큰으로 붙은 STOMP 세션을 어떻게 다룰지 (앱이 바로 토큰을 바꾸므로 받아들일 수도 있다. 받아들이면 그 토큰으로 오는 쓰기가 FK 위반 500이 아니라 404가 되는지만 본다)
- `users.status`·`delete_at` 같은 소프트 삭제 잔재를 이번에 지울지
- ADR을 하나로 쓸지 나눌지

## 열린 문제

- 애플 해지 요건의 최신 문구는 구현 전에 애플 문서("Offering account deletion in your app", Sign in with Apple REST API `revoke`)로 다시 확인한다
- 카카오 연결 끊기를 서버 어드민 키로 할 필요가 생기면 비밀값이 하나 더 는다
- 안드로이드 애플 딥링크 주소와 `state` 형식은 FE가 정한다. 정해지기 전에는 콜백 설정값이 비어 404다
