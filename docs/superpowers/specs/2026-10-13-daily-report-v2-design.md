## 1. 배경

매일 10시(KST) Slack으로 오는 일일 리포트(BY-461)를 팀이 제대로 보지 않는다. 인터뷰에서 확인한 섹션별 사용 실태:

| 지금 섹션 | 실태 | v2 |
|---|---|---|
| 가입 수·신규 목록(id·시각) | 수는 매일 봄, 시각 나열은 안 봄 | 수 + **가입 시간대 분포** |
| 헤비유저 수·id | 의미 없음 | 제거 → 고정 세그먼트 S1·"정착" 단계로 흡수 |
| 10분+ 세션 건수 | 의미 없음 | 제거 |
| 소셜 vs 싱글 순공 | 숫자만 있어 판단 불가 | 제거 → 세그먼트의 "주로 한 행동"으로 |
| 코호트 첫주 공부일수 | 안 봄 | 제거 → 리텐션 섹션으로 |
| 세션 상세(상위 20명) | "많이 했네"에서 끝남 | **어제 공부한 유저를 단계별 한 줄 프로필로** |

리포트로 하려는 결정은 **기능 우선순위**(어떤 기능이 남는 유저와 연결되나)와 **타겟 유저 정의**(어떤 사람이 남나)다.
규모는 누적 가입 약 540명·DAU 10~20명(2026-10-13 사용자 확인)이라, 모든 비율은 분모와 함께 쓰고 하루가 아니라 28일 코호트로
계산한다.

## 2. 결정 (2026-10-13 인터뷰)

1. **세그먼트는 명시적 행동 규칙으로 정의하고, 규칙 문장을 메시지에 그대로 적는다.** 업계의 행동 코호트·아하 모먼트
   분석과 같은 틀이다.
2. **고정 규칙 1개 + 자동 탐색 40개.** 고정 규칙은 "가입 후 첫 7일 중 공부한 날 3일 이상"(S1). 앱 스트릭·헤비유저와 같은 잣대다.
3. **리텐션은 두 층이다.** 전체 흐름은 다음 날(D1)·7~13일 뒤(D7~D13)·28~34일 뒤(D28~D34), 세그먼트 비교는 "첫 7일 행동 →
   7~13일 뒤에 공부했나"(2주차). 행동 기간과 결과 기간이 겹치지 않게 한다.
   - D7·D30을 "딱 그날"(N-day)로 세지 않고 7일 구간(bracket)으로 센다(2026-10-13 사용자 질문: "6일·8일에 온 사람은?"). 하루 가입
     수십 명이라 딱 그날 값은 요일·우연에 크게 흔들리고, 격일로 공부하는 사람이 그날만 쉬어도 이탈로 잡힌다. "그날 이후 언제든"
     (unbounded)은 구간이 닫히지 않아 지난 값이 계속 오르고 한 번 들른 사람도 남은 걸로 세서 기각. 7~13일 뒤는 세그먼트의
     2주차 결과와 같은 정의라 요약의 전체 값과 세그먼트 값을 바로 비교할 수 있다. D1은 하루라 그대로다.
4. **공부한 날 = 순공 10분 이상 세션이 하나라도 있는 날**(ADR-0009). 자정 분할 조각은 병합하지 않는다(ADR-0012 결정 3).
5. **노출 조건과 순위는 Amplitude Compass 기준을 따른다**(§6). 상관(phi) 0.2 이상만, 상관 순 정렬. %p 차이·배수 정렬은 기각 —
   작고 극단적인 그룹이 1위로 올라온다.
6. **Amplitude 이벤트도 쓴다.** 매일 Export API로 받아 유저×날짜×이벤트 횟수로 적재하고, 리포트는 DB만 읽는다(§7).
   리포트 때마다 다운로드하는 안(Amplitude 장애 = 섹션 누락, 매일 6주치 재다운로드)과 Amplitude 차트 API 안(서버 기준
   "공부한 날"을 못 쓰고 유저별 프로필 불가)은 기각.
7. **별도 배치 인프라는 두지 않는다.** prod 하루 4~6천 건(2026-10-13 실측)으로 서버 안 `@Scheduled`면 충분하다. 장애 범위는
   줄 단위 스트리밍·전용 스레드·타임아웃·크기 상한으로 묶는다. 재검토 신호: 리포트 생성이 수 분을 넘음, 리포트 쿼리가 API 응답에
   영향, ECS 태스크 2개 이상, 크기 상한 초과 알림.
8. **Slack은 요약 1개 + 스레드 댓글 6개.** Incoming Webhook은 스레드를 못 달아 봇 토큰(`chat.postMessage`)으로 바꾼다.
   스레드 순서: 가입 → 리텐션 → 고정 세그먼트 → 명단 → 자동 탐색 → 어제 공부한 유저.
9. **서버에 기록이 없는 행동은 Amplitude로만 본다.** 새 화면 이벤트 수집, FE 자기 신고 유입 채널 연결은 범위 밖이다.

## 3. 공통 정의

- **기준일 A**: 발송일 KST 어제. 오늘은 부분 집계라 쓰지 않는다.
- **가입일 D0**: `users.created_at`의 KST 날짜. Dn = D0 + n일 = "가입 n일 뒤". 메시지에는 "n일째" 대신 "n일 뒤"로 쓴다
  ("7일째"는 가입일을 1일째로 세는 사람과 0일째로 세는 사람이 갈린다).
- **첫 주**: D0~D6(가입일 포함 7일). **둘째 주**: D7~D13(가입 7~13일 뒤).
- **공부한 날**: 그 `stat_date`에 `focus_sec >= 600`인 세션이 하나 이상. 상수는 `StudySessionThresholds`를 공유한다.
- **하루 순공**: 그 `stat_date` 세션들의 `focus_sec` 합.
- **제외 유저**: 설정값 `metrics.report.excluded-user-ids`(팀 내부 계정 등, 기본 빈 목록). 데모·테스트 유저를 빼는 기존 장치는
  없다(랭킹도 탈퇴 유저만 뺀다, 데모 유저는 dev 전용). 탈퇴(`status = DELETE`)는 아직 경로가 없지만, 생기면 코호트에 남겨 이탈로
  센다(빼면 리텐션이 부푼다).
- **비율 표기**: `64% (9/14)`. 분모가 0이면 `—`.
- **조회 범위**: 원본 사실은 `[A−61, A]` 62일, 가입자는 `[A−68, A]`. 28~34일 뒤 코호트(가입 `[A−61, A−34]`, 지난주 값은
  `[A−68, A−41]` — 사실은 A−40부터 필요)와 "연속 Top" 판정(A−2까지 재계산)을 덮는다.

## 4. 섹션 정의

### 4.1 🕐 가입
- 어제 가입 수와 회원번호 범위(`#최소~#최대` user id, 제외 유저 뺌). 전주 같은 요일 대비 증감은 쓰지 않는다(2026-10-13 사용자
  피드백 — 하루 수십 명 규모에선 의미 없음).
- **바로 공부**: 가입 시각부터 3시간 안에 시작한 세션들의 순공 합 ≥ 10분(`started_at` 기준, 자정 분할 조각도 합친다). "가입한 날
  공부한 날"로 세면 23시 가입자는 1시간밖에 기회가 없어 시간대 비교가 기운다. 3시간 창은 어제 가입자도 리포트(10:00) 전에 모두
  닫힌다(최대 03:00).
- 어제 가입자 중 바로 공부한 비율.
- 최근 7일(`[A−6, A]`) 가입을 3시간 구간 8개(00–03 … 21–24)로 나눈 텍스트 막대, 구간마다 "바로 공부 k/n (r%)"(n < 5면 % 생략),
  가입 피크 구간과 바로 공부 비율이 가장 높은 구간(n ≥ 5인 구간 중).
- 공부 분야(`category`: 수능·공시·자격증 등, 미입력 포함) 비율. 로그인 방식은 지금 전원 게스트(`DEVICE`)라 쓰지 않는다.
- 유입: Amplitude 유저 속성의 광고 클릭 유입 여부(`initial_fbclid`·`initial_gclid` 등 클릭 ID 존재)와 `initial_utm_source` 상위 값.
  Amplitude 속성이 없는 유저는 "미수집"으로 센다.

### 4.2 📈 리텐션
구간이 다 끝난 가입자만 센다(아직 구간 중인 사람은 분모에서 뺀다). 각 값은 최근 28일치 가입자 기준이다.

| 이름(메시지 표기) | 분모: 가입일 | 분자: 그중 |
|---|---|---|
| 가입 다음 날 | `[A−28, A−1]` | D1이 공부한 날 |
| 7~13일 뒤 | `[A−40, A−13]`(코호트 C와 같음) | D7~D13 중 공부한 날 ≥ 1일 |
| 28~34일 뒤 | `[A−61, A−34]` | D28~D34 중 공부한 날 ≥ 1일 |

- 6일 뒤·14일 뒤처럼 구간 밖에 온 날은 그 구간 값에 들지 않는다. 스레드에 이 문장을 그대로 쓴다: "7~13일 뒤 = 가입 7일 뒤부터
  13일 뒤까지 7일 중 하루라도 10분 이상 공부한 사람".
- 옆에 지난주 값(같은 계산을 기준일 A−7로).
- **첫 주 미사용**: 가입일 `[A−6−27, A−6]` 중 첫 주(D0~D6) 공부한 날 0일인 비율.

### 4.3 👥 고정 세그먼트
- **코호트 C**: 가입일 `[A−40, A−13]`(둘째 주까지 끝난 최근 28일치 가입자).
- **S1**: 첫 주(D0~D6) 공부한 날 ≥ 3일. **2주차 리텐션**: 둘째 주(D7~D13) 공부한 날 ≥ 1일.
- 표시: 코호트 C를 첫 주 공부한 날로 세 묶음으로 나눠 각 2주차 리텐션을 쓴다 — **3일 이상(S1) · 1~2일 · 0일**. "나머지"
  한 덩어리로 쓰지 않는다(2026-10-13 사용자 질문 "못 채운 사람은 뭐야" — 0일 묶음이 커서 "나머지"가 "조금 해 본 사람"보다 훨씬
  낮게 나오고, 무엇과 비교하는지 안 보였다). 상관은 S1 vs 나머지(1~2일 + 0일) 그대로 계산해 쓴다.
- **주로 한 행동**: 규칙 카탈로그(§5)의 행동형 규칙(묶음 D~I)을 행동으로 쓰고, **S1의 30% 이상이 한 행동** 중 S1 사용률 − 나머지
  사용률이 큰 순 5개, 6번은 항상 **프로필(분야·목표 중 하나라도) 입력**(2026-10-13 사용자 요청). S1이 5명 미만이면 "표본 부족".
  - 프로필은 입력 시점 기록이 없어(`PATCH /me/profile`이 값만 덮어씀) "첫 주에"가 아니라 "지금 기준"으로 표시한다. 오래 남은
    사람일수록 입력할 기회가 많았으니 차이가 부풀 수 있다 — 그래서 자동 탐색 규칙에는 넣지 않는다.
- **어떤 사람**: S1과 나머지의 공부 분야, 가입 시간대(3시간 구간), OS, 광고 유입 비율을 나란히. 광고 유입(가입 스레드의 광고 클릭도)은
  유입 정보(Amplitude 속성)가 있는 사람 중 비율이다 — 미수집을 "광고 아님"으로 세면 수집 장애가 유입 특성처럼 보인다.

### 4.4 🙋 명단: 첫 주 3일 이상 공부한 사람
요약의 "첫 주 3일 이상 N명 중 k명" 뒤에 있는 사람 그대로다(코호트 C의 S1). 2026-10-13 사용자 요청 — 비율만으로는 "이 사람들이
누구고 뭘 했나"를 알 수 없다.

- 두 묶음: **① 둘째 주에도 공부한 사람**(k명) · **② 둘째 주에 안 온 사람**(N−k명). ②는 같은 출발선에서 떠난 사람이라 ①과 나란히
  봐야 차이가 보인다.
- 묶음 안 정렬: 가입일 최신 순. 어제로 둘째 주가 끝난 사람(가입일 A−13)은 앞에 🆕 — 명단은 28일 동안 같은 사람이 계속 나오므로
  매일은 🆕만 보면 된다.
- 묶음마다 30명 상한, 넘으면 "외 N명(가입 M/D 이전)".
- 카드 4줄(예시는 부록 A):
  - 1줄(누구): 닉네임(#id), 가입 시각(시 단위), 분야(목표는 입력한 경우만 괄호), OS(Amplitude 미수집이면 생략), 유입 — 광고 클릭
    ID가 있으면 "광고(utm_source, 없으면 소스 없음)", 아니면 D0~D1에 `invite_deep_link_opened`가 있으면 "초대 링크", 아니면
    utm_source 값, 다 없으면 "표시 없음". Amplitude 속성이 없는 유저는 "유입 미수집".
  - 2줄(공부 흐름): 첫 주 공부한 날·순공 합(최장 연속), 둘째 주 공부한 날·순공 합, A까지의 마지막 공부한 날("어제"·"n일 전",
    첫 주가 마지막이면 "n일 전(첫 주)"), 지금 연속(A부터 거꾸로 센 연속 공부한 날, 0이면 생략). ②는 둘째 주가 "0일"이다.
  - 3줄(첫 주에 한 일): 규칙 카탈로그 묶음 D·E·G·H·I의 행동 중 **한 것만** 횟수와 함께(안 한 건 생략, 없으면 "기록된 행동 없음").
    첫 주에 Amplitude 미수집 창이 있으면 끝에 "(Amplitude 일부 미수집)".
  - 4줄(습관): 묶음 F의 값 — 세션 평균 순공, 순공이 가장 많은 시작 시간대(3시간 구간), 소셜 세션 순공 비율, 세션당 일시정지 수,
    순공 1시간당 딴짓 수(Amplitude, 미수집이면 생략).
- 명단은 첫 주 행동을 보여준다. 세그먼트·탐색이 "첫 주 행동 → 둘째 주"를 보므로 같은 기간을 써야 카드와 통계가 맞는다.

### 4.5 🔍 자동 탐색
- 코호트 C에 규칙 카탈로그 40개를 모두 적용한다(행동 = D0~D6, 결과 = 2주차 리텐션).
- §6 노출 조건을 통과한 규칙을 상관 내림차순(동률이면 해당 인원 많은 순) Top 3.
- 규칙마다: 인원(코호트 대비 %), 상관과 강도 라벨, 2주차 리텐션 vs 안 한 사람, "남은 사람 R명 중 k명이 했음".
- 같은 계산을 A−1, A−2 기준으로도 돌려 세 번 모두 Top 3이면 "3일 연속 Top" 표시.
- 꼬리: "규칙 40개 중 통과 n개 · 제외: 사람 부족 a · 너무 흔함 b · 상관 약함 c · Amplitude 미수집 d"와
  "상관관계이지 인과는 아님. 실험으로 확인할 후보" 주의 문구. 통과가 0개면 "오늘은 조건을 통과한 규칙 없음(표본 부족)".

### 4.6 🧑‍🎓 어제 공부한 유저
- 대상: A가 공부한 날인 유저.
- 단계(위에서 먼저 맞는 하나). 이름은 팀이 부르는 영어 이름(New·Lovers·Comeback·Sometimes)을 요약·스레드 모두 쓰고, 스레드
  첫머리에 기준 문장을 그대로 적는다(2026-10-13 사용자 요청, 이름은 2026-10-14 BY-910).
- Comeback은 처음에 "어제 전 14일 공부 0일"이었다가 **"어제 전 7일 공부 0일"**로 줄였다(2026-10-14 사용자 요청). 그러면
  Comeback은 최근 7일에 어제 하루만 공부한 사람이라 Lovers(3일 이상)와 겹치지 않고, New만 먼저 판정하면 된다.

| 단계 | 조건 | 메시지에 쓰는 기준 문장 |
|---|---|---|
| New | A − D0 ≤ 6 | 어제가 가입 첫 주(가입일 포함 7일) 안 |
| Comeback | `[A−7, A−1]` 공부한 날 0일 | 첫 주가 지났고, 어제 전 7일 동안 공부 안 하다가 어제 공부 (가입 뒤 처음 공부한 사람 포함) |
| Lovers | `[A−6, A]` 공부한 날 ≥ 3일 | 최근 7일(어제 포함) 중 3일 이상 공부 — 첫 주 3일 이상(S1)과 같은 잣대 |
| Sometimes | 나머지 | 나머지 (최근 7일 중 1~2일 공부) |

- 표시 순서는 New → Lovers → Comeback → Sometimes(판정 순서와 달라도 겹치는 사람이 없다).
- 사람마다 두 줄: `닉네임(굵게) (#id) · 가입 n일 뒤 · 어제 순공 h시간 m분(굵게) · 연속 K일`, 하위 항목
  `소셜/싱글 위주 · 과목 n개 · 분야(목표) · 최근 7일 앱 실행 n일`. 목표는 자유 입력이라 입력한 경우만 괄호로 붙인다.
  연속 K일은 A부터 거꾸로 센 연속 공부한 날(62일 상한, 넘으면 "60일+"). 앱 실행 일수는 Amplitude 미수집이면 생략.
- 단계 안에서 어제 순공 내림차순. 메시지 전체 100명 상한, 초과분은 "외 N명".
- 마지막 줄: Amplitude 기준 A에 `app_launched`·`app_foregrounded`가 있지만 공부한 날이 아닌 유저 수("앱만 열고 공부 안 함").

### 4.7 📊 본 메시지(요약)
매일 훑어보는 메시지라 **용어 없이 풀어 쓰고**(2026-10-13 사용자 피드백 — D1·세그먼트·상관 같은 용어는 설명 없이 읽히지
않았다), **"가입"·"리텐션" 묶음 아래 항목과 하위 항목**으로 나눠 쓴다(2026-10-14 BY-910 — 한 줄짜리 긴 문장은 읽히지 않았다).
정확한 정의·분모·코호트 기간은 스레드에 두되, 숫자의 기준(기간·묶음·단계 기준)은 요약에도 괄호로 짧게 쓴다. 형식 규칙은 §9.
전체 모습은 부록 A 본 메시지.
- 상관 강도는 "연관 강함/보통/약함"으로, "N일 연속 Top"은 "N일째 1위"(1위일 때) 또는 "N일째 상위권"으로 쓴다.

  자체가 정보다. 노출 조건에서 빠지면 탐색 스레드 꼬리에 빠진 이유를 한 줄로 쓴다.
- 전체 메시지 예시는 부록 A.

## 6. 노출 조건과 순위

2×2 표: a = 함·남음, b = 함·안 남음, c = 안 함·남음, d = 안 함·안 남음, N = a+b+c+d.

- **사람 수**: a+b ≥ 5 그리고 c+d ≥ 5.
- **너무 흔함**: (a+b)/N ≤ 0.90. 거의 모두가 하는 행동은 남는 사람을 못 가른다(Compass의 "세션 시작" 예).
  - 하한(처음엔 10%)은 두지 않는다(2026-10-13 사용자 피드백 — 누적 가입 540명·DAU 10~20명이면 28일 코호트 250명 안팎에서 25명
    이상이 해야 해, 첫 주 3일 이상 같은 핵심 묶음부터 빠진다). 작은 묶음의 우연은 "각 쪽 5명"과 상관 0.2가 막는다 — 2×2 표의
    카이제곱 = N × phi²라 N ≈ 250에서 phi 0.2는 카이제곱 10(우연일 확률 약 0.2%)이다. 소수만 한 규칙은 인원(%)이 같이 보이고,
    여러 날 연속 상위인지로 다시 거른다.
- **상관**: phi = (ad − bc) / √((a+b)(c+d)(a+c)(b+d)) ≥ 0.2. 분모가 0이면 탈락(상관 약함으로 집계).
- **강도 라벨**: ≥ 0.4 강함, 0.3~0.4 보통, 0.2~0.3 약함(Amplitude Compass 구간).
- **순위**: phi 내림차순, 동률이면 a+b 내림차순, 그다음 카탈로그 순서.
- 음의 상관(하면 덜 남음)은 이번 범위에서 보여주지 않는다.

출처: Amplitude Compass 문서(aha moment, interpret your chart), Reforge "상관 0.2 이상부터 실험 가치".

### 7.2 창(window)
- 창 = KST 하루에 해당하는 수신 시각 24시간. KST 날짜 W의 창은 `start = (W−1)T15`, `end = WT14`(UTC 시 단위, 양끝 포함).
- 처리 대상 = `[오늘 − backfillDays, 어제]` 중 처리 기록이 없는 W, 그리고 창 끝 + 3시간 < 지금. 오래된 것부터.
  첫 배포는 이 규칙으로 과거를 채우고, 실패한 창은 다음 실행이 다시 집는다.
- 창 하나 = 다운로드 하나 + 트랜잭션 하나(처리 기록 insert + 횟수 upsert 가산). 처리 기록은 W를 PK로 `ON CONFLICT DO NOTHING`
  선점 후 0행이면 롤백 — 배포 중 태스크 둘이 같은 창을 처리해도 한 번만 센다.

### 7.3 파싱
- 응답을 임시 파일로 받아 `ZipFile`로 연다(중앙 디렉터리까지 검증 — 순차 읽기로는 항목 경계에서 잘린 zip이 정상 종료처럼
  보인다). `.gz` 항목을 하나씩 `GZIPInputStream` → 줄 단위로 읽고 파일은 지운다. 원본은 저장하지 않는다.
- `user_id`가 없으면 익명(가입 전 웹 방문, 평소 약 7%)으로 건너뛴다. 깨진 JSON·`event_type`/`event_time` 없음·형식 다름·
  숫자가 아닌 `user_id`는 깨진 줄로 건너뛴다. **깨진 줄이 적재한 줄보다 많으면** Export 형식이 바뀐 것으로 보고 창을 실패시킨다.
- `.gz` 항목이 하나도 없는 zip도 실패다(데이터 없음은 404로 온다).
- 문자열의 널 문자는 지우고, `event_key` 120자·`utm_source` 200자·`os_name` 50자로 자른다(넘으면 창 전체가 롤백되고 재시도마다 실패).
- 날짜 = `event_time`(UTC) → KST 날짜. 늦게 수신된 이벤트도 발생일로 들어간다.
- 키 = `event_type`. 아래 3개는 속성값 키를 추가로 센다.

| 이벤트 | 조건 | 추가 키 |
|---|---|---|
| `session_simple_mode_toggled` | `event_properties.on == true` | `session_simple_mode_toggled:on` |
| `session_orientation_changed` | `event_properties.orientation == "landscape"` | `session_orientation_changed:landscape` |
| `social_room_camera_toggled` | `event_properties.on == true` | `social_room_camera_toggled:on` |

- 유저 속성: `user_properties.initial_utm_source`, 광고 클릭 ID(`initial_fbclid`·`initial_gclid`·`initial_ttclid` 등 값이
  비어 있지 않고 `EMPTY`가 아님), 운영체제(`device_family`, 없으면 `os_name` — 웹뷰라 `os_name`은 브라우저다). **값마다 그 값을 본 시각을 따로 두고 더 늦게 본 non-null이 이긴다**(같은 시각이면
  먼저 있던 값). 창 안(Java 병합)과 창 사이(SQL upsert)가 같은 규칙이다. 광고 클릭은 한 번이라도 보이면 남는다.
- 다운로드 크기 상한 200MB(설정값). 넘으면 그 창을 중단하고 예외 → Sentry.

### 7.4 테이블 (V28)
```sql
CREATE TABLE amplitude_export_window (
    window_date  DATE        PRIMARY KEY,           -- KST 날짜 W
    event_count  INT         NOT NULL,              -- 적재한 이벤트 수(user_id 있는 것)
    skipped      INT         NOT NULL,              -- user_id 없거나 숫자 아님

);
CREATE TABLE amplitude_daily_event (
    user_id    BIGINT       NOT NULL,
    event_date DATE         NOT NULL,
    event_key  VARCHAR(120) NOT NULL,
    count      INT          NOT NULL,
    PRIMARY KEY (user_id, event_date, event_key)
);
CREATE INDEX idx_amplitude_daily_event_date ON amplitude_daily_event (event_date);
CREATE TABLE amplitude_user_attribute (
    user_id       BIGINT       PRIMARY KEY,
    utm_source    VARCHAR(200),
    utm_seen_at   TIMESTAMPTZ,
    ad_click      BOOLEAN      NOT NULL DEFAULT false,
    os_name       VARCHAR(50),
    os_seen_at    TIMESTAMPTZ,
    first_seen_at TIMESTAMPTZ  NOT NULL,
    last_seen_at  TIMESTAMPTZ  NOT NULL

```
user_id에 외래키를 걸지 않는다 — Amplitude에는 탈퇴·타 환경 id가 섞일 수 있고, 리포트가 users와 맞춰 거른다.

### 7.5 "수집됨" 판정
리포트는 날짜 W의 창 처리 기록이 있으면 W를 Amplitude 수집일로 본다. 규칙 판정 기간·프로필 기간에 미수집일이 있으면 그
Amplitude 항목은 "미수집"으로 표시하고 0으로 세지 않는다.

              analyzer/ SignupAnalyzer · RetentionAnalyzer · SegmentAnalyzer · SegmentRoster · RuleExplorer · ActiveUserClassifier

- **도메인 조회**: metrics는 다른 도메인 테이블을 읽지 않는다. user·studysession·room·subject·dday 서비스에 "기간 내
  사실"을 돌려주는 메서드를 하나씩 추가한다(계획 참조). 세션의 소셜 여부는 기존 `findQualifyingSessions`와 같은 방식(같은
  시간대에 확정된 방 참여가 있었나)으로 studysession 쿼리가 판정한다.
- **실행기**: `TaskScheduler`·`Executor` 타입 빈을 새로 만들지 않는다. 만들면 Boot의 기본 스케줄러·실행기 자동 구성이 물러나
  다른 스케줄러까지 그 빈으로 돈다. `MetricsJobRunner`가 내부에 단일 스레드 `ExecutorService`를 갖고, 스케줄 메서드는 제출만
  하고 바로 반환한다(prod 스케줄러 풀 2개를 붙잡지 않음).
- **삭제**: `DailyReport`, `HeavyUser`, `CohortFirstWeek`, `RoomVsSingleFocus`, `FocusStat`, `UserSessionDetail`, `QualifyingSession`,
  `NewUser`, `SlackWebhookNotifier`와 이들만 쓰는 조회 메서드·테스트. ADR-0012가 가리키는 `HeavyUserQueryIntegrationTest`는
  헤비유저 조회가 사라지므로 함께 지우고, 자정 분할 비병합 규칙은 `UserTimeline` 단위 테스트가 이어받는다.

## 9. Slack

- `POST https://slack.com/api/chat.postMessage`, `Authorization: Bearer <SLACK_BOT_TOKEN>`, 본문 `{channel, text, blocks,
  thread_ts?, parse:"none", unfurl_links:false, unfurl_media:false}`. 응답 `ok:false`면 `error` 코드로 `SlackNotificationException`. HTTP 429는
  `Retry-After`초 대기 후 재시도.
- **형식(BY-910)**: 메시지는 제목 + 줄들(`SlackMessage`)이고 Block Kit으로 보낸다 — 제목은 `header` 블록, 본문은 `rich_text` 블록
  하나(문단 = `rich_text_section`, 목록 = `rich_text_list` indent 0·1, 인용 = `rich_text_quote`). 들여쓰기는 두 단계(항목·하위
  항목)까지, 핵심 숫자만 굵게, 코드 블록은 쓰지 않는다 — 처음엔 표를 코드 블록으로 정렬했지만 회색 고정폭 상자가 읽히지 않았다.
  같은 깊이로 이어진 항목은 목록 하나로 묶고, 하위 항목에 끊긴 번호 목록은 `offset`으로 번호를 잇는다.
  마크다운 블록은 중첩 목록 지원이 문서로 확인되지 않고 메시지당 12,000자 상한이라 쓰지 않았다.
- **길이**: 블록 전체 길이 상한은 문서에 없고, rich_text 블록 JSON 약 1만 6천~1만 7천 자에서 `msg_blocks_too_long`으로 거절된 보고가
  있다(bolt-js#2867). 그래서 메시지 하나의 대체 글을 6,000자 이하로 둔다. 넘는 스레드는 맨 위 항목 경계에서 여러 댓글로 나눠
  보내고(하위 항목은 위 항목과 같이 간다), 뒤 댓글 제목엔 "(이어서)"를 붙인다. 본 메시지는 스레드를 달 하나여야 해서 자른다.
- `text`는 알림·검색에 쓰이는 대체 글(mrkdwn)이다 — 같은 내용을 하위 항목은 공백 네 칸, 굵은 글은 `*`로 쓴다. 테스트도 이 글로
  비교한다.
- 본 메시지 실패: 기존처럼 `@Retryable` 2회 → Sentry, 스레드는 안 단다.
- 스레드 댓글 실패: 재시도 후 그 댓글만 건너뛰고 다음으로. 댓글 사이 1초 간격(설정값, 테스트 0).
- 토큰·채널이 비었거나 보이는 ASCII가 아닌 문자(개행 등)가 섞이면 발송기 비활성(WARN, 값은 남기지 않음), 리포트 계산도 건너뛴다.
- `text`의 `&`·`<`·`>`는 이스케이프하고 `parse:"none"`으로 URL 자동 링크도 끈다 — 목표·UTM 같은 사용자 입력이 `<!channel>` 멘션이나
  위장 링크가 되지 않게.
  `blocks`의 rich_text 글자는 Slack이 해석하지 않아(멘션·링크는 `user`·`broadcast`·`link` 같은 별도 요소다) 이스케이프하지 않는다
  — 이스케이프하면 `&lt;`가 글자로 보인다. 2026-10-14 예시 발송에 확인 줄(`<https://example.com|링크> · a & b · <합격>`)을 넣어
  보냈다.
- 429는 응답마다 `Retry-After`초(한 번에 120초 상한)를 기다려 최대 3번 다시 보내고, 그래도 막히면 `@Retryable`에서 빠지는
  예외로 끝낸다(짧은 재시도를 얹으면 한도를 더 오래 끈다).
- 봇 앱 권한: `chat:write`, 채널 초대 필요.

## 10. 실패 처리

| 상황 | 처리 |
|---|---|
| Export 실패(타임아웃·5xx·깨진 zip) | 창 롤백, 예외 → Sentry. 다음 실행이 재시도 |
| Export 404 | 0건으로 처리 기록 + WARN·Sentry 경고(prod에서 404는 설정 오류일 수 있다) |
| 200인데 zip이 아님·잘린 zip·`.gz` 없음·깨진 줄 과반 | 창 실패(처리 기록 없음), 다음 실행 재시도 |
| 다운로드 마감(`download-timeout`, 기본 15분) 초과 | 창 실패. 마감은 요청 시작부터의 전체 시간이다(Spring 7 동작) |
| 크기 상한 초과 | 창 중단, Sentry("배치 분리 검토 신호") |
| 어제 창 미수집 | Amplitude 항목 "미수집", 탐색에서 Amplitude 규칙 제외 |
| 분석기 예외 | 그 섹션만 "계산 실패", Sentry. 나머지 발송 |
| 메시지 길이 | 메시지당 대체 글 6,000자 — 스레드는 넘으면 여러 댓글로 나누고, 본 메시지·한 묶음이 혼자 넘는 경우만 뒤쪽 줄을 버리고 "잘림" 표시(§9). 어제 유저 100명 상한, 명단 묶음마다 30명 상한 |
| 중복 발송 | 태스크 2개면 두 번 온다(기존과 같음, 무해). 적재는 창 선점으로 중복 없음 |

## 14. 알려진 한계

- 상관은 인과가 아니고 표본이 작다. 40개 규칙 중 우연히 높은 규칙이 섞일 수 있어 "규칙 40개 중"과 "연속 Top"을 같이 보인다.
- 웹에서 연 초대 링크·스토어 이동 같은 익명 이벤트(약 7%)는 유저와 연결되지 않는다.
- 유입 채널은 광고 클릭 ID·UTM 대용이다. 자기 신고 채널은 FE 연결 후 추가한다.
- 랭킹·타임랩스 이벤트는 prod 출시 후부터 쌓인다. 그전엔 해당 규칙이 "사람 부족"으로 빠진다.
