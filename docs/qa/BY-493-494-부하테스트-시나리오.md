# 부하테스트 시나리오 — coturn 단독(BY-493) · 풀 경로 결합(BY-494)

> 작성: 2026-09-01 · 대상 독자: 팀원·멘토 · 상태: **실행 전 확정 시나리오 v2** (4갈래 적대 검증 반영)

---

## 1. 배경과 목적

**목표: 동시접속 5,000명**을 감당하는 아키텍처 설계의 실측 근거를 만든다.

이전 부하테스트(BY-462 계열, 리포트 #1~#4)의 한계 3가지를 이번에 해소한다:

| 이전 테스트의 한계 | 이번 해소 방법 |
|---|---|
| VPC 내부에서 서버 IP 직결 — ALB·인터넷 구간 미포함 | **ALB 경유 + 모바일 RTT(50ms) 주입**으로 실제 유저 경로 재현 |
| WebRTC 미디어(coturn 릴레이) 부하 미포함 | **turnutils로 릴레이 부하 동시 주입** (결합 테스트) |
| 시그널을 "3초마다 상시"로 과대 재현 (worst-case) | **유저당 총 3회** — 실제 WebRTC 시그널링(연결 수립 시 버스트 후 침묵)에 근접한 현실 모델 |

**이번 테스트가 답할 핵심 질문:**
1. **coturn(Oracle E2.1.Micro)의 지속 가능 릴레이 한계는 몇 쌍인가?** → 릴레이 비율별 "coturn이 버티는 동접 수" 환산표
2. **태스크 1대(최대 스펙 1vCPU/2GiB)는 몇 명까지 받는가?** → "5,000명 = 태스크 몇 대" 설계 근거
3. 시스템 한계는 **min(Spring, coturn)** 중 어느 쪽이 먼저 오는가?
4. 지난 OOM의 원인 규명 — 죽음 시점 힙은 455MB/1GiB뿐이었고 나머지 ~550MB의 정체가 미규명. 유력 가설인 "송신 큐 적체"(CPU 포화 시 세션당 송신 대기줄이 최대 512KB×1000세션=512MB까지 팽창)를 이번에 심은 계측(`sendLimitExceededSessions` 카운터)으로 **확증하거나 기각**한다
5. **egress 비용 모델 제시** — 비용은 산술로 결정된다(동접×릴레이비율×쌍당 0.7Mbps×시간×$0.09/GB). 부하테스트는 이 모델을 "실측"하지 않는다(합성 트래픽을 되재는 순환일 뿐) — 테스트의 역할은 주입 부하 검증(sanity check)까지이며, 모델의 진짜 미지수(릴레이 비율·실사용 시간·**실제 평균 bitrate — 350kbps는 상한이라 정지 장면에선 훨씬 낮을 수 있음**)는 출시 후 운영 로그(BY-490 rtc-stats + coturn NetworkOut)로 대체한다

## 2. 테스트 대상 시스템

```
                        (인터넷, netem +50ms)
[k6 로드젠 c7g.2xlarge] ────────────────────→ [스테이징 ALB:80] → [ECS 태스크] ─→ [RDS]
      │                                              (idle 300s)        │
      │  snap2.sh (관측: 직결 8080, 무지연)  ────────────────────────────┘
[turn 로드젠 c7g.xlarge] ──(인터넷, 서울→오사카 RTT ~30ms)──→ [coturn E2.1.Micro] (운영 서버, **Oracle Cloud ap-osaka-1·예약 IP 161.33.27.117** — BY-578 이전, SSH로 지표 수집)
```

- **테스트 이미지**: 개선 2종이 포함된 빌드 (★ BY-492 Redis 버퍼는 미도입 결정으로 제외 — PR #29·#30 머지 후 dev 기준 재빌드)
  - **BY-470** 체크포인트 코얼레싱 버퍼 (요청당 UPSERT → 5초 벌크, DB 풀 병목 제거 — 실측 pending 141→0)
  - **BY-491** JVM 힙 상한 75%→50% + direct 버퍼 상한 (OOM의 native 원인 대응) + WS 송신버퍼 한도 512KB→64KB + `/actuator/wsstats` 관측
- coturn은 **운영 서버를 직접** 테스트 (앱 미출시로 유휴 — 시작 전 유휴 확인을 게이트로 둠). coturn은 **Oracle Cloud로 이전 완료(BY-578)** 상태라, 스테이징(AWS)과 coturn(Oracle 테넌시 breathlessyouth) **두 클라우드를 병행 운용**한다

## 3. 부하 모델 (현실 모델의 근거)

| 요소 | 값 | 근거 |
|---|---|---|
| 방 구성 | **3명/방·6명/방 두 변형** | 3명=서비스 기본, 6명=최대 방 크기. 방 인원이 브로드캐스트 팬아웃과 릴레이 쌍 수를 좌우한다 (풀메시: 3명방 1쌍/인, 6명방 2.5쌍/인) |
| 영상 | **360p / 15fps / 350kbps / VP8** | 프론트 송출 상한 설정 (확정값) |
| 체크포인트 | HTTP PUT, **1초 주기** | 실제 운영 환경과 동일 (이전 테스트에서 0.5vCPU는 1초에 OOM — 런 A 부검 대상) |
| 시그널 | **유저당 총 3회** (세션 300초 창의 10/45/80% 지점, 피어 로테이션) | 실제 WebRTC는 연결 수립 시 버스트 후 침묵 — 재협상 수준의 저빈도만 재현 |
| 상태 브로드캐스트 | 10초 주기 (카메라/집중/공부시간) | 기존과 동일 |
| **릴레이 비율** | **30% (기본)** | 업계 통용 15~25%, 변동 0~50%(심하면 70%) — 평균보다 보수적으로 30% 채택. 출시 후 자체 로그(BY-490 rtc-stats)로 실측 대체 예정 |
| 모바일 RTT | +50ms (편도 주입) | LTE/5G 평균 RTT 40~60ms 재현 |

> **릴레이 비율 근거 조사**: callstats.io 프로덕션 통계 분석(webrtcHacks "The Big Churn")에서 컨퍼런스의 22%가 TURN 릴레이 필요(그중 9%는 TCP 릴레이까지 하강). 업계 조사(Kranky Geek 등) 통용 범위 15~25%. BlogGeek.me는 "0~50%까지 환경별 편차가 크니 가정하지 말고 직접 측정하라" — 그래서 평균보다 보수적인 30%로 측정하고, 출시 후 자체 로그(BY-490)로 실측 대체.

**릴레이 산술** (이 문서의 모든 coturn 숫자의 기초):
```
릴레이 쌍 1개 = 양방향 스트림 2개 = 0.35 × 2 = 0.7Mbps가 coturn을 통과
Oracle E2.1.Micro 지속 대역폭 = 0.48Gbps  →  지속 한계 가설 ≈ 685쌍 (구 t4g.micro 64Mbps≈91쌍에서 갱신)
릴레이 비율 30% · 3명방(1쌍/인): 동접 N명 → 릴레이 쌍 0.3N개 → 동접 한계 ≈ 2,283명
릴레이 비율 30% · 6명방(2.5쌍/인): 동접 N명 → 릴레이 쌍 0.75N개 (3명방의 2.5배) → 동접 한계 ≈ 913명
  → 1000명 = 750쌍 = 525Mbps ⚠️ 6명방·30%는 동접 1000명에서 대역폭 한계 초과
```

## 4. 테스트 ① — coturn 단독 한계 실측 (BY-493, 약 60분)

> **✅ 실행 완료 (2026-09-03 micro → 2026-09-04 A1 재측정)** → 결과는 `2026-09-04-리포트5-3-coturn-A1-재측정.md`. 아래는 실측 반영본이다. (E2.1.Micro 기준의 첫 실행(#5-1)은 인터넷 50Mbps 캡으로 55~60쌍이 나와 셰이프를 A1으로 교체했고, 그 수치는 무효 처리.)

**대상**: Oracle Cloud `coturn-a1` — VM.Standard.A1.Flex **2 OCPU / 12GB**(Always Free 한도), 네트워크 OCPU당 1Gbps(인터넷 캡 없음), coturn 4.6.1, 릴레이 스레드 2개. 공인 IP 161.33.27.117.

**로드젠**: 같은 리전·같은 VCN의 임시 A1 인스턴스(2 OCPU). **Oracle 리전 내부 트래픽이라 AWS·Oracle egress 비용 0.** 측정 후 즉시 삭제.

**측정 방식 (요약)**: 프로그램으로 "가짜 통화 쌍"을 만들어 실제 영상과 같은 속도의 데이터를 coturn 경유로 주고받게 한다. 이 쌍의 수를 **100 → 200 → 400 → 600 → 800개**로 4분마다 늘려가면서, 단계마다 세 가지를 기록한다:

1. **패킷이 사라지는가** (손실률) — 사라지면 유저 화면이 깨지거나 멈춘다
2. **패킷이 늦게 도착하는가** (지연·지터) — 늦으면 영상이 밀린다
3. **coturn 서버의 CPU(특히 steal)·pps·네트워크가 얼마나 차는가**

손실이 1%를 넘는 첫 단계에서 램프를 멈추고, 그 직전 무손실 단계로 **30분 소크**를 돌려 "잠깐 버팀"과 "계속 버팀"을 구분한다.

**도구**: coturn 패키지의 `turnutils_uclient`(Ubuntu 24.04 arm64), 100쌍/프로세스 분할·1초 간격 기동(초기 할당 폭주 방지)

**핵심 파라미터**:
- `-y -c`: 클라이언트 페어링 + RTCP 비활성 — **클라이언트 2개 = 릴레이 쌍 1개** (`-m` = 쌍 × 2)
- `-l 875 -z 20`: 875B × 50pps = **스트림당 0.35Mbps**(쌍당 0.7Mbps). 실제 영상은 ~1,200B × 36pps라 이 모델이 pps 기준 ~40% 보수적이다.
- 판정 도구 주의: 요약 전 timeout으로 종료되면 누적 송/수신 카운트로 손실을 역산한다(1차 스윕에서 "손실 0"으로 오판한 결함을 고침)

**단계표 (실측)**:

| 단계 | 릴레이 쌍 | 제시 부하 | coturn 송신 | 손실 | RTT | 판정 |
|---|---|---|---|---|---|---|
| 1 | 100 | 70Mbps | 73Mbps | 0.05% | 0.3ms | ✅ |
| 2 | 200 | 140Mbps | 147Mbps | 0.27% | 1.1ms | ✅ 경계 |
| 소크 | 200 × 30분 | 140Mbps | 147Mbps | **0.09%** | 5.6ms | ✅ 지속 안정 |
| 3 | 300 | 210Mbps | **156Mbps** | 🔴 28.9% | 57ms | 절벽 |
| 4 | 400 | 280Mbps | **156~164Mbps** | 🔴 42~45% | 25~116ms | 절벽 |

→ **H(무손실 최대) = 200쌍(≈140Mbps)**. 300쌍부터 송신이 ~160Mbps·21k pps에서 고원을 이루고 초과분은 버려진다.

**판정 근거**: 절벽에서도 NIC 드롭 0, 대역폭 사용 7%(2Gbps 중 140Mbps), idle 26~33% — 대역폭·총 CPU 포화가 아니다. 벽은 **릴레이 스레드(2개)의 pps 처리 한계 ≈ 21k pps**이고, 여기에 공유 호스트의 **steal 25~30%**(부하와 함께 11→29%로 상승)가 겹친다. 손실은 UDP RcvbufErrors(스레드가 못 비운 소켓 큐)로 나타나며, 소켓 버퍼를 20배 키워도 손실은 그대로고 RTT만 악화(bufferbloat)해 버퍼 튜닝은 답이 아님을 확인했다.

**측정**: coturn VM 10초 수집(NIC Mbps/pps/drop, CPU usr/sys/soft/steal/idle, UDP RcvbufErrors) + uclient 단계별 손실·RTT. 로드젠 결백은 로드젠 측 UDP 에러 0·send dropped 0으로 확인.

**결과**: X쌍까지 손실이 1% 안이면 그게 서버 한 대의 실측 수용량이다. 릴레이를 타는 연결이 30%라고 할 때 **3명방 기준 X÷0.3명, 6명방(풀방) 기준 X÷0.75명**까지 이 서버 한 대로 감당할 수 있다는 뜻이다.

**동접 환산표** (실측 H=200쌍 기준 — 이 표가 ①의 최종 산출물):

| 릴레이 비율 | 3명방 동접 한계 | 6명방(풀방) 동접 한계 |
|---|---|---|
| 10% | 2,000명 | 800명 |
| **30% (측정 기준)** | **667명** | **267명** |
| 50% | 400명 | 160명 |
| 70% | 286명 | 114명 |
| 100% (최악) | 200명 | 80명 |

> 실제 영상 패킷(1,200B) 기준으로는 H≈280쌍(6명방 ~370명)까지 여유가 있다. 이 표는 **순간 동접**이며, 월 10TB 트래픽 한도가 결정하는 누적 사용시간 예산은 §9의 운영 용량 모델이 별도로 담당한다. **coturn 1대(6명방 ~267)가 Spring(A스펙 2,000)보다 훨씬 먼저 병목**이므로 확장 로드맵은 릴레이 레버(송출 비트레이트 절감 → OCPU 증설/2대 분산)를 앞세운다.

## 5. 테스트 ② — 풀 경로 결합 (BY-494, 런당 약 12~15분)

**k6 프로파일** (ALB DNS 경유, `ws://`+`http://`, 체크포인트 주기는 런 변형별):

```
0.5vCPU, 1GiB: 500명(75s) → 1000(75s) → 1500(75s) → 2000(300s)
1vCPU,   2GiB: 1000명(75s) → 2000(75s) → 3000(75s) → 4000(75s) → 5000(300s)
HOLD=900(세션 유지, 안 나감) · 시그널 총 3회/인 · 상태 브로드캐스트 10초 · 로드젠→ALB 왕복 +50ms(netem)
```

**릴레이 부하는 주입하지 않는다** (2026-09-03 결정): 미디어 릴레이는 클라이언트↔TURN 서버 간에만 흐르고 Spring/ALB를 거치지 않는다. Spring이 릴레이와 엮이는 지점은 입장 시 ICE 자격 발급(join 응답)과 시그널링 중계(WS)뿐이며 둘 다 k6 모델에 포함돼 있다. coturn 한계는 ①에서 독립 실측했고 두 서버는 공유 자원이 없으므로, ②에 릴레이를 동시 주입해도 Spring 지표에 정보가 더해지지 않고 AWS egress만 소모된다.

**이미지**: dev + BY-470(코얼레싱 버퍼) + BY-491(힙 상한·WS 송신버퍼 한도) (+ 2차 재실행은 BY-593 cleanupExpired 인덱스). coturn 단독 = 운영과 동일 경로.

### 각 사양마다 총 4번 테스트

- **체크포인트 1초**
    1. 방 인원 3명
    2. 방 인원 6명
- **체크포인트 3초**
    1. 방 인원 3명
    2. 방 인원 6명

체크포인트 주기(1초 vs 3초)는 클라이언트 설정값이라 서버 쪽 DB 쓰기·코얼레싱 버퍼 압력에 어떤 차이를 주는지, 방 인원(3 vs 6)은 같은 동접에서 브로드캐스트 팬아웃 2배·SNAPSHOT 페이로드 증가가 WS 버퍼·CPU에 어떤 차이를 주는지를 각각 분리해 본다.

**런 구성** (각 스펙을 위 4가지 변형으로 실행 — **A-1s-3 / A-1s-6 / A-3s-3 / A-3s-6 / B-1s-3 / B-1s-6 / B-3s-3 / B-3s-6, 총 8런**):

| 스펙 | 태스크 | 프로파일 | 목적 |
|---|---|---|---|
| **A** | 0.5vCPU/1GiB (현재 prod) | 500→2000 | 현 스펙에서 2000명 SLO 유지 여부 + 개선 3종 효과 · **10초 주기 정밀 캡처**(OOM 부검용) |
| **B** | **1vCPU/2GiB (최대 스펙)** | 1000→5000 | ★ 태스크당 수용량 — SLO 이탈 또는 태스크 사망 지점 = **실측 무릎점** |

**런 전환 절차** (측정 오염 방지): **매 런 사이에 태스크를 강제 교체**(`update-service --force-new-deployment` → `services-stable` 대기 → 새 태스크 IP 재조회 → health UP 확인 → 캡처 스크립트에 주입)해 힙·WS 세션·버퍼 상태를 0에서 시작한다. A→B 전환 시에는 태스크 정의(1vCPU/2GiB)를 새로 등록해 같은 절차로 교체한다. (TG deregistration 30s·헬스체크 10s/2회로 단축 설정)

> 릴레이 비율 변형 런은 두지 않는다 — 릴레이 용량은 ①의 실측 한계 + §4 환산표로 커버된다.

**방법론 개선 (3차 사후 확정 — 다음 라운드부터 적용)**: 3차(#5-4)에서 "매 런 태스크 강제 교체" 때문에 교체 직후 JIT 콜드 JVM에 입장 버스트가 겹쳐 런 전체 p95가 램프 초반 2분에 좌우되고, 같은 조건이 라운드마다 뒤집히는 편차가 관측됐다(§1-3·§1-4).
1. **워밍업 60초**: 태스크 교체 후 k6 `WARMUP=1`(100명 저부하 60초)로 JIT을 데운 뒤 본 램프 진입. 워밍업 구간 지표는 리포트에서 제외.
2. **램프/유지 분리 표기**: 최종 인원 95% 도달 시점부터 유지 구간만 잘라 CPU 중앙/최대·WS 이탈·ALB p99·4xx를 별도 표로 낸다(런 전체 p95는 참고값).
3. **경계 조건 반복**: CPU 60~90%대에 걸리는 구성(A스펙 3명방, B스펙 5,000)은 **2~3회 반복해 중앙값** 사용.
4. **태스크 하드웨어 기록**: 런 시작 시 태스크의 `lscpu`/`/proc/cpuinfo`(Graviton 세대)를 스냅샷에 남겨 Fargate 배치 편차를 분리.
5. **드라이버 END 시각은 k6 exit 직후 기록**하고 k6 종료에 타임아웃을 씌운다 — 3차에서 END 지연이 "태스크 교체 20~40분"으로 오독됐다.

## 7. 실행 게이트 (전부 통과해야 본 부하 진입)

4. **coturn 접근**: Oracle VM SSH(`~/.ssh/oracle-coturn`, ubuntu@161.33.27.117) 접속 + coturn active 확인. 지표는 SSH로 ethtool/ss/vnstat 수집 (CloudWatch 대신 — BY-578 이전 반영)
5. netem 프리플라이트: 1ms 시험 적용→제거, ALB가 IPv4로 잡히는지 확인
6. coturn 실사용 트래픽 유휴 확인 (베이스라인 기록)

## 10. 산출물

1. **리포트 #5** (기존 양식): 런별 요약표 → 인원별 상세 → p95/p99 → 구간 분해(평균) → coturn 한계 판정 → **"5,000명 아키텍처: 태스크 N대 × M명 + coturn 증설안"** 결론
1-b. **egress 용량 모델** (산술 — BY-578 Oracle 이전으로 "비용"에서 "무료 한도 내 용량"으로 재정의): 월 10TB 무료 ≈ **31,700 쌍-시간/월**. 릴레이 30% 기준 일간 수용량 3명방 3,527 인-시간 / 6명방 1,411 인-시간 (릴레이 10~100% 전체 표는 §9 운영 용량 모델). 초과분도 $0.0085/GB(AWS의 1/10). 주의: 350kbps는 **상한**이라 실제 평균 bitrate는 더 낮아 실효 수용량은 이보다 클 가능성 — 출시 후 운영 실측(BY-490)으로 대체. **산술 모델**임을 명시
1-c. **coturn 증설 옵션**: Oracle 무료 계정은 1인 1계정 — **팀원 3명 각자 계정으로 coturn 3대 증설 가능** (월 30TB·합산 1.44Gbps로 모든 용량 3배). 단 시크릿 3벌 관리, 계정 소유권이 개인별 분산(이탈 시 서버 소실 리스크), 클라 TURN URL 3세트 구성이 전제 — 실측 한계가 나온 뒤 필요 시점을 판단

## 11. 알려진 한계 (정직하게 보고서에 명시할 것)

- **TLS 미포함** (`ws://`/HTTP 80) — 스테이징 도메인·인증서 부재. TLS 종단은 ALB라 서버 부하 결론엔 영향 적음
- **릴레이 30%는 가정치** — 출시 후 rtc-stats(BY-490)로 실측 대체
- turnutils c2c 모드는 서버 소켓 연산이 실제 대비 ~2배 → **CPU 한계는 보수적(하한) 추정치**
- 셰어드 CPU(1/8 OCPU) 특성상 CPU 한계는 이웃 부하에 따라 변동 가능 — 측정 시점 값으로 서술, %steal 병기 (§4 판정 기준)
- **과거 런(리포트 #1~#4)과의 직접 비교 불가** — 부하 모델(시그널 상시→3회, 체크포인트 1초→3초)과 서버 이미지(개선 3종)가 동시에 바뀌어 개선 효과와 부하 경감 효과를 분리할 수 없음 (worst-case 재현 런은 시간 절약을 위해 의도적으로 생략). 이번 결과는 "현실 모델 기준 수용량 수립"으로 포지셔닝
- 입장 지연 지표에 스크립트 고정 대기 500ms 포함 — 리포트에서 차감 표기

## 부록 — 용어 (비개발 독자용)

- **TURN 릴레이**: 두 사용자가 방화벽 문제로 영상 데이터를 직접(P2P) 못 주고받을 때, 서버(coturn)가 중간에서 대신 전달하는 것. 전체 연결의 일부(가정 30%)만 릴레이를 탄다.
- **셰어드 코어(1/8 OCPU)**: Oracle 무료 VM은 물리 코어를 다른 사용자와 나눠 쓴다. 보장치는 코어의 1/8이고 유휴 용량이 있으면 더 쓸 수 있어, CPU 한계가 측정 시점에 따라 달라질 수 있다 (%steal 지표로 확인).
- **netem**: 로드젠에서 인위적으로 네트워크 지연(+50ms)을 넣어 모바일 사용자의 체감을 재현하는 리눅스 기능.
- **p95/p99**: 요청 100개 중 95번째/99번째로 느린 요청의 응답시간 — "거의 모든 사용자가 이 시간 안에 응답을 받는다"는 지표.
