# 부하테스트 리포트 #5-1 — coturn 단독 한계 실측 (테스트①)

**목적**: Oracle coturn 서버 한 대가 릴레이 쌍을 몇 개까지 품질 저하 없이 버티는지 실측 → 릴레이 비율별 동접 한계 환산
**대상**: Oracle Cloud `coturn` VM — **VM.Standard.E2.1.Micro** (1/8 OCPU 셰어드 · 1GB · 스펙표 0.48Gbps) · ap-osaka-1 · coturn 4.6.1
**공통**: turnutils_uclient 가짜 통화 쌍(스트림당 875B×50pps = 0.35Mbps, 쌍당 0.7Mbps 양방향) · 부하생성기 AWS 서울 c7g.xlarge → 인터넷 경유 · 단계당 6분 · 손실률·RTT·coturn NIC/CPU 30초 수집

## 3. 근본 원인

**Oracle Always Free 문서에 명시된 한도**: E2.1.Micro는 *"up to 50 Mbps network bandwidth via the internet. Traffic … within the same Oracle Cloud region is up to 480 Mbps."* — 스펙표의 480Mbps는 **리전 내부** 수치였고, 인터넷에서 오는 유저 트래픽은 **50Mbps 캡**. 실측 고원 50.7Mbps(와이어 오버헤드 포함)가 이 수치와 일치한다.
사전 가설(685쌍)은 480Mbps를 인터넷 대역폭으로 오독한 산술이었다. PAYG 전환으로도 이 셰이프의 캡은 풀리지 않는다 (Always Free 리소스는 업그레이드 후에도 동일 한도).

## 4. 결론

- **한계선**: coturn(E2.1.Micro) 한 대 = **단기 무손실 55쌍, 30분 지속 시 55쌍에서도 ~1% 손실**(셰어드 CPU steal 영향) → 안전 운용 한계는 **~50쌍(35Mbps)**, 경계 ~60쌍(50Mbps). 70쌍부터 손실, 100쌍이면 31% 유실.
- **동접 환산** (실측 H=60쌍): 릴레이 30% 기준 **3명방 ≈ 200명 / 6명방(풀방) ≈ 80명**. 릴레이 50%(팀 실측 수준)면 **120명 / 48명**.
- **가설 판정**: ① "지속 한계 ≈ 685쌍" **기각** (실측 60쌍) · ② "coturn은 더 이상 첫 병목이 아님" **기각** — 동접 200명 이전에 coturn이 먼저 막힘.
- **개선 우선순위**: ① **Cloudflare TURN을 ICE 목록 우선으로**(BY-587 — 월 1TB 무료, pps/대역폭 정책 없음, coturn은 백업) → ② **A1.Flex 확보**(1Gbps/OCPU, 50Mbps 조항 없음 — 자동 재시도 cron 가동 중, PAYG 전환 시 확보 확률↑) → ③ 프론트 pps 절감(오디오 ptime 40ms·10fps·250kbps) → ④ 팀원 계정 3대 증설(3×50Mbps).
  > **정정(2026-09-04)**: Cloudflare TURN은 검토 후 미채택(BY-587 폐기). 실제 조치는 A1 이전(#5-3, H=200쌍)이었고 이후 확장은 송출 비트레이트 절감 → OCPU 증설/2대 분산 순.
- **비용**: 이번 테스트 AWS egress **55.3GB ≈ $7** (인스턴스·RDS·ALB 포함 ~$10). Oracle 측 10TB 무료 한도 소모 0.5%.
- **다음 회차로 이월**: TCP 릴레이 스모크, 테스트②(Spring 풀 경로 A/B×3/6명방) — 스테이징 전체 테어다운 완료 상태에서 재구축 필요(~30분).

**알려진 한계**: 관측점이 AWS 서울 단일 — 국내 ISP 유저 경로에서 같은 캡이 걸리는지는 직접 검증 못 함(집 회선 한계). 다만 Oracle 문서상 캡이 인스턴스 정책이라 경로와 무관하게 적용될 가능성이 높다.
