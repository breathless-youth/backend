# 확장 로드맵 v2 — DAU 구간별 실행 계획 (BY-593 적용 · coturn A1 실측 반영)

2026-09-04 실측(#5-3 coturn A1, #5-4 풀 경로 v2) 기준으로 전면 개정. 이전 판의 "릴레이는 서버보다 늦게 병목" 전망은 틀렸다 — **coturn 1대의 한계가 Spring보다 7배 이상 먼저 온다.** 수치는 운영 권장값(방 6명·체크포인트 3초·릴레이 비율 30%) 기준이다.

---

## 0. 전제 — DAU → 피크 동접 환산

부하를 결정하는 건 순간 동접이다. 스터디 앱은 저녁 집중·긴 세션이라 **피크 동접 ≈ DAU × 15%** 를 보수적으로 쓴다. 실제 피크/DAU가 확보되면 이 비율만 바꾸면 전체 표가 따라 움직인다.

| DAU | 1,000 | 1,800 | 3,500 | 7,000 | 13,000 | 26,000 | 33,000 |
|---|---|---|---|---|---|---|---|
| 피크 동접(×15%) | 150 | 270 | 530 | 1,050 | 2,000 | 4,000 | 5,000 |

## 1. 현재 수용 능력 (실측)

**Spring 서버 — BY-593 적용 후 (#5-4)**

| 스펙 | 안전 동접 | 근거 |
|---|---|---|
| **A = 0.5vCPU/1GiB (현행 prod)** | **2,000** | cp3·6명방 전 SLO. **cp1·3명방도 전 SLO 통과**(BY-593 전엔 붕괴). CPU 56~66% |
| **B = 1vCPU/2GiB** | **4,000** (최대 5,000) | 4,000까지 이탈 0. 5,000은 cp·6명방 완주하나 입장 버스트 CPU 94~99%, cp3·3명방은 불안정 |

- 단일 태스크 상한은 B 5,000. 그 이상은 방 상태가 인메모리라 **Redis(BY-492) 선행 후 수평 확장**만 가능.
- 남은 서버 병목은 방 순회가 아니라 **입장 버스트(join + STOMP CONNECT + 스냅샷 팬아웃)** 다.

**coturn — Oracle A1 2 OCPU 실측 (#5-3)**

| 구성 | 무손실 릴레이 쌍 H | 6명방·릴레이30% 동접 (H÷0.75) | 3명방 동접 (H÷0.3) |
|---|---|---|---|
| **A1 2 OCPU (현재)** | **200쌍(140Mbps)** | **~267** | ~667 |
| A1 2 OCPU, 실제 영상 패킷(1,200B×36pps) 기준 *환산* | ~280쌍 | ~370 | ~930 |
| + 송출 비트레이트 350→250kbps(pps ∝ 비트레이트) *추정, **무료*** | ~390쌍 | ~520 | ~1,300 |
| A1 4 OCPU (relay-threads 4) *추정, **유료 ≈ $27/월*** | ~400쌍 | ~530 | ~1,330 |
| 4 OCPU + 250kbps *추정* | ~780쌍 | ~1,040 | ~2,600 |
| coturn N대 분산 | ×N | | |

- 한계의 정체는 **릴레이 스레드 pps + 공유 호스트 steal(25~30%)** — 대역폭·메모리·NIC은 여유. 그래서 **OCPU(스레드)와 pps**가 레버. 소켓 버퍼는 릴레이 소켓(128KiB 하드코딩) 재측정이 남아 있어 **미검증**(#5-3 §2-2 정정) — 무료라 최우선 실험.
- *추정* 행은 pps 비례 가정이며 확장 직후 재측정으로 확정해야 한다.
- 릴레이 비율 30%는 가정이다. 실측이 10%면 coturn 수치가 ×3 여유, 50%면 ×0.6이다 — **§4의 릴레이 비율 실측이 이 표 전체의 정확도를 좌우**한다.

## 2. DAU 구간별 실행 로드맵

| DAU | 피크 동접 | 병목이 오는 곳 | **이 구간 전에 해둘 조치** |
|---|---|---|---|
| **~1,000** | ~150 | 없음 | 현행 유지(A스펙 + A1 2 OCPU). **BY-593 머지·배포**, 체크포인트 3초·방6명 기본값 |
| **~1,800** | ~270 | **coturn A1 1대 한계(267)** | ① **송출 비트레이트 350→250kbps(무료, pps ∝ 비트레이트)** → 6명방 ~520 ② 릴레이 비율 실측. (OCPU 2→4는 **무료 아님** — Always Free는 모든 테넌시 공통 월 1,500 OCPU-h 풀, 초과 ≈ $27/월) |
| **~3,500** | ~530 | coturn 2 OCPU+250kbps 한계 | ③ **A1 OCPU 2→4**(≈$27/월, relay-threads 4) → ~1,060 |
| **~7,000** | ~1,050 | coturn 1대 최종 한계 | ④ **coturn 2대 분산**(ICE 목록에 2대 제공, 클라이언트 자동 분산) |
| **~13,000** | ~2,000 | **Spring A스펙 한계** | ⑤ **B스펙(1vCPU/2GiB) 승격**(tfvars 한 줄, 비용 2배). coturn은 3~4대 분산 |
| **~26,000** | ~4,000 | Spring B 안전선 | ⑥ **입장 버스트 최적화**(전역 락→방 단위 락, 입장 지터, WS 그레이스풀 셧다운) |
| **~33,000** | ~5,000 | Spring 단일 태스크 상한 | ⑦ **Redis(BY-492) 재개 → 수평 확장 + 오토스케일**. coturn 대량 분산 |

> 읽는 법: 각 행의 조치는 "그 DAU에 **도달하기 전**"에 끝내야 한다. 릴레이 조치(①~④)가 서버 조치(⑤~⑦)보다 훨씬 앞에 온다는 게 이번 개정의 핵심이다.

## 3. 확장 레버 — 싸고 빠른 순서

**릴레이(coturn) — 먼저 당길 것**
1. **송출 비트레이트 절감(350→250kbps)** — `peerMesh.ts` maxBitrate 한 줄, 무료. 영상은 MTU(~1,200B)로 잘려 pps ∝ 비트레이트라 쌍 수 ~1.4배. 화질 트레이드오프. (ptime은 오디오 전용 설정이라 영상만 보내는 우리 앱엔 무효)
2. **A1 OCPU 2→4** — **유료(≈$27/월)**. Always Free A1은 2026-06-15부터 모든 테넌시 공통 월 1,500 OCPU-h/9,000 GB-h 풀이라 2 OCPU 상시가 한도. 필요 시 헌터로 확보 → 이전(예약 IP 이동, IPv6 갱신). 스레드 2배.
3. **coturn 2대 분산** — 두 번째 A1(유료 셰이프이거나 다른 리전 Always Free) + ICE 목록 2개. 클라이언트가 자동 분산.

**서버(Spring)**
4. **체크포인트 3초·방6명 기본값** — 무료. BY-593 후엔 cp1·3명방도 A스펙 2,000 통과하지만 여유를 위해 유지.
5. **B스펙 승격** — DAU ~13,000 전.
6. **입장 버스트 최적화** — 방 단위 락, 입장 지터, WS 그레이스풀 셧다운(배포 시 5,000 WS 드레인 20~40분 문제도 해결).
7. **Redis + 수평 확장** — DAU ~33,000 전.

## 4. 지금 당장 (DAU와 무관하게 먼저)

- **BY-593 머지·prod 배포** — 실측으로 검증됨(A스펙 cp1·3명방 CPU 100→66%). 퀴즈 게이트 → 커밋 → PR.
- **coturn 릴레이 소켓 버퍼 4MiB 재측정** — 무료·30분(Oracle 내부 로드젠). coturn이 릴레이 소켓 SO_RCVBUF를 64KiB로 하드코딩해 steal 수 ms에도 넘침(#5-3 §2-2). LD_PRELOAD 심 또는 소스 패치로 4MiB 적용 후 H 재측정 — 200쌍 상향 가능성.
- **송출 비트레이트 250kbps 검토** — DAU 1,800이 첫 병목이라 급한 **무료** 레버(pps ~28%↓). OCPU 증설은 유료(≈$27/월)라 후순위. 실측 H는 875B 모델 기준이라 실제(1,200B)로는 ~280쌍 여유.
- **릴레이 비율 실측** — 클라이언트 ICE 통계(BY-490)에서 relay 후보 선택률. §1·§2 전체가 이 값에 걸려 있다.

## 5. DAU가 찍혔을 때 같이 볼 것 (관찰 지표 + 트리거)

**상시**

| 지표 | 어디서 | 정상 | 이러면 조치 |
|---|---|---|---|
| coturn NetworkOut Mbps / pps | OCI Monitoring | < 100Mbps (2 OCPU 기준 안전선 ~70%) | 120Mbps↑ 지속 → 다음 릴레이 레버 |
| coturn **steal %** | VM `mpstat` / 수집기 | 10~30% | 40%↑ → 호스트 노이즈, 이전·증설 앞당김 |
| 릴레이 비율 | 클라이언트 ICE 통계 | 가정 30% | 실측치로 §1 표 재계산 |
| ECS CPU (평균/피크) | CloudWatch | < 70% | 70%↑ 지속 → B스펙, 90%↑ → 즉시 |
| 입장 p95 | k6/APM | < 1s (500ms 측정 하한) | 초과 지속 → 입장 버스트 최적화 |
| checkpoint p99 | k6/APM | < 500ms | 초과 → 체크포인트 주기·CPU 확인 |
| ECS 메모리(RSS) | CloudWatch | < 85% | 85%↑ → 스펙업(힙% 올리지 말 것) |
| RDS CPU | CloudWatch | 5~10% | 20%↑면 그때 DB를 후보로 |
| Oracle 월 아웃바운드 | OCI | < 10TB | 근접 시 비트레이트 절감·분산 |

**DAU 구간별 트리거**

| DAU(피크) | 도달 시 확인 |
|---|---|
| **~1,000 (~150)** | 릴레이 비율 실측치 확보됐는지 · coturn Mbps/steal 추세 · BY-593 배포 후 prod CPU |
| **~1,800 (~270)** | **coturn NetworkOut이 100Mbps 근접?** → 비트레이트 250kbps 적용 완료됐는지. 손실(RcvbufErrors) 증가 여부 |
| **~3,500 (~530)** | OCPU 증설 결정($27/월) · 비트레이트 조정 후 재측정 H · 사용자 체감 지연 |
| **~7,000 (~1,050)** | 2대 분산 트래픽 분배 비율 · 두 번째 인스턴스 비용 · Spring CPU 추세 |
| **~13,000 (~2,000)** | ECS CPU 70%↑ 지속 → B 승격 · 입장 p95 · 배포 시 드레인 시간 |
| **~26,000 (~4,000)** | 입장 버스트 시 CPU 피크·ALB p99 · 태스크 교체 시간 · committed/RSS |
| **~33,000 (~5,000)** | 단일 B태스크 포화 → Redis+수평 착수 · coturn 총량 |

> 원칙: **coturn Mbps·steal이 1차 신호**(가장 먼저 오는 병목), 그다음 ECS CPU, 입장 지연은 그 그림자, DB·메모리는 뒤따르는 확인 대상.

## 6. 한눈 요약

- **첫 병목은 DAU ~1,800(피크 ~270)의 coturn A1 1대** — 서버가 아니라 릴레이. 무료 레버는 비트레이트 250kbps, 그다음 OCPU 증설($27/월)·2대 분산. (ptime은 오디오용 — 영상 전용 앱엔 무효)
- **DAU ~7,000까지 릴레이 3단계**(비트레이트↓(무료) → OCPU↑($27/월) → 2대 분산)로 버티고, **Spring은 A스펙 그대로 DAU ~13,000까지** 간다(BY-593 덕).
- **DAU ~13,000 B 승격, ~26,000 입장 버스트 최적화, ~33,000 Redis+수평 확장.**
- 가정 두 개(피크/DAU 15%, 릴레이 30%)를 실측으로 바꾸는 게 로드맵 정확도의 전부다.
